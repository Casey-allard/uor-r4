UOR-R4

Where UOR-R4 is going

In one paragraph. The goal is a fast language model that runs on your own laptop or browser, holds a conversation with durable memory, and later reasons and writes code, all through geometry and exact memory rather than a transformer. M1 is complete: 1 of 8 milestones. M2 is the next capability milestone: complete correct replies grounded in exact memory. The immediate obstacle is new-phrasing reply opening, not the already-passed next-token count-table bars. This page is a plan, not a promise.

M1 is complete. Current work targets new-phrasing reply opening and one useful model end to end.

Terms are in the glossary. Labels are proof, measurement or hypothesis.

A milestone closes only when its full bar is met on a saved model. M1's close does not imply M2 or useful conversation.

What M1 established

The saved discrete model passes six bars at both seeds: a self-contained D11 artifact; exact 14,287-row DEV export/reference agreement and a planted-fault control; tokens per second; DEV integer top-1 above unigram and T2; Fresh V2 transfer; and held-out-phrasing transfer.

  • DEV: 7,002 / 7,001 of 14,287 against unigram 1,226 and T2 6,300.
  • Fresh V2: 7,215 / 7,228 of 14,479 against unigram 1,279 and T2 6,582.
  • p-f: 7,850 / 7,872 of 15,953 against unigram 1,409 and T2 7,375.
  • Apple M1 decode: 10,876 / 10,566 tok/s, measured with a 192-token prefill and 64-token decode.

The limitation is equally important: 62.5% of p-f's reference replies are verbatim TRAIN replies. M1 reads new prompt phrasings into known reply kinds; it does not show new reply kinds or useful conversation. See CHARTER §4.8, the M1 close, Fresh V2, and the bar-f report.

The current order of work

  1. Localize the parity MISS, then complete integer-nearest-readout and rerun point-key-integer. Claude-218 found trunk-state keys that improved openings offline; claude-219 showed a partial free-generation gain on fresh p-v, and claude-220 then served the point key inside one float model on fresh p-w: templates improve by +41/+40/+42 at three seeds with exact claude-219 parity, while recalling TRAIN replies rather than generalizing. Claude-222 has built the integer point table, search and /8 record, with 380 library tests and a full serving audit. Claude-224 has built the panel decode and grade; claude-227 passed retention GPU parity within the 3% bar; Claude-228 built the run's reference/read-back/BOS instruments (390 integer-library tests with one ignored and four negative gates), which held in row 0; Claude-229 found an instrument fault: the integer session uses the native writer instead of the trained whole-table nearest readout, so no bar result or throughput is reported. Claude-231 built the nearest readout and export on native and browser paths; claude-232 then missed greedy parity in every cell, so the mismatch must be localized before the p-x rerun (item).
  2. Serve every required part in integers. Finish the served read, memory and readout rather than treating an export or an audit alone as the whole model.
  3. Train and score one model end to end. Measure complete generated replies on untouched phrasings with tokens per second, then export and serve that same model.
  4. Qualify M2 and M3, then M4. Complete correct replies and durable memory precede the accepted model's full serving contract. After that come laptop cost, reasoning/coding, distribution and the alpha release.

The preceding claude-217 result explains why this order matters. Its cycle step ends every registered loop, but its content decision is underpowered and greedy remains the decode. On p-s, teacher-forced reply openings are 17.4%, 13.7% and 18.6% at three seeds, against about 80% on later tokens. Stopping a loop does not repair a reply that began wrong (report).

What comes after the first useful reply

  • M3: qualify durable memory: provenance, correction, abstention, reset and restart, with token-identical restored sessions.
  • M4: select the accepted model and qualify the full UORLUT01 export, CLI, quality, session and audit path. A lawful likelihood (PRLL) exists, but GPU held-out scoring remains open.
  • M5: measure real laptop cost rather than infer efficiency from arithmetic counts.
  • M6: add reasoning and coding on the same model with executable checks and causal ablation.
  • M7: prove library/CLI/browser parity on the accepted model and ship a truthful local-by-default Studio, with optional user-configured web API.
  • M8: cut one versioned, checksum-pinned release and verify it independently on consumer hardware.

The three products at the end

ProductWhat it will beWhat exists today
The modelOne integer UORLUT01 model for local servingThe M1 pair and a separate FBS export, but no conversational product release
Web clientThe Studio running that file locally in WebAssemblySynthetic parity harness plus public M1 top-8 next-token prediction; no chat or qualified bundle
Desktop clientA Tauri app sharing the interface with durable memory and offline useNative shell and durable session restore verified on a synthetic artifact; no qualified bundle

Nothing ships until a trained model passes the remaining product bars. Serving an exported D11 artifact on the user's device is the product and is allowed. GPU remains the qualification authority; only the owner-authorized D84 CPU program runs development research locally (charter, sections 3.5-3.6).

The biggest unknown

Can the model start a correct reply when the user's phrasing is new, rather than only retrieve or continue a familiar template? M1 answered the narrower next-token count-table question. It did not answer that broader generation question. Claude-220 serves the point key inside one float model on fresh p-w: templates improve by +41/+40/+42 at three seeds with exact claude-219 parity, while recalling TRAIN replies rather than generalizing. The integer table, client-sized search and whole-model score are still unproven; useful conversation has not been established.
