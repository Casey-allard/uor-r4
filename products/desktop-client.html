The desktop client

The desktop client is a pre-alpha native shell you install on your laptop. It shows the same interface as the web client, with a host-managed uor-chat sidecar and native Rust backend. It opens only user-granted project folders, remembers conversation text locally, and needs no external CDN at page load. The older engine path separately verifies durable object-store snapshots; that is not exact sidecar hidden-state resume. The target machine is an M1-class laptop. No qualified trained product bundle exists for it to run. The project is pre-alpha: 1 of 8 milestones is complete, and the src-tauri/ desktop shell is verified on the 469,252-byte mk-synthetic-stack (seed = 5) synthetic stand-in artifact (record). Nothing ships until the remaining model and client bars pass.

Labels used below: proof (derived from definitions or code), measurement (a recorded run with its artifact), hypothesis (untested). See the glossary.

Same interface as the web client; the engine, memory and file access run as native Rust inside the app. The host starts a loopback uor-chat sidecar automatically; external MCP connections require an explicit user action and native confirmation. Custom third-party providers and remote model URLs remain browser-only.

Goals and non-goals

Goals.

  1. Run the released UORLUT01 model natively, under the D11 integer contract, on an M1-class laptop.
  2. Share the web client's interface, so there is one interface to maintain.
  3. Give the model access to the user's chosen project folders, for coding help.
  4. Keep durable conversation memory on disk (the D19 line), so a conversation can be closed and resumed exactly.
  5. Work fully offline after install.

Non-goals. No cloud model, account, telemetry or remote server is required, and no second model format is introduced. A host-managed loopback uor-chat sidecar is part of the local app, not a public server. Training and evaluation stay on GPUs (charter, section 3.5).

Architecture

The app is built with Tauri: a small native shell that shows a web page in the system's own webview and runs a Rust backend beside it. The page calls the backend through named commands. Rust is the project's default language (charter, section 3.11), so the backend can link the project's crates directly.

Data flow

  1. Install. The installer carries the app and, optionally, the model file. If the model is not bundled, the first run downloads it once (update and download).
  2. Load. The model manager reads the file, checks its SHA-256 against the release pin before parsing, and passes the verified bytes to IntegerStackModel::parse. The UORLUT01 reader checks every offset and length and returns an error rather than crashing on a malformed file (format.rs; proof by reading the code).
  3. Chat. The live interface sends an OpenAI-compatible chat request through Tauri IPC to the host-managed uor-chat sidecar. The host relays JSON and SSE bytes, exact usage and UOR timing metadata without exposing the sidecar token to the page. The older native_step_tokens engine command remains available for focused synthetic-engine tests; it is not the main chat transport. Conversation text persists locally, but exact sidecar hidden-state resume is not claimed. Exact arithmetic is a separate host tool, not generated by the model. A strict bounded decimal addition/subtraction uses the shared m6_exact_arithmetic engine before starting the sidecar and returns an OpenAI-compatible JSON fallback with zero model usage; unsupported arithmetic-shaped forms and arithmetic over 160 bytes return explicit errors, while ordinary prompts continue through the unchanged sidecar stream. Exact-tool metrics read 0 model tokens · tool, without a computed model rate, model stop reason or allocation delta. Live model loads carry operation IDs, reject stale responses and clear old capabilities on current identity failures. The whole exact-tool exchange (its user prompt and answer) remains visible in conversation history but is excluded from subsequent OpenAI message context, so neither a long trace nor a tool-only arithmetic prompt can overflow the model. This was added after the LexLean full-pack probe at repository commit 23436bdcd69e5238fcda51ef2529bbd4a5dc1e73 and deployed tree 563a7549e432fc035bc603504bb3a162eb332212 reproduced its correct arithmetic but failed self-description and immediate-fact recall; LexLean itself is not adopted as a second runtime or default model. No-space trailing or adjacent-minus forms fail explicitly, while ratio prose and multiple separated hyphens in dates, telephone numbers and identifiers fall through. Clock-time ranges with a prose tail fall through only when the tail contains no digits or arithmetic/grouping glyphs; 5 pm - 6 pm + 3 and 2026-11-05T17:25 - 1 remain explicit errors. Recognized no-space date pairs fall through, while other compact or one-sided-space decimal subtraction computes exactly (50-12, 50 -12, and 50- 12 return 38; 17-25 is an explicit underflow). Compact numeric ranges with declared unit prose (5-10 minutes, 50-12 minutes, and 5-10 minutes, 3 times) and ISO calendar ranges (2026-11-05 - 2026-11-10, including 2026-11-05 - 2026-11-10, 3 days) fall through, as do ordinary ratio counts such as 3/4 of the 20 students passed and mixed clock/prose forms such as 12:00 - 1, then lunch; continued arithmetic after them errors. One-sided date-like pairs compute when whitespace separates the hyphen from either numeric group (11 -05 returns 6 and 2026 -11 returns 2015), while adjacent 11-05 and 2026-11 remain date prose. Signed numeric tails after ISO dates, including comma-adjacent forms such as 2026-11-05,-1, are explicit arithmetic errors. Declared compact ranges also include 5-10 km, 5-10 cm, 5-10 min, 5-10 students, and 5-10 dollars; spaced numeric dates are arithmetic (2026 - 11 computes 2015), and 2026 - 11 - 05 is an explicit multiple-operator error. Telephone-like prompts fall through only in the explicit 3-3-4 shape: an optional leading +, an optional country code 1, then a parenthesized or bare 3-digit area code, a 3-digit exchange and a 4-digit subscriber, with spaces or single hyphens between groups (1 (800) 555-0100, (800) 555-0100, 1-800-555-0100, +1-800-555-0100, +1 800 555 0100). Dotted 3-3-4 forms such as +1.800.555.0100 fall through as ordinary prose, while a dotted parenthesized form such as (800).555.0100 remains an explicit unsupported/grouping error. Unprefixed numeric ranges may end with ?, !, , or . and fall through as prose (10 - 20?, 10 - 20,, 10 - 20.), while prefixed underflow questions such as What is 10 - 20? remain explicit underflow errors. Source selections made while a reply is active preserve the healthy session: model-load and API-use/removal clicks are blocked during generation, while a load started before the reply and a programmatic source selection are retained as the latest pending selection and applied on the existing generation-finished event; programmatic removal of an active API fails closed rather than leaving the deleted endpoint active.
  4. Remember (older engine path). When that path saves a turn, native_save_session_durable snapshots its session state as UR4SESS1 (9,782 B after 32 steps on the synthetic stand-in), wraps the conversation history and snapshot in a UORMEM01 envelope (encode_memory_envelope + fold_memory_envelope), and stores the content-addressed records (446 records on the 32-token self-test, object_version = bc98ac3d0a8f363ea6e7bcb10dea9acf59bd1a43859d9e6dd4417f0e1d5364ca) in uor-r4-object-store::Store (record).
  5. Resume (older engine path). On reopening, native_restore_session_durable reconstructs and verifies the UORMEM01 envelope from the local store (verify_memory_envelope), loads the embedded UR4SESS1 snapshot back into LutStackSession::from_session_bytes, and continues generation token-for-token (16 + 16 == 32 verified in durable_memory_object_store_close_and_resume_continues_token_for_token). That is the M3 restore contract on the synthetic stand-in; M3 itself remains open until a trained model passes the full M3 acceptance panel (project track, M3).
  6. Work on files. When the user launches the host with --grant <dir> (or selects a folder through a host-owned dialog), native_grant_folder canonicalizes and registers it in GrantedFolders (native_grant_folder is host-owned and refused over page RPC); native_read_file, native_write_file, native_list_directory and native_git_status refuse any path outside granted roots. The loopback host also accepts --studio-root <dir> to serve a reviewed web/studio/dist instead of the default web/studio; its existing token, Host, Origin, canonical-path and all-root TypeScript/TSX/source-map refusals remain in force; an explicit --studio-root must name an existing canonical directory rather than silently falling back to source. For bounded browser automation, an operator can explicitly launch with --enable-terminal and --approve-command <cwd> <command>. Those CLI arguments call the same host-owned enable/approve methods as the native dialogs and preserve the 60-second, exact cwd/command, one-shot grant. Browser RPC only reports whether enablement/approval already exists; it cannot create, extend or consume approval except by running the approved command once. No browser dialog is simulated, and no page RPC can enable or approve itself.

Interactive PTY terminal

The Terminal view uses a persistent host-approved PTY with xterm, direct keyboard input, raw-byte streaming, resize, and close/reaping. It does not show the old Run command button or request approval per keystroke. Every open presents the native Enable terminal confirmation followed by one approval of the exact working directory/shell; the second-open native acceptance observed both dialogs again. This is one shell-specific approval per open, not one total host dialog. The default shell is /bin/zsh. At most eight sessions, 64 KiB per input, and 1 MiB retained output per session are enforced. Stale sessions, out-of-grant paths, and post-close input are refused. Static browser previews explicitly report the native service as unavailable.

The loopback acceptance uses isolated HOME and workspace fixtures, real /bin/zsh input, printf, read plus an answer, pwd, stty size, exit, and closed-input refusal. Its raw events use the same camel-case JSON contract as the TypeScript adapter. This is unsigned development-terminal evidence, not a hosted terminal service, arbitrary shell grant, detached-process-containment guarantee, or full agent runtime.

Why native, and how fast

The browser runs the engine as WebAssembly in one worker. A native build can use the processor's vector units (NEON on Apple silicon) and several threads. The project already has native table kernels for NEON and AVX2, though they belong to an older, frozen engine (crates/uor-r4-simd). That native will be faster is a hypothesis. Nobody has timed WebAssembly against native on the same file. As of 29 Oct 2026 the FBS trunk serves in integers on the M1 laptop at 4,829 tok/s snapped (claude-177) and 4,217–4,504 under lut-stack/5, with exact rotations and its DEV export gap inside the bar, (claude-182, claude-186), natively and without a vector (NEON) kernel; no browser figure exists. Older speeds on record are from older float models served exactly by the integer engine: 68 to 80 tokens per second on 8 threads for a 29M model, which is evaluation throughput over 64 scored windows rather than decode (D11 serving record), and 184.58 tokens per second on one thread for input-driven forward passes, which is not free-running generation either (lut-serving dossier). M5 is the milestone that measures laptop cost: ms per token, peak memory, mJ per token and weights read per token (project track, M5).

Serving on the user's laptop is allowed. The charter says serving the exported D11 file on client devices, including Apple silicon, is the product, and the research-compute placement rule does not apply (charter, section 3.6). D84's CPU training path is separate research and does not make the desktop client a qualification engine.

Durable memory (D19)

D19 makes grounded conversation and durable memory the first priority (D19). The object store was split out as its own crate for this purpose on 14 October (D34). What it has shown, all on test data (measurement):

  • 60 tests pass, and a pure-Python client pulled a 256 KiB object byte-identically from the Rust server (conformance record).
  • A 23-byte read of a 32,768-byte object touched 8 authenticated nodes, 384 bytes (object-store dossier).
  • Repeated content compresses well (7,776 bytes stored in 380), but unique content expands about 2.17 times (32,768 bytes become 70,972) (D19 store record).
  • src-tauri folds and restores UORMEM01 + UR4SESS1 session state through uor-r4-object-store::Store (446 records for a 32-token synthetic session, 9,782 B UR4SESS1 snapshot), and resumes generation token-for-token across process close/reopen (desktop client record).

Never tested: any trained model reading from the store, the M3 memory bars on a trained model, and storage cost on real chat logs (object-store dossier). The store keeps exact identity (what was said, where, in which version) separate from any geometric address, as the charter requires (section 3.12).

Update and model download

  • Model files are versioned releases. Each is one UORLUT01 file with a published SHA-256 (releases). The app never runs an unpinned file.
  • First download. Fetch the file once, verify the hash, store it locally. After that the app needs no network.
  • App updates. Use Tauri's signed updater, or manual install. Signing keys and the hosting choice are open questions.
  • Delta updates for models (hypothesis). The object store can send only the pieces that changed. In one test a receiver holding a slightly older 1 MiB object fetched 22 records, 1,014 bytes, in 3 rounds. But a cold pull of unique content through the store is far larger than a compressed download (5,725,408 bytes against 39,920 for a 2 MiB artifact), so the supported recipe is a compressed download first, then deltas (object-store dossier). Whether deltas help for real model files is untested.

Open questions

  1. Superseding the old plan. archive/integration/frontend-port-plan.md (historical, 4 September) says Tauri should not be the main client. The owner's 19 October decision replaces it, and that file needs a supersession note.
  2. Sharing one interface. The Studio is one 7,107-line HTML file with inline scripts. Does it need to be split into modules before two shells can share it cleanly?
  3. The terminal command. Keep it (with consent and folder limits) or drop it from the first release?
  4. Where memory meets the model. Which comes first: storing session snapshots in the object store, or exact quotations from the store feeding the model's output? This is the object store's open path to ACTIVE status (object-store dossier).
  5. Threads and D11. The five D11 rules say nothing about threads. Whatever kernels the app ships, threaded or vectorized, must still pass their engine's serving audit. Every audit refuses float. The FBS stack's audit also refuses vector and matrix multiplies, and since D80 and D81 allows the scalar integer multiply and divide. The other engines' audits keep the zero-multiply rule.
  6. Engine format. The legacy Studio also calls native_list_local_models, written for an older model format. The model manager must accept only UORLUT01.
