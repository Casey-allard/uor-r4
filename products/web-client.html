UOR-R4

The web client

The web client is meant to be a language model that lives in a browser tab. You open a web page once, it downloads the model file, and from then on the model can run on your own computer, inside the browser, in a sandboxed form of machine code called WebAssembly. In local WASM mode your prompts and the model's replies stay on the device. An optional user-configured OpenAI-compatible API instead sends prompts to the endpoint the user chooses. The page you would use is the Studio, an editor-and-chat interface already in the repository. The live /studio/ page now offers the publicly released M1 model as a top-8 next-token predictor after an explicit download click, alongside a clearly labelled synthetic demo and local-file, URL and API model sources. M1 is complete, but the M1 model is a language base, not a chat assistant; until M7 and M8 pass the web client is a research explorer and demonstration, not a product.

How it is meant to work

  1. Load the static Studio. The charter places it at /studio on the documentation site.
  2. Download one UORLUT01 file and verify its SHA-256. A release pin identifies the model. A download-once browser-storage cache is planned, not claimed as delivered.
  3. Start the integer engine in a Web Worker. The worker loads pkg/uor_r4_integer.js and calls init and loadStack on the model bytes.
  4. Generate. Each token calls step. The D11 engine uses integer arithmetic; integer multiply and divide are allowed, while floats, transcendentals and dense matmul stay banned. Accepted-model cross-browser parity is an M7 measurement, not an assumption.
  5. Save and resume. saveSession emits a UR4SESS1 snapshot and restoreSession loads it.

The real exports are init, tickClock, loadStack, step, saveSession, restoreSession, weightsPerToken, allocEvents and leakedModels (wasm_bindgen_exports.rs). Serving an exported D11 artifact on a client device is allowed; the GPU-first research-compute rule does not apply to product serving (charter, section 3.6). D84's CPU training program is development research and does not qualify the browser runtime.

The SIMD kernels in the WebAssembly build are fixtures, not the hot path; the engine currently uses its scalar table kernel. These implementation limits do not negate the M1 model's native results, but they are not a browser qualification of that model.

What is still missing

  • A qualified model bundle for the web product. M1's native artifacts do not by themselves prove browser parity or M7 distribution.
  • The accepted M4 model and its browser export. Full quality, session and audit bars come before M7's accepted-model parity check.
  • A download-once cache and release loader.
  • Bit-identical tokens and sessions on the real model across library, CLI and browser. The synthetic harness passing is an instrument result, not M7 completion.
  • Automatic build/publish remains owner-only. DeepSeek's manual production publish is already live; this documentation refresh performs no deployment.

Privacy and integrity

  • Local WASM mode computes locally. No prompt or reply needs a model server. An optional user-configured OpenAI-compatible API instead sends prompts to the endpoint the user chooses.
  • Page-load resources are self-hosted. The static and headless-Chrome checks report zero external requests on both Studio pages. Loading the public M1 model from Hugging Face is a separate, explicit click that downloads the artifact without sending prompts. User-initiated GitHub features are also explicit actions and are refused in Tauri/offline mode.
  • A checksum proves integrity, not secrecy or quality. The model is public; a hash identifies the released bytes, not who made them or whether they answer well.

Until M7 and M8 pass, the page remains a research next-token explorer and synthetic-engine demonstration, not a working assistant. M1's language-base result and browser prediction are real, but they do not change that product boundary.

Open questions

  • How large will the accepted model file be, and is a one-time download acceptable on a phone?
  • How fast is WebAssembly against native on the same file? The M1 pair's native 10,876/10,566 tok/s does not answer that. Older FBS native rates and older evaluation throughput are not browser rates.
  • Which remaining served-memory/readout parts are needed for the accepted model's full browser path?
