UOR-R4

The web client

The web client is meant to be a language model that lives in a browser tab. You open a web page once, it downloads the model file, and from then on the model runs on your own computer, inside the browser, in a sandboxed form of machine code called WebAssembly. Your prompts and the model's replies never leave the device, because there is no model server to send them to. The page you would use is the Studio, an editor-and-chat interface already in the repository. Today the pieces exist separately and are not joined: the browser engine works on a synthetic test model, the Studio still points at an older engine that was retired, the public site is frozen, and there is no trained model to download. Until milestones M7 and M8 pass, the web client is a geometry explorer and demonstration, not a product.

Labels used below: proof (derived from definitions or code), measurement (a recorded run with its artifact), hypothesis (untested). See docs/formal_vocabulary.md and the glossary.

One download, then everything runs in the tab. The only network traffic is fetching the static page and the model file.

How it is meant to work

  1. Load the page. The Studio is static HTML, JavaScript and CSS. The charter places it at /studio on the project's documentation site (charter, section 2).
  2. Download the model once. The page fetches one UORLUT01 file and checks its SHA-256 against the hash published with the release (releases). It then keeps the file in browser storage so later visits work offline. This cache is planned, not built (from reading the repository).
  3. Start the engine in a Web Worker. A worker is a background thread of the page, so typing stays smooth while the model computes. The worker loads the WebAssembly build of crates/uor-r4-integer and calls init, then loadStack on the model bytes.
  4. Generate. For each token the worker calls step. The engine uses only integer adds, shifts and table look-ups (the D11 contract), so the same file gives the same tokens in every browser. That is a design property; M7 has to measure it.
  5. Save and resume. saveSession writes the conversation state as a UR4SESS1 snapshot, and restoreSession brings it back byte for byte.

These function names are the real exports of the WebAssembly build: init, tickClock, loadStack, step, saveSession, restoreSession, weightsPerToken, allocEvents, leakedModels (record; proof by reading wasm_bindgen_exports.rs).

Why serving in the browser is allowed. Research compute must run on a GPU (D24). On 15 October that rule paused the browser engine, because serving in a browser runs on the user's processor (D36). The owner resolved this on 19 October: serving the exported D11 file on client devices, including browser WebAssembly, is the product, and D24 does not apply to it (charter, section 3.6).

The M7 bar sums it up: the qualified model "produces bit-identical token completions and session snapshots across the Rust library, the uor-chat CLI and the browser serving-wasm worker", and the Studio "runs entirely client-side in a Web Worker with truthful capability reporting and zero remote model calls" (project track, M7). The .wasm audit criterion is green and will be re-run on the shipped bundle; the rest of M7 (rewiring the Studio, three-host parity, client-side Studio) is open.

Until then: an explorer, honestly labelled

Until M7 and M8 pass, the web page should present itself as what it is: a geometry explorer and a demonstration of the serving engine on a synthetic model. It must not offer a chat box that implies a working assistant. The Studio's engine-status banner already says so. Showing the engine's real exports (weightsPerToken, allocEvents) on a synthetic model is fair. Showing chat replies is not, until there is a trained model behind them.

Privacy model

  • The model computes only on the device. No prompt or reply is sent anywhere by the engine. That is the M7 bar, and today it holds trivially, because there is no remote model to call.
  • Network use is not yet limited to static files. The target is the page and the model file only. Today the Studio also loads third-party code and fonts from CDNs (Monaco, pdf.js and three.js from cdnjs; marked, KaTeX and the three.js controls from jsDelivr; fonts from Google Fonts), and its search feature sends the typed query to en.wikipedia.org and api.duckduckgo.com. Features that open files from GitHub talk to GitHub. None of that is model compute, but a privacy claim must not hide it: the requirement is to self-host every asset and make web search opt-in, or remove it, before M7 (index.html, lines 11 to 25 and 5845 to 5906).
  • Integrity, not secrecy, of the model file. The SHA-256 check proves the file is the released one. The model is public, so there is nothing to hide in it.

Open questions

  • How large will the model file be, and is a one-time download of that size acceptable on a phone? Unknown until a model exists.
  • How fast is WebAssembly against native on the same file? No tokens-per-second figure for the browser has been recorded. The only native figures are from older float models: 68 to 80 tokens per second on 8 threads for a 29M model, which is evaluation throughput over 64 scored windows, not free-running decode (D11 serving record). No decode tokens per second exists for any D11 artifact.
  • Should the Studio's provenance be settled first? Its source is an import from a companion repository, Casey-allard/uor-r4-wasm-chat, which this audit did not inspect.
