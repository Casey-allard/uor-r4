UOR-R4

The three products

UOR-R4 aims to ship one thing people can use: a small, fast language model that runs on your own laptop or in your browser, with local computation by default and no model server required. For the web Studio only, an optional user-configured OpenAI-compatible API sends prompts to the endpoint the user chooses; the desktop shell has no OpenAI-compatible API mode. The three products are the model in one integer file, a web client that runs it in a browser tab, and a desktop client that runs it natively with durable memory. None ships today. M1 is complete (1 of 8), but no useful conversation, integrated qualified product or alpha release exists.

Labels: proof, measurement, hypothesis (docs/formal_vocabulary.md, glossary).

One model file is intended to feed two clients sharing one interface and local storage.

Releases and artifacts covers the file format, future M8 release, Hugging Face repositories and checksum binding.

Why the products look like this

Local by design. The mission is fast local AI, and the lead metric is tokens per second. A product that needs a data centre would defeat the point.

One file, many hosts. D11 bans float and transcendental arithmetic and excludes dense matmul. D80 and D81 allow integer multiply and divide. That lets one integer artifact run natively, in a browser or on Apple silicon. Serving the exported artifact on the user's device is the product and is allowed (charter, section 3.6).

One interface, two shells. The browser runs the engine as WebAssembly; the desktop app wraps the same Studio and runs native Rust. Native being faster is a hypothesis until a same-file comparison exists.

Since M1 closed

The open research problem is complete replies on new phrasing. Claude-217's cycle step ends every registered loop but leaves content underpowered, so greedy remains the decode. On p-s, teacher-forced reply openings are 17.4%, 13.7% and 18.6% at three seeds, against about 80% on later tokens. Exact turn memory keys on exact first token ids and misses reworded prompts. Claude-220 now serves the point key inside one float model on fresh p-w: templates improve by +41/+40/+42 at three seeds with exact claude-219 parity, while recalling TRAIN replies rather than generalizing. Claude-222 has built the integer point table, search and /8 record, but only synthetically. Claude-224 has built the panel decode and grade. Claude-227 passed retention GPU parity within the 3% bar; Claude-228 built the run's reference/read-back/BOS checks; Claude-229 found an instrument fault: the integer session uses the native writer instead of the trained whole-table nearest readout, so no bar result or throughput is reported. Claude-231 built the nearest readout and export on native and browser paths; claude-232 then missed greedy parity in every cell, so the mismatch must be localized before the p-x rerun; M2–M4 remain open.

The order things must happen in

  1. M2 and M3 produce complete grounded replies and durable memory on the selected model.
  2. M4 exports and qualifies that model through D11 and the command line.
  3. M5 measures laptop cost, M6 adds reasoning and coding on the same model.
  4. M7 proves library/CLI/browser parity and truthful local-by-default Studio behavior, with optional user-configured web API.
  5. M8 releases one versioned, checksum-pinned model that meets every earlier bar.

The desktop client rides on M3 for memory, M4 for the accepted integer artifact, M5 for laptop cost and M7 for the shared interface. Full definitions are in the project track.
