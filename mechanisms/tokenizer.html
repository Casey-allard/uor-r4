Tokenizer

Status: ACTIVE. Every current corpus, driver, test panel and trained artifact is bound to one pinned tokenizer with 4,096 pieces (identity d36d3e87). A Rust trainer for a 16,384-piece tokenizer landed on 19 October as tooling only, and a three-arm number-aware pre-tokenization comparison (Digits(individual_digits=false) + ByteLevel) landed on 22 October as host tooling and a draft comparison sheet. No model has been trained or scored on any other tokenizer (trainer record, donor-corpus sheet, number-aware record, number-aware sheet).

Labels used below: proof means derived from definitions or code, measurement means a recorded run, hypothesis means an untested idea (see the charter, section 4.6). Unfamiliar project terms (K16, A8, admission, NOT_RUN) are in the glossary.

In plain words

The model never sees letters. It sees numbered pieces of text, and this component cuts text into those pieces and turns pieces back into text. It starts from raw bytes, so any text can be encoded. Then it learns which neighbouring pairs of pieces occur most often and glues them into bigger pieces, so common words become one piece and rare words stay in several. The project's pinned tokenizer has 4,096 pieces. This is a standard technique, not a novel one. What is distinctive here is that the tokenizer's fingerprint is recorded in every file that depends on it.

What it replaces in a transformer

It fills the same slot as a transformer's tokenizer; it replaces no transformer part with a different mechanism. A transformer has a tokenizer too, usually byte-level BPE. This page is on the board because the tokenizer fixes the vocabulary size and id space that the prime-zeta codebook and the address-structured cells are sized by. It also pins the identity that makes results comparable.

Bytes become pieces by repeated merging, and the fingerprint of the merge table travels with every prepared file. A two-digit number is still two pieces.

How it works

Vocabulary layout (Definition). Ids 0, 1 and 2 are start, end and unknown. Ids 3 to 258 are the 256 single bytes. The rest are learned merges. For the pinned tokenizer that is \(3+256+3837=4096\).

Training (Definition). Count adjacent pairs over the unique pieces of text in the corpus (pre-tokens), each weighted by how often it occurs. Then repeat: merge the pair with the highest weighted count into a new piece, and recount only the words that contain it. Ties go to the pair with the smaller left, then right, token string, so the result is deterministic. Special tokens are atomic. No merge crosses a special token, a pre-token boundary or an input file.

Encoding (Definition). Apply the merges to a text's bytes in rank order. This is a table lookup with no learned arithmetic.

Identity (Definition). The tokenizer is stored as a tokenizer.json. Its raw-byte BLAKE3 hash is the runtime content address returned by ByteBpeTokenizer::address. The discrete controller separately uses a SHA-256 file pin (config.tokenizer.sha256, verified by FilePin::read). Prepared corpora and artifacts bind the tokenizer using their declared hash domain. A different tokenizer is therefore a different corpus.

Prepared corpora. The UORT v1 format is a 64-byte header followed by 16-bit token ids, with start markers and an optional binary response mask. Before reading a target, the discrete driver verifies the file hash, the token count and the tokenizer identity.

One dialogue encoding. A DialogueProtocol object fixes how roles and turns are written out, so training, test panels and chat use identical token segments. The need is real. Two branches once used incompatible serialisations, and even identical visible text can encode differently, because the merge rules may join a marker's trailing space to the first content token.

Numbers. In the pinned vocabulary (Digits(individual_digits=true) + ByteLevel) no piece made only of digits has more than one digit: it has 10 pure single-digit pieces and 0 pure multi-digit pieces (measurement, below; audited via ByteBpeTokenizer::digit_piece_census). Under plain ByteLevel(add_prefix_space=false) (digits_individual = None), leading spaces attach to digit runs (" d1d2" \(\mapsto\) "Ġd1d2"), so ("Ġ", d1) sums across all trailing digits \(d_2\) and merges before \((d_1, d_2)\), forming \(\ge 109\) space-prefixed digit pieces while leaving unprefixed "48" split into 2 tokens (pure_multi_digit = 5). Under Digits(individual_digits=false) + ByteLevel(add_prefix_space=false) (number_aware_digits_policy(false)), split_digits(segment, false) splits at digit/non-digit boundaries while keeping contiguous digits together, yielding pure_single_digit = 10, pure_multi_digit = 109 (100 two-digit, 6 three-digit, 3 four-plus-digit), space_prefixed_digit = 0, and distinct single-token IDs for "84" and "48" at both \(V = 4{,}096\) (blake3:c38dabf5…) and \(V = 16{,}384\) (blake3:411c366d…). A separate numeral codec reads consecutive digit pieces left to right into one ordered value, so pieces 8, 4 give 84 and pieces 4, 8 give 48.

Rule check. Everything here is integer bookkeeping on the host and is not model compute. It involves no softmax or squashing (D23), no matrix multiplication (D30) and no float. The encode path was not itself put through the D11 instruction audit. It sits outside the served numerical kernels, and the integer runtime takes the tokenizer as an optional dependency for text sessions.

What has never been tested

  • Whether 16,384 pieces help or hurt the discrete model. No model has used any tokenizer other than the pinned one.
  • Whether a number-aware tokenizer (Digits(individual_digits=false) + ByteLevel, built and pinned at \(V=4{,}096\) and \(V=16{,}384\) in #2872) improves downstream discrete model training or numeric copy/successor accuracy.
  • Whether the tokenizer interacts with prime-zeta placement or cell coverage. The prime-zeta qualification used \(V=4096\) only.
  • Fairness across scripts and languages. The training corpora are English chat and code.
  • Reclaiming the three superscript-digit slots (idle vocabulary) for multi-digit pieces.

What comes next

The mechanism is ACTIVE, so this is a plan, not a reopening. The next step is executing the matched 4,096-against-16,384 and number-aware comparison (number-aware-tokenizer-DRAFT-2026-10-22.md) once a corpus rebuild and GPU model comparison are cleared. Open questions it should answer: does 16,384 improve the prime-zeta and address-cell numbers or just spread cells thinner (the planned shape uses 512 cells instead of 256), do multi-digit pieces (Digits(individual_digits=false)) outperform single-digit pieces on numeric spans at matched BPB, and would training the tokenizer on the donor corpus make it a different corpus identity.

Code

  • uor-r4-tokenizer/src/lib.rs: runtime byte-level BPE, tokenizer.json parser, raw-byte identity, and DigitPieceCensus (ByteBpeTokenizer::digit_piece_census).
  • training.rs: the deterministic merge trainer (weighted pair counts, pair-to-word index, lazy heap) and pre-tokenizer policy constructors (number_aware_digits_policy, individual_digits_policy, plain_byte_level_policy, number_aware_comparison_corpus). bin/train-bpe.rs: the host-only command, for vocabularies from 259 to 65,536.
  • dialogue.rs: the shared dialogue encoding. tests/training.rs: checks against an independent recount.
  • uor-r4-discrete/src/corpus.rs: the prepared-corpus loader that verifies hash, count and identity.
  • native_geometric/numeral.rs: the numeral codec (older engine, outside the selected build).
  • Corpus preparation: prepare-knowledge-corpus, prepare-chat-parquet and mix-chat-corpus in crates/uor-r4-training/src/bin/.

Related mechanisms

prime-zeta-codebook: maps each id to a prime and phase position; the tokenizer fixes \(V\). address-cells: the cell placement is sized by the vocabulary. discrete-learning: the driver verifies tokenizer identity on every corpus. native-geometric: the numeral codec and an older lexical codec sit on token ids. lut-serving: the served engine carries the tokenizer for text sessions.
