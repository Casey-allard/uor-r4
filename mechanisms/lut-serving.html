D11 integer table serving (UORLUT01)

Status: ACTIVE, by D72's own condition (recorded on 29 Oct 2026 by claude-183). D72 (owner ruling, 24 Oct 2026) set it READY "until a lawful trained model is exported through it". The condition has been met on three artifact lines:

  • The discrete Stage T path, 26 Oct (antigravity-96, #2839). Four Stage T checkpoints were exported through uor-r4.lut-discrete/1 with an export gap of exactly 0 on the 14,287-row DEV panel.
  • The closing M1 pair (antigravity-110, #3312). The 19-table uor-r4.lut-discrete-trunk/1 artifacts match their reference on all 14,287 DEV rows at both seeds and pass B4.
  • A separate D37 float-trained SpiralCore/FBS trunk, 29 Oct (claude-182, uor-r4.lut-stack/5). It was inside the export-gap bar on both seeds, at DEV scope.

See "What has been tried". It is the end-of-pipeline contract: the finished model must ship as one integer artifact, and this engine runs it. The engine reproduces its reference answers exactly, and its serving audits are green (since claude-175 they count the hardware multiplies and divides, which the stack uses since claude-177). A table-native schema (uor-r4.lut-discrete/1) exports DiscreteModel snapshots into UORLUT01 (discrete.table, discrete.cells, discrete.routes, discrete.gates) and evaluates Route, Flock, and Relation prefixes in uor-r4-integer with exact integer parity against the CUDA-qualified witnesses (#2838). The float trunk's export is scored at DEV scope only; its fresh split has not been read.

Labels used below: proof means derived from definitions or code, measurement means a recorded run, hypothesis means an untested idea. See docs/formal_vocabulary.md.

In plain words

This is how a finished model runs on an ordinary laptop or in a web browser using only whole numbers: adds, shifts and table look-ups. There is no decimal arithmetic. Since D80 and D81 (28 Oct 2026) the chip's own whole-number multiply and divide are allowed too, and since claude-177 the stack's kernels use them. A dense/FBS model is exported to a compact file, mostly 4-bit numbers; M1's table-native lut-discrete-trunk/1 instead stores named integer lookup tables and has zero 4-bit matrix sections. A checker then reads the compiled program and counts machine instructions to prove that no decimal arithmetic sneaks in, and it counts the multiplies and divides it now allows. The discrete M1 pair and the separate FBS trunk have been exported and served; the M1 pair has exact 14,287-row DEV export/reference agreement and native Apple M1 decode at 10,876 / 10,566 tok/s. Neither result is useful-chat qualification. On p-f, 62.5% of reference replies are verbatim TRAIN replies: reference-data overlap, not a generated-copy rate or new reply kinds.

What it replaces in a transformer

The arithmetic. A transformer runs on large matrix multiplications. Here the same weights are read through tables, so every product is a table read and an add. This changes how a model is computed, not what it is. The engine does not make a weak model better, and, as the history below shows, it still reads every stored weight for every token.

How it works

Export. Training is offline and may use float. For serving the weights go into a UORLUT01 container. In dense/FBS schemas, weights are 4-bit codes in groups of 32, each with a one-byte scale (a 4-bit mantissa and a 4-bit exponent). Small integer tables cover permitted nonlinear steps such as square root, decay rates and arcosh; SiLU and exp tables belong to older banned schemas. M1's table-native lut-discrete-trunk/1 instead stores named integer tables and has zero 4-bit matrix sections.

One projection (definition). For a weight matrix \(W\) and an integer activation vector \(x\), the output is \(y_i=\sum_j w_{ij}x_j\), where each weight is a group scale times a 4-bit code, \(w_{ij}=s_g\,q_{ij}\) with \(s_g=m\,2^{e}\). The engine does not multiply \(q_{ij}\) by \(x_j\). For each activation it builds a 16-entry table \(T_j[q]=q\,x_j\), which needs only additions to fill, and then reads \(T_j[q_{ij}]\) for each weight. Four output rows are blocked to reuse the table. The scale \(s_g\) is applied by shifts and adds.

Products of two runtime values. A score, a gate or a value mix needs a true product of two numbers known only at run time. Since claude-177 (D80) it is one hardware multiply. Before, the engine built a table of the sixteen multiples of one operand by repeated addition, read it at each base-16 digit of the other operand, and summed the reads with shifts: \(ab=\sum_k 16^k\,T_a[d_k(b)]\), exact by the definition of base-16 digits (proof; kept as the tests' reference for stack_mul_u64 and stack_mul_u128 in kernels.rs). The quarter-square identity would also be allowed, but the serving engine does not use it. Normalisation uses an integer square root or a table. Sampling is integer min-p.

Session state. A conversation's state is saved and restored byte-for-byte (the UR4SESS1 format).

The five rules (D11). R1: no floating point and no maths library. R2: no multiply or divide instruction, amended by D80 and D81 (28 Oct 2026): the hardware integer multiply and divide are now allowed, and R1 still bans float. R3: dense per-token access to a learned store is interim, not the end state (D5). R4: no transformer backbone. R5: energy is claimed only when measured.

The audit. The release binary is disassembled, and the multiply, divide and float instructions are counted over the serving symbols, natively and in WebAssembly. Since claude-175 (D80, D81), the FBS stack's audits allow the scalar integer multiply and divide and report how many they see. They still refuse every float instruction (fmov included) and every vector, dot-product or matrix multiply. The audit proves absence of the refused instructions. It says nothing about model quality, and the SIMD kernels in the WebAssembly build are unintegrated fixtures that the 7-of-7 audit never exercises (record). Legacy audits retain their historical contracts; current D11 allows and counts integer multiply/divide under D80/D81 rather than imposing a project-wide zero-multiply rule.

Geometry, as exact finite tables. The 120-element icosian group's Cayley table (about 14 KiB), a 1,025-entry arcosh table for Lorentz read scores, icosian-pair weights and the Q30 Hopf observation are stored as tables. The current integer crate selects typed H4 geometry and checked integer arithmetic (native_geometry.rs). discrete_d11.rs loads both the earlier four-table uor-r4.lut-discrete/1 and the M1 19-table uor-r4.lut-discrete-trunk/1 (UORLUT01) containers exported by d11_export.rs. The four base tables are discrete.table, discrete.cells, discrete.routes and discrete.gates; the M1 trunk adds 15 joint-pointer tables. These table-native schemas have zero 4-bit matrix sections.

What has been tried

"Gap" means served minus float score. "Bits per byte" (BPB) is the model's loss on a held-out chat stream, lower is better; the milestone bar is at most 0.90. The D10 engine is the older engine that allowed multiplies. A "D11 minus D10" loss of 0.0 therefore means the multiplier-free engine reproduces the older one exactly.

Reading these honestly. The engine is exact at its declared contracts, and the M1 pair passes its language-base bars at 10,876 / 10,566 native decode tok/s. Those results do not make every served model strong or every path cheap. Older float models missed quality bars, dense table-based products cost more energy and time than float, and M5 has not measured the accepted model's full-path energy or traffic. A dense model streamed through tables is still dense, which is why the sparsity rule asks for selected, addressed reads instead.

What has never been tested

  • The float trunk's export on the fresh split. Its export gap is measured at DEV scope only (claude-182), and on one passing configuration. The earlier Stage T discrete exports were measured on 26 Oct (antigravity-96), before the current M1 pair's exact close.
  • Hardware-counter measurement of memory traffic per token (D5-a) and of parameters touched per token (D5-b). Milestone M5 has not run.
  • Whole-system energy per token with a validated sampler. The only earlier figures (5.7 and 21.0 millijoules per token) came from a truncated capture.
  • A valid scored use of the integer point-key path. Claude-229 ran the real TRAIN export and p-x decode/grade, but row 0 was an instrument fault: the native writer was not the trained whole-table nearest readout, so every grade pair was (0, 0) and no throughput was reported. Claude-231 built that readout on native and browser paths; claude-232 then missed greedy parity in every cell, so the p-x rerun waits on localizing the mismatch. The older product-key addressed-memory kernel remains unbuilt.
  • A comparison with the SIMD kernels on the serving hot path.
  • Free-running generation speed and fresh-split performance on the accepted model. The 184.58 tokens/s figure was input-driven forward throughput, not a substitute for the M1 pair's native decode measurements or for M7 browser parity.

What stays frozen, and what would restore it

This mechanism is ACTIVE (D72's condition is met), so nothing here needs reopening. Two sub-parts are held:

  1. The D10 engine and its SIMD crate stay frozen, non-mission comparators. D80 and D81 allow hardware integer multiply and divide in the current D11 serving path, but they do not restore the old D10 engine or its dense schemas.
  2. Serving of the older product-key or addressed memory still needs an integer read kernel; that exporter refuses it. The separate integer point-key table/search and /8 record exist only as synthetic/host instruments. The real export and p-x run happened, but row 0 was an instrument fault, not a usable score. Claude-231 built the nearest readout on native and browser paths; claude-232 missed greedy parity in every cell, so the p-x rerun waits on localizing the mismatch.

Open questions. The discrete M1 and FBS /5 export gaps are measured at their declared scopes; the open work is the accepted model's full serving path, addressed memory and cost. How many of the 30.2 million parameters touched per token can selected reads remove before tokens per second move, given that arithmetic count was not time? Are the audit scripts, which are Python, to be ported to Rust and run in CI?

  • kernels.rs: table kernels, blocked product tables, radix-16 multiples-table products (stack_mul_u64, stack_mul_u128). session.rs: the per-token step and exact session state.
  • format.rs: the container and its schemas. flock.rs: integer flock rank selection.
  • simd.rs: WebAssembly SIMD fixtures, not on the hot path. wasm_serve.rs: browser and Node entry points. session_codec.rs: the exact session snapshot.
  • native_geometry.rs and discrete_d11.rs: integer geometry and uor-r4.lut-discrete/1 loader/evaluator for the discrete model's export, paired with d11_export.rs and crates/uor-r4-lut/src/format.rs. uor-r4-stack.rs: the command-line program the audit checks.
  • audit_zero_matmul_serving.py and audit_zero_matmul_wasm.py: the native and WebAssembly instruction audits (existing Python scripts).
  • uor-r4-lut: container metadata only, with the dense engines excluded. preserved D10 engine and uor-r4-simd: frozen. stack_export.rs: the old exporter, compiled out.
  • Evidence: served stacks, protocol pin, port design.

Related mechanisms

geometric-stack: the older float model this engine exported and served; its quality is the limit. flock-read: the softmax-free read used in current paths. exact-memory: addressed memory whose full integer read path remains open. spin-weights: icosian-pair weights that make table serving of quaternion maps exact. ternary-xor: the integer arithmetic substrate. r4g1-graph: the earlier frozen table runtime. discrete-learning: the live model whose integer export now carries the M1 result.
