UOR-R4

Serving and export

A finished model has to leave the lab and run on an ordinary laptop or in a web browser. The project's rule is that the file it ships contains only whole numbers, and that the program running it uses only adds, shifts and table look-ups: no decimal (floating-point) arithmetic and no multiply instruction. The program that does this exists, and a checker has counted its machine instructions. But it has only ever run older models that fell short of their targets, plus a synthetic stand-in. No model built under today's rules has been exported to it yet, so nobody can chat with the project's model on a laptop today.

Labels used below: proof means derived from definitions or code, measurement means a recorded run, hypothesis means an untested idea. See docs/formal_vocabulary.md and the glossary.

Training may use decimals; serving may not. The snap from one to the other is where quality can be lost, and that loss is the export gap.

Two halves with one hard border

Offline half. Training runs on rented GPUs and may use floating point. The owner's rule (D37, 18 October) allows float forward passes, gradients and optimizers offline, with two limits that stay: no matrix multiplication and no squashing functions such as softmax (D37). The project's active learning path, the discrete model in crates/uor-r4-discrete, is stricter still: it is integer from end to end (GPU and CUDA).

Served half. What ships is "D11", the project's serving contract (D11, 27 September). It has five rules:

RulePlain meaning
R1No floating point and no maths library
R2No multiply or divide instruction in any served kernel. Products of runtime values use tables or exact geometry
R3Reading every stored weight for every token is an interim stage, not the end state (D5)
R4No transformer backbone
R5Energy is claimed only when measured

Serving on the user's own device, including browser WebAssembly, is the product and is allowed (charter, section 3.6). The border between the halves is the export, and it is where a float-trained candidate is judged.

How the engine works

The container (definition). UORLUT01 stores weights as 4-bit codes in groups of 32. Each group has a one-byte scale, built from a 4-bit mantissa and a 4-bit exponent. A few small integer tables cover the nonlinear steps: square root, decay rates, exp, SiLU, GELU and arcosh (SiLU, GELU and exp are squashing-type tables; see the compliance note under "Where it stands") (format.rs).

A projection with no multiply (proof by construction). For a weight row \(w_{ij}=s_g\,q_{ij}\) with 4-bit code \(q_{ij}\) and group scale \(s_g\), the output is

\[y_i=\sum_j s_{g(j)}\,q_{ij}\,x_j .\]

Instead of multiplying \(q_{ij}\) by \(x_j\), the engine builds once per activation a 16-entry table \(T_j[q]=q\,x_j\) for \(q=0,\dots,15\). Each entry comes from the one before by adding \(x_j\). Each weight's code then selects an entry, and the group scale is applied with shifts and adds. Four output rows share each table (kernels.rs).

Two runtime values multiplied together (proof). A score, a gate or a value mix needs a true product of two numbers that only exist at run time. The engine reads it from a table of the sixteen multiples of one operand, built by repeated addition, indexed by the radix-16 digits (base-16 digits) of the other operand and summed with shifts (stack_mul_u64 and stack_mul_u128 in kernels.rs). Write \(b=\sum_k 16^k d_k\) with each digit \(d_k\in\{0,\dots,15\}\) and let \(T_a[q]=q\,a\), built as \(T_a[q+1]=T_a[q]+a\). Then

\[ab=\sum_k 16^k\,T_a[d_k(b)] ,\]

which is exact by the definition of base-16 digits, and each term is a table read followed by a shift. (An alternative that D11 rule R2 would also allow is the quarter-square identity \(ab=\lfloor (a+b)^2/4\rfloor-\lfloor (a-b)^2/4\rfloor\), which holds for all integers; the training crate uses it in addressing_arms.rs, but the serving engine does not.) Normalisation uses an integer square root, computed digit by digit, and the sampler is an integer min-p rule. That sampler filters on probability mass read from the exp tables, so it is part of the compliance gap described under "Where it stands".

Exact geometry as tables. Where the model uses geometry, the tables are exact: the Cayley table of the 120-element icosian group (about 14 KiB), a 1,025-entry arcosh table for Lorentz read scores, and the Q30 Hopf observation. The integer crate's native_geometry.rs provides the typed H4 geometry and checked integer arithmetic that the qualified native build uses, and discrete_d11.rs loads the table-native uor-r4.lut-discrete/1 (UORLUT01) container exported by d11_export.rs (discrete.table, discrete.cells, discrete.routes, and discrete.gates, with zero 4-bit matrix sections) to evaluate Route, Flock, and Relation prefixes in integer arithmetic (#2838).

A saved conversation (definition). The UR4SESS1 format saves a session's state and restores it byte for byte (session_codec.rs).

The zero-multiply audit

The audit disassembles the compiled release program and counts three kinds of instruction over the serving functions: Class I multiply, Class II divide, Class III floating point. The scripts are audit_zero_matmul_serving.py (native) and audit_zero_matmul_wasm.py (WebAssembly, with a call-graph mode). They are existing Python scripts; porting them to Rust is an open question.

  • Native: 44 symbol ranges audited, none with a forbidden instruction (project track, milestone M4). Measurement.
  • WebAssembly: 7 of 7 serving functions (not modules) with multiply, divide and float counts all 0, in the runtime merged as UOR-Foundation/uor-r4#2654 (record). It was written by an outside contributor and hardened in review before merge. Measurement.

What the audit proves is absence: those instructions are not in the audited functions. It says nothing about model quality, and it does not cover every function in the binary. The record also lists three limits. First, the WebAssembly SIMD kernels are fixtures that nothing calls; the serving path still uses the scalar table kernel. Second, the demo in docs/wasm-serving/ does not run from a clean clone until its bundle is built. Third, the serving-wasm build compiles the model, sampling and tables modules unconditionally. Compliance with the "presence counts" rule (D29) rests on the feature defaulting off plus link-time removal, an interpretation that DECISIONS.md does not record.

The export gap

Definition. The export gap of a candidate is its served score minus its float score, on the same evaluator and the same positions. It is the price of snapping. The charter says a float candidate whose gap is above the two-seed noise band is disqualified (charter, section 3.7).

Past gaps come from an older float model, the "geometric stack", not from today's discrete model. Bits per byte (BPB) and nats are different units, and lower is better in both.

And the export of a model built under today's rules has not been measured, because none has been exported.

Why reading every weight is not the end state. A dense model streamed through tables is still dense. The table-emulation energy test above is the evidence, and D5 asks instead for selected, addressed reads that touch few parameters per token. No existing schema fits today's rules as it stands. Schemas /1 and /2 carry softmax-style reads through exp-table masses, which the no-softmax rule (D23) names. A third schema serves a softmax-free flock read, but its trained arms missed their bar (record). All three carry SiLU and GELU tables, which the charter bans in renamed or table form (section 3.2), and all three stream dense 4-bit weight maps through a table-based matrix-vector product, which the charter excludes as a dense model disguised as lookup tables (sections 3.3 and 3.6). The min-p sampler also works on exp-table probability mass. D11 rule R3 ("reading every weight is an interim stage") is historical wording: dense table maps are no longer an allowed stepping stone for new exports. A new table-native schema, built on selected and addressed reads, is therefore likely required. These are the engine's known compliance gaps, and the serving mechanism page tracks them.
