# [codex] Why a better count score still produces the same answer

All four normal text prompts end with original ID 28, the colon in the literal assistant marker. The unpruned count file chooses ID 223 (one space) after that colon. With its own emitted space as the next input it chooses another space. All three trained count carriers emitted sixteen spaces and reached the generation limit on each question. The original trunk replied “Got it, I'll remember that.” and emitted EOS each time. Both directions of the Dan/Ben question, the arithmetic question and the planet question failed at their first emitted ID in every arm. The literal references and actual emitted IDs are preserved. The order-one count model only reads the last token. With identical starting IDs, deterministic feedback forces identical trajectories, regardless of names, facts or question. Its lower teacher-forced BPB therefore establishes a usable normalized local predictor and leaves prompt-conditioned writing open. The learned read, copy and generate decision remain separately measured components. This normal-entry result uses seed 1 and the bound M1 tokenizer on the client host.

The client loads one D11, scores original IDs through the same default integer library path as the stateless prediction API, and feeds each winner back. The library's optional trace exposes previous ID, fitted weight, winner and exact Q32 mass. An older trunk retains its original writer. Across the three count carriers, 495 raw rollout steps could be joined to the scorer's initial example list. That list stores device-chosen IDs and Rust-reconstructed winner masses. A second comparison joined **all 576 raw client steps** to an actual observed target at which the GPU winner equaled the corpus token. It read the winner ID and Q32 target mass directly from the hash-verified CUDA output. Every ID and mass matched, including later steps using the client's own output.
