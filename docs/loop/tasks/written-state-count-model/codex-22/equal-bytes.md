## Order-10 count cost and shared budget

The [sealed P0 receipt](https://github.com/UOR-Foundation/uor-r4/blob/78f97740fadb9d9432276635dba0c0d127cc9d73/docs/loop/tasks/written-state-count-model/claude-422/run1/sealed/sealed.json) lists 6,731,119,106 triples and 5,442,744,951 contexts across depths 0–10. At the canonical widths in `ngram_count.rs` (22-byte triple, 40-byte context), those record counts imply 148,084,620,332 and 217,709,798,040 bytes, respectively, or 365,794,418,372 bytes combined before any directory. These are canonical stream equivalents, not files on disk. Depth 10 alone implies 76,699,387,536 bytes. Query filtering kept 41,496,121 triples and 38,057,303 contexts, an equivalent 2,435,206,782 bytes combined. Its 226,587,908-byte depth-10 portion is also query-conditioned. `kn_filter.rs` takes each known query pair including the next ID. This is a valid target-mass witness for the KN reference, but these retained tables cannot serve as a query-blind model or equal-byte control.

Use 125,998,708 bytes as a feasible prototype total with seed 1. This leaves 39,462,576 bytes after the common trunk, or 39,445,788 after the current /2 envelope and unigram/weights. The 20-byte replay codec with its observed 348-byte overhead could fit at most 1,973,111 rows with eight bytes left at this budget, before any added scoring state. A 22-byte triple-only stream could hold at most 1,793,753 records even with zero overhead beyond the trunk and zero context records. A new format is needed to support an exact token-context control through k=12. Twelve 12-bit IDs require 144 bits before length/order, so fixed-order token digits alone take 18 bytes and cannot use the current order-10 u128 codec.

For each scored arm, let H be actual arm container bytes, U its unigram and weight bytes, I its address and read index bytes, P its output-head and transport parameter bytes, and S its other mandatory state beyond the common trunk. If fixed successor slots cost r bytes, their capacity at this total is floor((39,462,576 − H − U − I − P − S) / r). A common base scorer in addition to the trunk reduces the numerator by its actual bytes. A variable layout must measure the actual serialized sum of these terms across retained context and successor records. The canonical S3 rows, Starling index and output expert have no qualifying serialized footprint to substitute into this formula. For perspective, two 57,600-code scales need 460,800 bytes for a hypothetical single u32 index word per state. If naively provisioned for every optional (state, last ID) or state-only key, 471,974,400 u32 words would need 1,887,897,600 bytes. Sparse back-off indexing is necessary at this prototype budget if using that index representation. These examples impose no implementation layout. The P1 4 GB ceiling leaves 3,913,463,868 bytes beyond the seed-1 trunk. Ignoring all metadata, indexes, context totals and expert state, that ceiling holds at most 177,884,721 × 22-byte triples or 195,673,193 × 20-byte slots. Compression still must be measured for the real scorer.
