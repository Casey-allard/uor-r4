# CPU training repair program

The project has used several lawful training families, and most now survive only as inactive source or dated evidence. D84 authorizes a CPU research program to repair them without changing the default GPU training path or reopening mechanisms that already failed their rules.

This page is the durable plan behind the `cpu-training-program` roadmap item. Component parity below is evidence for the named implementation only; it is not qualification of CPU training or language capability.

## Boundary

- GPU remains the qualification authority. A CPU result is development research unless a later owner decision makes it a qualification path.
- Every CPU unit lives in a separately scanned Rust module, declares CPU execution, names the hardware, and has no silent GPU fallback.
- Geometry, no-squashing and no-matmul rules are unchanged.
- Each comparison uses the same tokenizer, panel, deterministic grader and count-table controls as its GPU counterpart.
- A negative closes the configuration that ran. It never erases the historical mechanism or its reopen conditions.
- Active Claude-owned float/FBS/integer files are out of scope until their current claim merges.

## Ordered work

### 1. CPU discrete writer core

Implement codebook decoding, canonical token vectors, cell admission, full-vector ranking, deterministic lower-token-ID tie-breaking, top-1/top-8, admitted-target reporting, and a reproducible row benchmark. Compare exact output with existing host oracles and stored GPU observations before adding a read.

### 2. CPU discrete training path

The component path is complete on finite fixtures: Route, Flock and Relation reads, 16-lane counterfactual proposals, strict-improvement semantics, atomic BVG-K apply, cursor/resume and checkpoint playback. This does not establish a corpus-training or language result.

### 3. CPU shared-vector forward

Create a conflict-free trainer crate around:

```text
token id -> shared token vector -> route/recurrence/read -> vector point -> token
```

Prove finite forward parity against the current integer artifact before adding gradients. The input, carry and output use one token table; exact token identity stays separate from its geometric address.

### 4. CPU shared-vector training

The component trainer is complete: rank-margin learning without softmax or dense matrix multiplication, deterministic update order, checkpoint identity, admission preservation, exact-integer panel evaluation and a strict masked-corpus driver. Final promotion now requires a complete served-forward audit and retains its receipt; a public zero-step smoke passed 64 positions and 16,384 Q12 coordinates exactly. The pre-registered public pilot then ran and produced a configuration negative: no top-1/top-8 gain on either seed, with admission and exact export preserved. The follow-up step-size and same-amplitude coordinate-breadth comparisons were also negative. K4 reduced the margin objective on both seeds but produced no top-1 gain and, on seed 1, lost one admitted target and one top-8 row.

### 5. Quantization and exact memory

Hamming reads, exact turn memory, saved-session restart and the finite integer/float shadow gate are complete. A genuine trained FBS float snapshot is not available, so the trained-artifact float-shadow and complete-reply comparisons remain `NOT_RUN`.

### 6. Whole-path exact updates

Cancelled at its probe. The retained source has no optimizer or run loop and cannot be separated from its rejected sampled M2 objective and dependencies. Exact-store transaction, bounded record ordering and replay remain future design input, not a trainer.

### 7. CPU pilot and disposition

The bounded public corpus pilot ran on the Ryzen 9 9950X and reported cost, exact export, admission and ranking. A separate FIT-reviewed public control then stopped at step 64 and resumed in a new process to step 256 on both seeds, producing byte-identical final artifacts and checkpoints. The FIT-reviewed BVG-K breadth pivot subsequently proved that four-coordinate blocks execute and improve the margin objective, but the ranking result remained negative on both seeds. Complete-reply/fresh-phrasing evaluation and a positive training configuration remain unavailable. A final disposition marks every historical family as supported, superseded, or retained as a rejected configuration, with links to its evidence.

## Why this order

The discrete writer is the smallest independently testable part and the arithmetic foundation of the discrete learner. The shared-vector forward then measures the current serving-aligned design before gradients add ambiguity. Training follows only after exact scoring exists. Quantization and memory come after both paths can run so their gains can be separated from a changed runtime. The corpus pilot comes last because a fast wrong trainer is not progress.

## Performance readings

Local synthetic diagnostics on the Ryzen 9 9950X recorded:

- exact outer-L1 writer rows: 216,251 rows/s on one thread and 3,034,004 rows/s on 16 threads;
- precomputed joint-pointer trunk rows: 132,385 rows/s on one thread and 1,793,613 rows/s on 16 threads;
- current synthetic integer FBS forward: about 5.4-7.5k tok/s with the native writer and 1.4-1.83k tok/s with whole-table nearest.
- full Hamming plus memory FBS path: about 3.1k tok/s on the current six-layer synthetic shape.
- composed served-forward audit fixture: one five-token synthetic artifact exercised Hamming copy/type reads at stream and readout depths, exact opening-memory lookup, point-key fallback, two reply rows and the native head with zero decision mismatches; this is mechanism coverage, not a throughput result or trained-model reading.
- served-forward audit on the two public trained raw FBS seeds: 4,331 / 5,649 CPU-oracle tok/s and 3,556 / 4,681 instrumented serving tok/s over 64 positions, with zero mismatches over 16,384 Q12 coordinates, 64 tokens and 512 kept cells per seed. These single-pass timings separate parity from timing and are component diagnostics, not a capability result.
- first tied-table rank-margin unit: about 236 accepted-step attempts/s on a width-64, two-layer synthetic Hamming path; 56 of 64 repeated steps accepted.
- exact BVG-K parameter candidates: 758.970 to 790.051 candidate evaluations/s on width 64, across normalization, bias, decay and route groups.
- matched panel evaluator: 10,802.874 synthetic rows/s with zero CPU/serving query, token or kept-cell mismatches and 6,320 KiB peak RSS.
- pre-registered public CPU pilot: 59.654/62.827 target visits/s, 4,824.742/5,081.373 context-tokens/s, 16.763/15.917 ms mean update, 66.024/64.993 s wall and 52,060/51,956 KiB peak RSS on seeds 1/2.
- public same-amplitude BVG-K K4 pivot: 62.968/68.153 target visits/s, 15.881/14.673 ms mean step, 127.108/121.640 s wall and 52,080/51,964 KiB peak RSS on seeds 1/2. These are component timings for a negative configuration, not evidence that CPU training is qualified.
- registered public restart: the resumed 192-step tails ran at 4,790.191/5,029.959 context-tokens/s and produced the same final artifact and checkpoint bytes as the uninterrupted arms on seeds 1/2.

These are unsealed component ceilings, not corpus training rates or language evidence. They justify building the CPU path; they do not qualify it.
