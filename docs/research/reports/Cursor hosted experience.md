# Cursor hosted experience

**Research report — 2026-11-09**

**Scope and evidence.** This report synthesizes six research notes and the retained primary sources gathered on 2026-11-09. No Cursor account was used, no login was attempted, and no task, repository or account was mutated. Tags used throughout: **[OBS]** public UI observed on 2026-11-09; **[DOC]** official Cursor or VS Code documentation, help, changelog or release notes; **[INF]** inference from cited facts; **[UNV]** not verifiable without an account, a task or a paid team. Exact strings are copy candidates from documentation, not observations of the authenticated interface.

Cursor's hosted experience is not a browser copy of VS Code. It is an auth-gated, conversation-first cloud-agent workspace: one durable agent thread, three distinct ways to send a message, a review handoff through Changes and pull requests, and remote terminal/desktop evidence, with the full editor inheritance deliberately left to the desktop IDE. The public record is strong enough to specify the behavior and state model, but not to pixel-match the signed-in product: `/agents` redirects every unauthenticated visitor to WorkOS, the public marketing mock uses different grouping and placeholder text than the release notes, and no screenshot or DOM of the current signed-in landing exists in the source set. More importantly, a static browser cannot reproduce Cursor's execution plane at all: repository installation tokens, webhooks, isolated VMs, PTYs, MCP stdio servers, secret storage and signed commits all live behind a backend or a local companion. The correct UOR-R4 target is therefore not "Cursor's backend, reimplemented." It is a browser-native model and a Cursor-grade task shell first, a host-approved local companion for files, terminal, Git and MCP second, and an explicit, optional service boundary for auth, secrets, background work and integrations last. That ordering is also the only one consistent with UOR-R4's actual state: M1 closed at 1 of 8 milestones, no model holds a useful conversation, and the repository has a working shell but no agent runtime.

## Cursor's hosted product is five surfaces sharing one backend, not one web IDE

Cursor 3, generally available on 2 April 2026, split the product in two. The desktop **IDE** remains the VS Code-derived workbench with extensions, themes, debugger, notebooks and Remote SSH; the **Agents Window** is a new, agent-first desktop interface built from scratch, with multi-repo navigation, file/terminal/browser/Changes/Output tabs and full LSPs, and users can "switch back to the Cursor IDE at any time" ([Cursor 3 blog](https://cursor.com/blog/cursor-3); [Agents Window](https://cursor.com/docs/agent/agents-window)). Cursor 3.0 then **removed cloud agents from the Editor**; the Agents Window and web are the surfaces that now document them ([Cursor 3.0 changelog](https://cursor.com/changelog/3-0)). The result is five distinct interaction surfaces, not one product with responsive chrome: **Cursor Web** at `cursor.com/agents`, the **desktop IDE**, the **desktop Agents Window**, **Origin** at `cursor.com/codebase` for hosted code browsing and review, and **iOS** (with API, CLI and chat integrations as additional entry points) ([Cloud Agents § How to access](https://cursor.com/docs/cloud-agent); [Origin browse](https://cursor.com/docs/origin/browse); [Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)).

The hosted URL is `cursor.com/agents`, but it has no public landing page. Every probed app route returned `307` to `https://cursor.com/api/auth/login?redirect_uri=…`, which hands off to WorkOS AuthKit at `authenticator.cursor.sh`; `/sign-in` is a 404, not a login form ([cursor.com/agents](https://cursor.com/agents) [OBS]; [cursor.com/sign-in](https://cursor.com/sign-in) [OBS]). The observed sign-in screen says "Welcome to Cursor," "The new way to build software," offers Google, GitHub, Apple, Slack and X glyph buttons, and shows an **Email** field with placeholder **"Your email address"** and a **"Continue with email"** button ([authenticator.cursor.sh](https://authenticator.cursor.sh/) [OBS]). A fresh headless Chrome profile was stopped by Cloudflare's "Performing security verification" interstitial; the built-in browser passed it. That is bot protection, not product behavior, and it is one reason the authenticated UI is under-observed.

The public marketing chrome is fully observable and materially smaller than the product. The measured header at 1440 px contains **Models / Product / Enterprise / Pricing / Resources**, with **Sign in**, **Contact sales** and **Download** on the right; **Cloud Agents** is a footer link to `/agents`, and **Docs / Help / Changelog / Marketplace** are public ([cursor.com](https://cursor.com/) [OBS]). The longer inventory in the agent-creation note captures the full nav/footer set; the measured top-level header at 1440 px is the five items above. That matters for replication: the public site is not a preview of the app's information architecture.

## The durable object is an agent thread, and the composer serves three send modes

Cursor's task model is one durable **agent/thread** containing many **runs**. The agent lifecycle is `ACTIVE` (a turn is running, waiting on background work, or about to start), `IDLE` (the last turn finished; follow-ups accepted; the machine may hibernate), and `ARCHIVED` (terminal; workspace state may be deleted) ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). A run is `CREATING`, `RUNNING` or `WAITING_FOR_BACKGROUND_WORK` while active, then `FINISHED`, `ERROR`, `CANCELLED` or `EXPIRED`; terminal runs carry `durationMs`, `result` and a per-agent Git snapshot. The distinction is not cosmetic: a follow-up starts a **new run** on the same thread, Stop ends the active run, Retry resumes a retryable run without a new message, and a cancelled run cannot be resumed, only continued with a new run ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints); [Agent overview](https://cursor.com/docs/agent/overview)).

**The creation contract.** The documented task-creation state is instruction text plus optional images, then repository (or **Start from scratch**), branch or starting ref, model and parameters, environment/worker, mode, MCP servers, attachments and secrets, then send or queue. The API's `Create An Agent` body is the best available proxy for the composer: `prompt.text`, `prompt.images`, `model`, `name`, `env`, `repos`, `startingRef` or `prUrl`, `workOnCurrentBranch`, `autoCreatePR`, `skipReviewerRequest`, `envVars`, `mcpServers`, `customSubagents`, `mode` ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). Not every field is necessarily exposed on the web, and the exact grouping is unverified.

Three exact-string cautions apply. The real signed-in placeholder is **not** public; the "Ask Cursor to build, plan, fix…" string comes from the official marketing mock, and the "Enter prompt text…" string comes from an automation mock. The stale text-extraction string "Ask Cursor to build, fix bugs, explore" is not a UI observation and should not be reused. And the `@`/`/` behaviour is documented for Agent generally, not specifically for the hosted web composer.

**Validation and error copy that is sourced.** A web attachment over the limit produces **`<filename> is too large (4MB limit)`** ([Agent troubleshooting](https://cursor.com/help/troubleshooting/agent-issues)); ZIP is unsupported as a web document; fork-PR automations fail with **"Fork pull requests not supported"** ([Automations](https://cursor.com/docs/cloud-agent/automations)); a worker that cannot start produces **"Cloud Agent could not get a worker to start your session; please retry in a few minutes."**; an environment reconnect says **"Reconnecting to your environment. This can take a few minutes."**; a blocked model produces **"Model Blocked"**; a privacy block produces **"Privacy Mode (Legacy) blocks Cloud Agents."**; a self-hosted workspace says **"Workspace runs on a self-hosted worker"**; a disabled team project says **"Projects are disabled for your team."** ([Cloud Agents release notes, weeks of Sep 7–Oct 19 2026](https://cursor.com/docs/release-notes/cloud-agents); [Cursor web release notes](https://cursor.com/docs/release-notes)). The API adds `400 validation_error`, `409 agent_busy`, `403 feature_unavailable`, `404 run_not_found` and `410 stream_expired` ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)).

**The list is an agent list, not a run list.** `GET /v1/agents` returns agents newest first, defaults to 20, max 100, supports a cursor and `prUrl` filter, and includes archived agents by default (`includeArchived` defaults to `true`) ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). The web list has **Search**, a **source filter** and pinned agents; the **75-pin** limit raised from 50 is documented only for the desktop 3.22 surface, while the web limit is unverified. The desktop sidebar groups agents into **Today / Last 7 days / Older**, with Older collapsed, and pins are saved to the account so they follow browsers and devices ([Cloud Agents release notes, Sep 28 2026](https://cursor.com/docs/release-notes/cloud-agents); [Cursor release notes 3.22](https://cursor.com/docs/release-notes)). In the Agents Window, a **New Agent** button opens the new-agent input; rename is on the right-click menu; archive is reversible with `Cmd+Z` / `Ctrl+Z` (or Edit > Undo when no text field is focused); **Archive All** acts on the clicked group; an archived agent remains readable but cannot accept new runs until unarchived; `DELETE /v1/agents/{id}` is permanent and irreversible ([Cursor release notes 3.26/3.20](https://cursor.com/docs/release-notes); [Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). Web parity for those row actions is unverified. On direct links, the **header, status and starting prompt** render before the rest of the page; opening a conversation only collapses the sidebar below **1024 px**; a collapsed sidebar is reopened with an **Open sidebar** button; **Cmd+, / Ctrl+,** opens Settings ([Cloud Agents release notes, Oct 12 and Oct 19 2026](https://cursor.com/docs/release-notes/cloud-agents)). Whether the web list exposes the desktop's **Show > Status**, Error group or per-row "last updated" is unverified; so is whether Delete appears in the UI at all.

**The shared layer is the thread and transcript.** Cloud agent conversations at `cursor.com/agents`, the PR agent panel and the Agents Window use the same transcript; the first message, including images, appears immediately, and assistant text and tool calls stream in ([Cloud Agents release notes, Oct 19 2026](https://cursor.com/docs/release-notes/cloud-agents)). Subagent tool calls and messages stream inline under the parent's task, and tapping a subagent card on iOS opens its child transcript ([Cloud Agents release notes, Oct 5 2026](https://cursor.com/docs/release-notes/cloud-agents); [Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)). In the Agent/IDE, checkpoints are created before significant changes and can be previewed and restored; restoring reverts files only, not messages, and forking the chat is the way to shorten the conversation. **Cloud Agents do not document a hosted checkpoint restore**, so a hosted detail page must not display one without a new source (correction C2).

**The desktop Agents Window adds the review-oriented chrome.** Finished work folds into **Worked** sections with a duration; a status line says what the agent is waiting for; plans appear as an editable card with a **Minimize** button that collapses it to a **Plan pill**; status pills above the prompt list live status first (pending input, Changes, Agents, Terminals, Canvas, Queue); side chats (`/side` or `/btw`, or the plus button) are durable parallel conversations that use the parent thread as hidden context; conversation search is `Cmd/Ctrl+K` in the Agents Window and `Cmd/Ctrl+F` finds text in the open conversation ([Agent overview](https://cursor.com/docs/agent/overview); [Cursor release notes 3.23/3.25/3.27](https://cursor.com/docs/release-notes)). Web parity for these controls is unverified.

**Execution has three send modes, and the default is install-dependent.** While the agent works, `Enter` adds the message to a queue below the active task; queued messages can be dragged to reorder and are processed sequentially. `Cmd+Enter` / `Ctrl+Enter` sends immediately, bypassing the queue and appending to the most recent user message. **Send now**, or `Enter` twice, steers: the message is delivered at the agent's next tool call instead of cutting off work mid-action. `Tab` queues the message for after the turn in the web/Agents Window description, but the IDE keyboard reference assigns `Tab` to "cycle to next message"; new installs steer by default while existing installs keep prior behavior ([Agent overview](https://cursor.com/docs/agent/overview); [Keyboard shortcuts](https://cursor.com/docs/reference/keyboard-shortcuts); [Cursor release notes 3.25](https://cursor.com/docs/release-notes)). Do not bind `Tab` globally, and do not claim a single default for every surface (correction C6). The API mirrors the distinction: a follow-up without `delivery` starts a new run; `delivery: "steer"` sends into the running turn; a steer accepts only `prompt` and `delivery`; a failed steer may still have reached the agent, so retrying can deliver the prompt twice ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)).

**The run stream is SSE, and the event set is broader than six names.** The documented events are `status`, `thinking`, `heartbeat`, `assistant`, `tool_call`, an optional richer `interaction_update` carrying `text-delta`, `tool-call-started`, `tool-call-completed`, `step-started`, `step-completed` and `turn-ended`, then `result`, `error` and `done`; tool calls use a stable envelope and may be truncated with flags ([Cloud Agents API § Stream a run](https://cursor.com/docs/cloud-agent/api/endpoints), re-read in the independent review). The stream is scoped to one run, does not replay prior runs, can resume with `Last-Event-ID`, and returns `410 stream_expired` after retention; the terminal state should then be read with Get A Run. A client must tolerate unknown event names and must not fabricate assistant or tool output from a malformed or partial event.

**Review separates the workspace diff from the remote PR object.** In the Agents Window, **Changes** is the workspace diff: scopes include **Last Agent Turn**, branch and picked commits; the scope, branch and picked commits survive tab restores; clicking **Review** or a file in the end-of-turn summary opens Changes in that scope ([Cursor release notes 3.22/3.27](https://cursor.com/docs/release-notes)). The Agents Window **PR** tab is the remote review object: five sub-tabs **Changes / Description / Commits / Checks / Reviews**, remembered across agent switches and restarts; `Cmd/Ctrl+click` on a diff line opens that line on GitHub or Origin; generated files start collapsed with a **Generated** badge; the **Merge** button stays disabled while an Origin rule blocks the merge; PR chips show merged/closed status ([Cursor release notes 3.26](https://cursor.com/docs/release-notes)). iOS can read full diffs, commits, deployments, approvals, comments and checks, add or change reviewers, and merge with squash, mark ready, update the branch, toggle auto-merge, publish or close ([Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)). In the web PR review flow, a review can be discarded from the PR header, `Cmd+Enter` submits a reply, and pending comments show as drafts immediately ([Cursor web release notes, Sep 21 and Oct 12 2026](https://cursor.com/docs/release-notes)). Web PR review and merge are documented at that level, but whether web exposes the same Changes scopes, five PR sub-tabs and memory, artifact cards and merge-state controls is unverified.

Execution evidence is separate from the diff. In the Agents Window, a **Terminal** tab for cloud agents explains why a machine is offline and connects when it is reachable; a **Cloud Desktop** tab streams the agent's desktop and stops when another tab is selected; forwarded ports and **artifact cards** offer **Add to Chat**, **Download**, **Copy Image** or **Copy Text** ([Cursor release notes 3.22/3.25/3.26](https://cursor.com/docs/release-notes)). The API lists artifacts under `artifacts/` and downloads via a 15-minute presigned S3 URL ([Cloud Agent capabilities](https://cursor.com/docs/cloud-agent/capabilities); [Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). Cloud Agents docs confirm a terminal and artifacts, but the artifact-card and desktop-control behavior above is documented in the desktop release stream; web parity is unverified. Cloud agents clone the repo, work on a separate branch and push; `workOnCurrentBranch` controls whether commits go to a new `cursor/...` branch or directly to the starting ref; `autoCreatePR` controls PR creation; every commit is signed and attributed to the agent, not the person ([Cloud Agents § Overview](https://cursor.com/docs/cloud-agent); [Security/network](https://cursor.com/docs/cloud-agent/security-network)).

**Automation keeps the thread alive after the first turn.** CI autofix automatically tries to fix GitHub Actions failures on PRs the agent created, skipping if a human pushed, a follow-up was sent, the check already fails on the base commit, or after 10 CI-failure follow-ups; it is documented for Teams/Enterprise, and other plans request it manually ([Cloud Agent capabilities](https://cursor.com/docs/cloud-agent/capabilities)). **Subscriptions** let a person-owned agent wait for GitHub PR/CI, Slack, Linear or timer events; events arrive as follow-ups in the same conversation; bursts coalesce; a subscription lasts at most **180 days**; service-account automations are excluded ([Cloud Agent capabilities](https://cursor.com/docs/cloud-agent/capabilities)). CI autofix turns the PR into a long-lived task, which is why the thread, not the run, must be the durable object.

**Failure and recovery are typed.** A retryable run error shows a **Retry** button in the transcript that resumes without a new message; the generic copy is **"This run hit an unexpected error. Retry or send a follow-up below."**; errors appear in a tray above the input with one next step where one applies, such as **Retry**, **Manage Usage** or **Manage Environments** ([Cursor release notes 3.20/3.22](https://cursor.com/docs/release-notes)). A message sent after Stop runs instead of staying queued; a message sent as the agent wraps up is answered as one more step in the same run; editing an earlier message resumes from that turn's state, and if the state cannot be found the edit fails and leaves the transcript intact ([Cloud Agents release notes, Sep 14–Oct 12 2026](https://cursor.com/docs/release-notes/cloud-agents)). Stop is the documented interrupt, and stopping a subagent stops every subagent it started; the API's cancel is terminal (`CANCELLED`, cannot resume), so continuing requires a new run ([Agent help](https://cursor.com/help/ai-features/agent); [Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). **Pause is not a documented user action**: the word appears only as a state (an agent pauses on a question or MCP sign-in; a Jira run shows as working instead of paused). That is a negative finding about documentation, not proof the feature is absent (correction C15).

**Usage is per run, but cost is plan-level.** `GET /v1/agents/{id}/usage` returns input, output, cache-write, cache-read and total tokens per run and in total, including subagents and side chats; `GET /v1/agents/{id}/runs/{runId}` returns status, timestamps, `durationMs`, `result` and a per-agent Git snapshot ([Cloud Agents API](https://cursor.com/docs/cloud-agent/api/endpoints)). The Cloud Agents dashboard opens with **Total runs**, **Success rate** and **Recent runs**; **All Runs** adds a run-history chart, a table and filters for trigger, status and creator; team admins see team runs, personal users their own ([Cloud Agents release notes, Aug 31 2026](https://cursor.com/docs/release-notes/cloud-agents)). The Agents Window shows **"Worked for"** per turn. No per-task dollar cost, token-count UI on the task page, latency percentile or SLO is documented. That is again a documentation gap, not a confirmed absence.

## The web has an editing surface, but the IDE still owns the deep work

The single strongest official statement about web editing is the mobile FAQ: iOS has "no editor, terminal, or file browser," and "For full editing, use the desktop app or cursor.com/agents" ([mobile help](https://cursor.com/help/ai-features/mobile-app); [Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)). That establishes a web editing surface. It does **not** establish Monaco, LSP, a debugger, notebooks, themes, extensions or split view; no Cursor page describes the web editing surface's depth (correction C3). The desktop IDE is the only surface with the full VS Code inheritance: workbench, menus, keybindings, Open VSX extensions, Color Theme, Remote SSH/Dev Containers/WSL, language services, debugger and Jupyter ([VS Code user interface](https://code.visualstudio.com/docs/getstarted/userinterface); [VS Code Remote Development](https://code.visualstudio.com/docs/remote/remote-overview); [VS Code debugging](https://code.visualstudio.com/docs/debugtest/debugging); [VS Code notebooks](https://code.visualstudio.com/docs/datascience/jupyter-notebooks); [Cursor themes](https://cursor.com/help/customization/themes); [Cursor extensions](https://cursor.com/help/customization/extensions)). The Agents Window sits in between: multi-repo sidebar, file/terminal/browser/Changes/Output/canvas tabs, `Cmd+P` and `Cmd+Shift+F`, full LSPs per the Cursor 3 blog, remote SSH, but themes require **Open IDE** and VS Code extensions are not its extension model ([Agents Window](https://cursor.com/docs/agent/agents-window); [Cursor 3 blog](https://cursor.com/blog/cursor-3); [themes help](https://cursor.com/help/customization/themes)).

**Inline edit is retired.** Selecting code and pressing `Cmd+L` or `Cmd+K` now opens Agent with those lines referenced; `Cmd+K` used to open inline edit and has been replaced by that workflow ([Cursor help: Agent mode](https://cursor.com/help/ai-features/agent)). `Cmd+K` is also surface-specific: in the IDE it toggles the sidepanel or adds a selection to a new chat; in the Agents Window it opens the command palette with **Select Model**, **Archive** and **New Side Chat**, and pasting a PR URL or number jumps to that PR; on the web no command palette is documented ([Keyboard shortcuts](https://cursor.com/docs/reference/keyboard-shortcuts); [Cursor release notes 3.25](https://cursor.com/docs/release-notes)). A studio that binds `Cmd+K` to one action across surfaces will feel wrong to Cursor users and will collide with browser shortcuts.

The prompt input is the highest-value surface and the hardest to copy correctly. Documented controls include the **mode picker** (`Shift+Tab` rotates modes, `Cmd+.` opens the Mode Menu), the **model picker** (`Cmd+/` cycles), the **context ring** next to the prompt with a breakdown tray for **System prompt, Tools, Rules, Skills, MCP, Subagents, Summarized conversation, Conversation**, `@` context, `/` skills and commands, image drag/paste, microphone dictation, the waveform **Start voice chat**, and Send/Stop ([Prompting](https://cursor.com/docs/agent/prompting); [Plan mode](https://cursor.com/docs/agent/plan-mode); [Voice chat](https://cursor.com/docs/agent/voice-chat)). The `@` menu's documented items are files/folders, **@Terminals**, **@Chats**, **@Commit (Diff of Working State)**, **@Branch (Diff with Main)** and **@Browser**; `/` attaches a skill to one message with `Enter`, keeps it as a mode with `Option+Enter`/`Alt+Enter`, and a skill used as a Custom Mode stays in context on every turn ([Prompting](https://cursor.com/docs/agent/prompting)).

## UOR-R4 has a shell and a model file, not an agent runtime

The UOR-R4 baseline is materially different from Cursor's, and the difference is the point. M1 closed on 30 October 2026 at **1 of 8 milestones**, with a saved discrete model that passes six bars but reads new phrasings into known reply kinds; 62.5% of its held-out-phrasing reference replies are verbatim TRAIN replies, so it is **not useful conversation** ([D83](../../integration/DECISIONS.md); [project-track](../../integration/project-track.md); [web client](../../products/web-client.md)). The current worktree `AGENTS.md` records **1 of 8**; the owner's preserved checkout may still say 0 of 8, so use the current worktree and D83. Six findings frame the gap.

**B1 — The Studio is a manual, single-session workbench, not an agent.** The typed shell has a real section union (`agent`, `workspace`, `changes`, `terminal`, `models`, `guide`, `browser`), a real editor textarea with tabs and disk save, bounded Git status/diff, a real PTY in the native host, model source management including OpenAI-compatible SSE chat, a static guide, one secondary pane, both themes and responsive breakpoints. It has **no project entity, no task/plan/tool timeline, no concurrent sessions, no approval objects, no account, no scheduler and no agent loop**; session, file and model state are single-valued, and the "Project" modal and Environment/Permission selects are honest placeholders whose only alternative options are disabled ([`StudioApp.tsx`](../../../web/studio/src/components/StudioApp.tsx); [`lifecycle.ts`](../../../web/studio/src/state/lifecycle.ts); [`SessionToolbar.tsx`](../../../web/studio/src/components/SessionToolbar.tsx); baseline note §1). The typed composer is text-only: its file handler filters out images and calls `readTextFiles`; the legacy page still has a bounded raster image path, but the typed shell does not expose it, so a Cursor-like screenshot workflow needs new attachment handling, not a restyle ([`AgentComposer.tsx`](../../../web/studio/src/components/AgentComposer.tsx); baseline note §1).

**B2 — One frontend and one typed guard layer are the reuse spine.** One Vite/Preact build supplies the mounted web preview, the native runner and the Tauri app; the typed shell mounts into `#studio-typed-root` while the legacy `#app` stays in the same document and is hidden by CSS. The built page defaults to typed; the raw source page defaults to legacy unless `?typed=1`; `?legacy=1` and `?typed=0` are the documented escape hatches ([`vite.config.ts`](../../../web/studio/vite.config.ts); [`index.html`](../../../web/studio/index.html); [`bootstrap.ts`](../../../web/studio/src/bootstrap.ts); baseline note §1). The typed layer already encodes stale-result refusal, save serialization, verified session mutations and artifact SHA/capability checks; those are genuine reuse assets, but they are not an agent runtime ([`operations.ts`](../../../web/studio/src/adapters/operations.ts); [`fileSave.ts`](../../../web/studio/src/adapters/fileSave.ts); [`agentSession.ts`](../../../web/studio/src/adapters/agentSession.ts); [`modelSourceAdapter.ts`](../../../web/studio/src/adapters/modelSourceAdapter.ts)). Retained evidence at the kimi-17 fresh-main head records **455/455** Vitest tests, **47/47** Playwright checks, **15/15** runtime contracts, **11/11** gates and **7/7** direct WASM checks; the 2026-11-09 neutral Studio publish is gh-pages `4a435ab8…`, with `?legacy=1` and `?typed=0` retaining the old interface ([current-state](../../integration/current-state.md); [web client](../../products/web-client.md)).

**B3 — The API crate is a shim, and the model/tool stream contract does not exist.** `crates/uor-r4-api/Cargo.toml` sets `[lib] path = "src/native_support.rs"`; that file is a 17-line re-export of `uor_r4_core::native_geometric` and says every historical API module is preserved as uncompiled evidence. The old `lib.rs` and `native_capability_api.rs` are not the crate root and are not built. A repository-wide search finds **zero** occurrences of `ModelApi`, `ModelRequest`, `ModelEvent`, `AgentRuntime`, `AgentEvent` or `AgentClient`; the only `ModelApi::stream(ModelRequest)` mention is in a local draft, as a target dependency ([`Cargo.toml`](../../../crates/uor-r4-api/Cargo.toml); [`native_support.rs`](../../../crates/uor-r4-api/src/native_support.rs); baseline note §3). The only executable text stream is the `uor-chat` sidecar's OpenAI-compatible SSE, which accepts text, images and usage options but **not** `tools` or `tool_choice`; the browser client parses `choices[].delta.content`, `finish_reason` and usage, with no tool-call branch ([`openai.rs`](../../../crates/uor-r4-integer/src/openai.rs); [`studio_api.js`](../../../web/studio/assets/js/studio_api.js)). The preserved `complete_stream` callback is a false positive: it streams text pieces, has no event enum, no tool call and no cancellation token, and is not built by the active lib path.

**B4 — A precise ORDER draft exists, but it is unimplemented.** `local/kimi/studio-agent-order-draft.md` proposes a new `crates/uor-r4-studio-agent` runtime, narrow `src-tauri` adapters, a typed `agentClient.ts`/`state/agent.ts`, a versioned event schema, independent task cursors, generation-scoped cancellation, next-safe-boundary redirection, host-consumed approvals, proposed object-store snapshots with serialized writers, one schema for Tauri and authenticated HTTP/SSE, and red-first acceptance for malformed/partial/duplicate/out-of-order events, parallel tasks, stop preventing later tools, approval forgery, restart recovery, stale-generation rejection and corrupt snapshots (baseline note §4). The draft is Cowork-oriented in vocabulary and does not define a concrete event JSON schema, field names, error taxonomy, cursor encoding or approval object shape; it also does not specify a Cursor-like UI, file tree, diff comments, account/settings or hosted deployment. The draft's Rust runtime and object-store task persistence are not adopted in this report; the recommendation below is a browser TypeScript runtime with per-run IndexedDB event records, with `crates/uor-r4-studio-agent` retained only as an optional schema/canonical reference.

**B5 — Tauri command + loopback RPC is the only host authority worth extending.** The Tauri builder registers **36** command handlers covering models, arithmetic, images, sidecar chat/cancel, sessions, granted folders, file read/write/list, Git status/diff, pickers, terminal enable/confirm/run/open/read/input/resize/close and MCP remote/stdio. The page RPC is a single `POST /__tauri_invoke` on loopback requiring exact `Host`, exact `Origin`, `Content-Type: application/json` and a per-launch `X-UOR-Desktop-Token`; the same backend is reachable as a newline-delimited stdio JSON-RPC loop. Folder grants are host-owned and canonicalized with `..` and symlink refusal; terminal enablement and exact-command approval are host-owned; MCP remote/stdio sessions require native confirmation; the sidecar is host-owned and proxies OpenAI JSON/SSE without exposing its token to the page ([`lib.rs`](../../../src-tauri/src/lib.rs); [`main.rs`](../../../src-tauri/src/main.rs); [`sidecar.rs`](../../../src-tauri/src/sidecar.rs); baseline note §2). `uor-r4-object-store` provides a content-addressed `Store` with manifests and an `IdentityScope` (`user/project/session`); the Tauri backend already uses it for existing session save/restore, with serialized writers because the store does not promise concurrent writers or directory-metadata crash durability. It is scoped to those existing Tauri session snapshots and optional bounded exports, not to the browser task/event log; future task records belong in IndexedDB ([`durable_consumer.rs`](../../../crates/uor-r4-object-store/src/durable_consumer.rs); baseline note §2).

**B6 — There are three environments, and only two exist.** **Static browser** (GitHub Pages) has the shell, WASM artifact loading/prediction, exact arithmetic, localStorage persistence and explicit unsupported states; it has no host tools, no API host and no background work. **Tauri/local companion** is an unsigned development app with the 36 commands, token-protected loopback bridge, granted folders, a real PTY, remote/stdio MCP and a host-managed `uor-chat` sidecar; it is not a signed or production release. **Hosted service** does not exist: no account, no background task service, no authenticated public endpoint, no cross-device resume ([`docs/products/web-client.md`](../../products/web-client.md); [`docs/products/desktop-client.md`](../../products/desktop-client.md); [`harness-parity.md`](../../products/harness-parity.md); baseline note §6). The public runtime's only model-visible output is exact arithmetic (`17 + 25 = 42`), not generated prose; the 47/47 Playwright run does not exercise real model chat.

These are the gaps the staged plan must close, in that order, without pretending a fixture is a capability.

## Build browser-first, then earn the backend

The architecture question is not "browser or server." It is **which authority belongs where**. Cursor's own split answers it: the browser is a client for conversations, diffs, review and approvals; the agent loop and inference run in Cursor's cloud; tool execution runs in an isolated VM or a self-hosted worker; the desktop IDE owns the local filesystem, extensions, debugger and notebooks ([Cloud Agents § Environments](https://cursor.com/docs/cloud-agent); [Self-hosted](https://cursor.com/docs/cloud-agent/self-hosted)). UOR-R4 wants a different split for the one thing that matters most: **the model itself runs in the user's browser**. Everything else can follow Cursor's separation.

**The studio target, in one screen.** For UOR-R4, "copy Cursor" resolves to a concrete shell rather than a generic chat page: a left rail of tasks with search, pins and Today / Last 7 days / Older groups; a center transcript with a composer that supports queue, steer, force-send and stop, `@` context, `/` skills, image and document attachments and dictation; a tabbed work surface for Changes, PR, terminal, artifacts and an editor; a top bar with repository, branch, model, environment and account; and a settings layer that keeps personal, team and organization scopes distinct. Visually, the target is the measured low-chrome system: near-black canvas, one surface step, hairline borders, 4 px card radii, restrained type hierarchy and one accent reserved for focus and selection. The product target is the loop, not the chrome.

### Why some features still need a companion or a service

Model inference is the one Cursor capability that can move entirely into the browser, because WebAssembly can execute the exported integer artifact locally and the page can keep prompts and replies on the device ([web client](../../products/web-client.md)). The rest cannot:

- **Repository identity and webhooks.** A GitHub App installation token, a GitLab OAuth client secret, a webhook signature secret and a Slack app credential cannot live safely in browser JavaScript; they need a server-side app identity and a public endpoint. Cursor's GitHub App is installed by a Cursor admin and a GitHub org admin, and access is inherited from the triggering user ([GitHub](https://cursor.com/docs/integrations/github)).
- **Real files, Git and a PTY.** A browser can use user-mediated uploads and, where implemented, the File System Access API, but it cannot open an arbitrary shell, read a repository outside a grant, or run `git` without a host process. Cursor's web terminal is a remote PTY; the IDE terminal is local ([Cursor release notes, Oct 5 2026](https://cursor.com/docs/release-notes); [VS Code terminal](https://code.visualstudio.com/docs/terminal/basics)).
- **MCP stdio.** A stdio MCP server is a child process; a browser cannot spawn one. Cursor's cloud agents run stdio servers in the VM and proxy HTTP servers through the backend ([Cloud Agent capabilities](https://cursor.com/docs/cloud-agent/capabilities)).
- **Secrets.** Runtime secrets must be stored, injected at start and redacted from tool results, transcripts and commits; `localStorage` is not a secret store. Cursor documents three secret types and server-side redaction ([Security/network](https://cursor.com/docs/cloud-agent/security-network)).
- **Signed commits.** Cursor signs every agent commit with an HSM-backed Ed25519 key; a browser cannot hold that key or produce a GitHub-verified signature ([Security/network](https://cursor.com/docs/cloud-agent/security-network)).
- **Background and cross-device work.** Unattended execution, hibernation, resume, push notifications and shared team viewing require durable server state; a tab that closes cannot keep a task alive ([Cloud Agents](https://cursor.com/docs/cloud-agent); [Cursor for iOS](https://cursor.com/docs/cloud-agent/mobile)).
- **Collaboration and audit.** Team viewing, read-only sharing, follow-ups, audit logs and retention policies are server-side objects, not UI flags ([Cloud Agents § Share](https://cursor.com/docs/cloud-agent); [Compliance](https://cursor.com/docs/enterprise/compliance-and-monitoring)).

The implication is precise: **the browser owns the model, the transcript view and the user's intent; the companion owns host tools and local authority; the service owns identity, secrets, background execution and integrations.** A static page that pretends otherwise becomes capability theater.

### Four approaches, one recommendation

| Approach | What it buys | What it costs | Verdict |
|---|---|---|---|
| **A. Static-only Cursor clone** | Fast to build; honest demo; no backend; model stays local | No real terminal, files, Git, MCP stdio, secrets, GitHub App, background or cross-device; every "agent" action is simulated or disabled | **Shell/demo only.** Useful as a marketing preview and a design harness, not as the product. |
| **B. Backend-first Cursor clone** | Full execution plane; multi-user; integrations; background work | Rebuilds Cursor's hardest infrastructure (VMs, snapshots, workers, signed commits, webhooks, audit); slow; security burden; makes the browser model feel bolted on; contradicts the "model in the browser" differentiator | **Not recommended as the first move.** Some service boundary is inevitable, but building the whole backend before the shell is inverted. |
| **C. Browser-first progressive enhancement with a local companion and optional service** | Model runs locally; one frontend; host tools through explicit grants; service added only where needed; matches Cursor's own client/worker split | Companion install and trust UX; service is a later, separate security review; some features are unavailable until the service exists | **Recommended.** It is the only approach that preserves the product's identity and still reaches Cursor-grade behavior. |
| **D. Embed a VS Code-like editor** | Familiar editing, syntax highlighting, keybindings; Monaco/CodeMirror can be a component | Bundle weight; Monaco is not a workbench; a full `code-server` would be a second shell, a second backend and a second authority channel; LSP/extension host/debugger still need a server | **Optional component, not the architecture.** Use Monaco/CodeMirror for the editor pane if needed; do not embed a second IDE. |

The recommendation is **C**. It maps cleanly onto what UOR-R4 already has: one Vite/Preact frontend, a typed lifecycle/adapter layer, a Tauri host with grants/PTY/Git/MCP/sidecar, and a Tauri object store limited to existing session snapshots and optional bounded exports, not task authority. It also maps onto what Cursor actually documents: a web client, a cloud VM or self-hosted worker, and a desktop surface for local authority. The difference is where the model runs. In Cursor the model is server-side; in UOR-R4 it is in the browser tab. That is the differentiator worth protecting.

```
Browser (one Preact app, one build)
  ├─ Browser/page-worker task runtime; per-run IndexedDB event records; verified snapshot manifests
  ├─ R4 model runtime in a Web Worker (WASM, integer artifact, tokenizer, exact memory)
  ├─ Task shell (thread, composer, queue/steer/stop, Changes, PR, editor, artifacts)
  └─ Transport adapter (one event schema)
        ├─ Tauri IPC / loopback (local companion)
        │     ├─ granted folders, file read/write, Git
        │     ├─ PTY (enable + exact-command approval)
        │     ├─ MCP stdio/HTTP (native confirmation)
        │     └─ optional bounded export (object-store snapshot; not task authority or browser run log)
        └─ Optional HTTPS/SSE service (explicit opt-in)
              ├─ auth / identity / session
              ├─ secrets (store, inject, redact)
              ├─ background tasks, notifications, cross-device resume
              └─ integrations / webhooks / team sharing
```

**Gated appendix A — Optional service and integrations (not an executable stage).** Outcome: auth/identity, secrets, background tasks, notifications, integrations/webhooks and cross-device resume under a tenant boundary. Proof: auth/session tests; secret redaction; webhook signature verification; background restart; no unauthenticated endpoint. Non-claim: opt-in and not required for local use; no service exists in the baseline.

**Gated appendix B — Real R4 qualification (not an executable stage).** Outcome: a generation-capable R4 model runs in the browser and is measured on useful tasks, latency, RAM and energy where available. Proof: sealed fresh evaluation with denominator and uncertainty; bound artifact/tokenizer identity; no fixture output counted; `R4ModelPort` remains `NOT_RUN` until the generation-capable artifact and merged streaming/tool contract exist. Non-claim: no full Cursor parity; no useful conversation before evidence; no capability claim from UI or fixtures.

**Acceptance requirements that apply to every executable stage and gated appendix.** Correctness comes first: a versioned event schema, explicit state machine, idempotency, stale-generation rejection and cursor recovery. Security is host-side: approvals are identity objects consumed by the host, never a page-supplied boolean; grants are canonicalized; secrets never enter the page; no unauthenticated public endpoint. UX is testable: keyboard-only operation, focus return after dialogs, ARIA names, IME-safe `Enter`, `Shift+Enter` newline, paste/drag attachments, reduced motion, and 390/1024/1440 layouts. Performance is measured, not asserted: first-token latency, tokens/second, RAM, artifact size and energy where a meter exists. Model claims are separate: only a real R4 run on a fresh panel can establish useful behavior, and the report must state the denominator, uncertainty and exact negative scope.

**What not to do.** Do not clone Cursor's backend, its fonts, its assets or its copy at scale; use the documented labels as a vocabulary and write your own. Do not put **Restore Checkpoint** on a hosted detail without a new source. Do not bind `Tab` globally. Do not make the Tauri object-store the task authority or browser run log; it is only existing session snapshots and optional bounded export. Do not claim Pause, Delete, Logs or per-task cost are absent merely because the docs are silent; say "not documented; UI status unknown." Do not promote Agents Window chrome to the web. Do not present the marketing mock's grouping or placeholder as the signed-in product. Do not claim LSP, debugger, extensions, notebooks or themes on the web. Do not edit `crates/uor-r4-api/**`, the model/engine/worker/tokenizer, the owner roadmap metadata or `.github/**`, and do not break the legacy `#app` selectors or the `?legacy=1`/`?typed=0` paths.

## Conclusion

Cursor's advantage is not its color palette or its menu order. It is the **loop**: a durable thread that accepts a queue, a steer and a stop; a review handoff that turns agent output into a diff, a PR and a merge decision; and a cross-device continuity model that makes the task, not the tab, the unit of work. Those are the parts worth copying, and they are also the parts that require a real runtime and a real host boundary. The visual layer is a consequence of the loop, not a substitute for it.

UOR-R4 can build a cleaner product than Cursor because it has fewer surfaces to reconcile and a stronger locality story: one browser-native model, one shared frontend, one host authority, one optional service. But that story only becomes a capability claim after the model can do useful work and the runtime can survive a hostile event stream. Until then, the honest deliverable is a fast, inspectable, local-first workbench with explicit limits — and a parity matrix that says exactly which Cursor behaviors are documented, which are inferred, and which remain unverified.
