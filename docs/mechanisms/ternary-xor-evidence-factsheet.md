# Fact sheet: 1-bit / ternary inference, and what is actually XOR

Scope labels: **[THEORY]** = operation count or model-based estimate, no runtime measurement · **[KERNEL]** = custom kernel/op benchmark · **[E2E]** = end-to-end wall-clock. Every line's URL was fetched.

## 1. BitNet b1.58 (arXiv 2402.17764, Ma/Wang/Wei et al.)

- **1.58-bit framing:** every weight is ternary {-1,0,+1}; the name is log2(3) ≈ 1.585, stated as "added an additional value of 0 to the original 1-bit BitNet, resulting in 1.58 bits in the binary system". Absmean quantization: `RoundClip(W/(γ+ε), -1, 1)`, γ = mean |W|. Activations kept at 8-bit. — [abs](https://arxiv.org/abs/2402.17764), [HTML §1–2](https://arxiv.org/html/2402.17764v1)
- **Claimed replacement for matmul:** "the matrix multiplication of BitNet only involves integer addition"; the claim is INT8 **addition** only, with a per-weight scaling factor applied outside the multiply. It does **not** claim bitwise/XOR replacement anywhere. — [HTML §1](https://arxiv.org/html/2402.17764v1)
- **Measured quality [E2E-quality]:** 700M/1.3B/3B/3.9B trained from scratch on RedPajama, 100B tokens. Parity with reproduced FP16 LLaMA at 3B: PPL 9.91 vs 10.04; end-task avg 50.2 vs 49.7. At 700M it is worse (PPL 12.87 vs 12.33). 3B/2T-token run beats StableLM-3B (74.34 vs 73.22 avg). — [HTML Tables 1–4](https://arxiv.org/html/2402.17764v1)
- **Measured latency/memory [E2E]:** FasterTransformer codebase on GPU, with the Ladder 2-bit kernel. Time-per-output-token 3B: 1.87 ms vs 5.07 ms (2.71×), memory 2.22 GB vs 7.89 GB (3.55×). 70B claimed 4.1× faster. Throughput on 2×80 GB A100, pipeline parallel, seq 512: 70B goes from 333 to 2977 tok/s (8.9×) at 11× batch. — [HTML §3](https://arxiv.org/html/2402.17764v1)
- **Speedup class:** a real measured wall-clock speedup, but on a **2-bit GPU kernel** (not a ternary-arithmetic unit), and the authors note "still room for optimization".
- **Energy is [THEORY]/estimate:** "According to the energy model in [Horowitz 2014; PokeBNN], BitNet b1.58 saves 71.4 times arithmetic operations energy consumption for matrix multiplication on 7nm chips." Not a measurement. — [HTML §3 Energy](https://arxiv.org/html/2402.17764v1)

## 2. BitNet b1.58 2B4T (2504.12285) and bitnet.cpp

- **2B4T report:** 2B params, 4T tokens, W1.58A8, ReLU² FFN, RoPE, no biases; eval avg 54.19 vs Qwen2.5-1.5B 55.23 (a loss, not a win, at equal-ish size). Table 1 efficiency row: memory 0.4 GB non-emb vs 2.6 GB, "Latency (CPU; TPOT) 29 ms" vs 65 ms. **MEASURED SCOPE: CPU model/vendor not stated in the report** → the 29 ms and any implied speedup are **unattributed to hardware**; label UNVERIFIED as a hardware-relative speedup. — [HTML §5, Table 1](https://arxiv.org/html/2504.12285v2)
- **Its own GPU kernel does packing, then unpacking, then normal matmul:** "four ternary values are encoded into one int8"; kernel "unpacks these values back into a representation suitable for efficient ternary computation … immediately before performing the matrix multiplication with the 8-bit activations". Strategy named "pack-store-load-unpack-compute". **No bitwise arithmetic; the decode/unpack is explicit overhead.** — [HTML §5.1](https://arxiv.org/html/2504.12285v2)
- **CPU section delegates to lookup tables:** bitnet.cpp kernels "avoid… intricate low-level bit manipulation". — [HTML §5.2](https://arxiv.org/html/2504.12285v2)
- **bitnet.cpp kernels (2504.12285's cited report = arXiv 2410.16144, HTML fetched directly):**
  - **I2_S:** each weight → 2-bit code (see §5 below: {-1,0,1} mapped to 00/01/10); unpack then "vanilla multiply-then-addition GEMV". No bitwise trick.
  - **TL1:** every **two** weights → 4-bit index; the 9 = 3² activation sums precomputed into an int16 LUT; "GEMV processing is performed using an int16 LUT and accumulation through addition."
  - **TL2:** every **three** weights → one sign bit + 4-bit index (5-bit index total); "reduces model size by 1/6 compared to TL1".
  - So the actual technique is **table lookup + integer add**, i.e. multiplication removed by LUT, not by XOR. — [HTML §2, Tables 1–3](https://arxiv.org/html/2410.16144v2)
- **Benchmarked hardware:** ARM = Mac Studio, Apple **M2 Ultra**, 64 GB; x86 = Surface Laptop Studio 2, **Intel Core i7-13700H** (14C/20T), 64 GB. Two settings: 2 threads, and unlimited. — [HTML §3.1](https://arxiv.org/html/2410.16144v2)
- **Numbers [E2E wall-clock, tok/s]:** unlimited threads — Apple M2: 1.37× (125M) → 5.07× (70B; llama.cpp cannot host 100B, bitnet.cpp does 6.58 tok/s). Intel i7-13700H: 2.37× (125M) → 6.17× (13B). Thread-limited (2 threads) — M2 1.59×→2.48×; **Intel peak 6.46× at 7B** (12.41 vs 1.92 tok/s). Energy 55.4–70.0% (ARM) and 71.9–82.2% (x86) reduction in J/token. — [HTML Tables 4–6](https://arxiv.org/html/2410.16144v2)
- **Repo-side claim:** "speedups of 1.37× to 5.07× on ARM CPUs… On x86 CPUs, speedups range from 2.37× to 6.17×"; kernels "built on top of the Lookup Table methodologies pioneered in T-MAC". Supported-kernel matrix: x86 gets I2_S+TL2 for 2B4T, ARM gets I2_S+TL1 (TL kernels are arch-specific). — [raw README](https://raw.githubusercontent.com/microsoft/BitNet/main/README.md)
- **T-MAC (the LUT lineage):** "transforms the traditional data-type-centric multiplication to bit-wise table lookup"; claims up to 4× throughput and 70% energy reduction vs llama.cpp; BitNet-b1.58-3B at 30 tok/s single-core and 71 tok/s 8-core on M2-Ultra, 11 tok/s on Raspberry Pi 5. [E2E] — [abs 2407.00088](https://arxiv.org/abs/2407.00088)

## 3. The original binary / ternary line

- **BinaryConnect — arXiv 1511.00363** (NOT 1511.9030; that ID resolves to an unrelated handwriting-recognition thesis — [verified](https://arxiv.org/abs/1511.09030)). Claim: binary weights "would bring great benefits to specialized DL hardware by replacing many multiply-accumulate operations by simple accumulations, as multipliers are the most space and power-hungry components". **Measured: accuracy only** (near-SOTA MNIST/CIFAR-10/SVHN); no runtime benchmark. [THEORY] for the arithmetic claim. — [abs](https://arxiv.org/abs/1511.00363)
- **BinaryNet / BNN — arXiv 1602.02830** (the user's premise that 1603.05279 is BinaryNet is wrong). "replace most arithmetic operations with bit-wise operations". **Measured [KERNEL, not E2E]:** "we wrote a binary matrix multiplication GPU kernel with which it is possible to run our MNIST BNN **7 times faster than with an unoptimized GPU kernel**". The 7× is against an unoptimized baseline, on MNIST. — [abs](https://arxiv.org/abs/1602.02830)
- **XNOR-Net — arXiv 1603.05279** (Rastegari et al.). Two regimes: (a) binary **weights only** → convolution by "additions and subtractions (without multiplication), resulting in ~2× speed up"; (b) both binary → "convolutions can be estimated by XNOR and bitcounting operations", "~58× speed up in CPUs (**in terms of number of the high precision operations**)", 32× memory. **The 58× is explicitly an operation-count argument [THEORY]**, not wall-clock. Measured accuracy: binary-weight AlexNet = full-precision AlexNet; XNOR-Net "only 2.9% less" top-1; >16% better than BinaryConnect/BinaryNet on ImageNet. — [abs](https://arxiv.org/abs/1603.05279), [HTML §1, §3.1](https://arxiv.org/html/1603.05279v4)
- **DoReFa-Net — arXiv 1606.06160.** 1-bit weights, 2-bit activations, 6-bit gradients; "can use bit convolution kernels to accelerate both training and inference"; "bit convolutions can be efficiently implemented on CPU, FPGA, ASIC and GPU". **Measured: accuracy** — AlexNet 46.1% top-1 ImageNet with 1-bit weights/2-bit activations. No speedup number. [THEORY] — [abs](https://arxiv.org/abs/1606.06160)
- **Ternary Weight Networks (TWN) — arXiv 1605.04711.** Weights {-1,0,+1}; "2-bit storage requirement is needed for a unit of weight"; up to 16× compression. Key caveat: "the zero terms need not be accumulated… the multiply-accumulate operations in TWNs keep unchanged compared with binary precision counterparts" — i.e. the compute saving comes from **skipping zeros**, not from a cheaper per-weight operation. Text says only "need fewer multiplications"; no kernel, no timing. **Measured: accuracy** — ImageNet ResNet18B top-1 65.3 vs 67.6 FPWN; PASCAL VOC YOLOv5s mAP_50 76.8 vs 86.7 FPWN. [THEORY] — [abs](https://arxiv.org/abs/1605.04711), [HTML §2.1, Tables 2–3](https://arxiv.org/html/1605.04711v3)
- **Trained Ternary Quantization (TTQ) — arXiv 1612.01064.** Learns ternary values **and** assignment; "only ternary values (2-bit weights) and scaling factors are needed", "nearly 16x smaller". Critically: "Our ternary models can also be viewed as **sparse binary weight networks**, which can potentially be accelerated with custom circuit" — a proposal, not a measurement. Improves CIFAR ResNet-32/44/56 by 0.04/0.16/0.36% and ImageNet AlexNet top-1 by 0.3% over full precision. [THEORY] — [abs](https://arxiv.org/abs/1612.01064)

## 4. Multiplication-free / adder-only inference

- **AdderNet — arXiv 1912.13200 (CVPR 2020).** Replaces cross-correlation with **ℓ1 distance**: `Y = -Σ|X - F|`; "subtraction can be easily reduced to addition by using complement code". **Measured: accuracy** — ResNet-50 ImageNet 74.9% top-1 / 91.7% top-5 "without any multiplication in convolution layer". Accuracy cost vs a full-precision baseline is **not stated in the fetched sections** → the delta is UNVERIFIED here (`arXiv:2105.14202` is the extended version). Note batch normalization still multiplies; the paper argues BN cost is ~1/4068 of conv at d=3, c_in=512 → omission is an estimate, not a proof of zero multiplication. ## 5. The rigor question: is ternary inference "XOR-based"?

**XOR is addition in GF(2) — confirmed at field level.**
- GF(2): "If the elements of GF(2) are seen as Boolean values, then the addition is the same as that of the logical XOR operation… The multiplication of GF(2)… corresponds to the logical AND operation." Also: "The addition of this vector space is the bitwise operation called XOR." — [Wikipedia GF(2)](https://en.wikipedia.org/wiki/GF(2))
- Same page, the load-bearing caveat: bit-string spaces over GF(2) "can also be augmented with a multiplication operation that makes them into a field GF(2^n), **but the multiplication operation cannot be a bitwise operation**." So GF(2) gives you XOR as *addition*; it does not give you a bitwise dot product.

**Binary dot products = popcount of a bitwise op — but which op depends on the encoding.**
- **±1 encoding → XNOR.** XNOR-Net: `y = x*W ≈ x^b * W^b = popcount(XNOR(x^b, W^b))`, with weights/inputs in {+1,-1} "encoded as 1/0". — [ar5iv 2206.03325 §III-A eq. 8](https://ar5iv.labs.arxiv.org/html/2206.03325)
- **{0,1} encoding → AND, not XNOR.** PrecisionBatching states the reason explicitly: "typical binary quantized neural network weights contain values that are -1 or 1 rather than 0 or 1. Hence, instead of the xnor operation we use the **and** operation to simulate 1-bit multiplication." — [ar5iv 2003.00822 §3.4](https://ar5iv.labs.arxiv.org/html/2003.00822)
- **AND-based matching counts:** `a = popcount(AND(x^b,W^b))` (both 1), `b = popcount(AND(~x^b,W^b))`, `c = popcount(AND(x^b,~W^b))`, `d = popcount(AND(~x^b,~W^b))`; cross-correlation `y = a + d - (b + c)`. — [ar5iv 2206.03325 §III-A eqs. 10–14](https://ar5iv.labs.arxiv.org/html/2206.03325)
- **XOR/popcount gives Hamming distance, and only distance.** "For binary strings a and b the Hamming distance is equal to the number of ones (population count) in a XOR b." — [Wikipedia Hamming distance](https://en.wikipedia.org/wiki/Hamming_distance). Consequence, stated plainly: XOR alone cannot produce a signed dot product; the standard ±1 dot product is popcount(XNOR), and any XOR-only route first needs the identity |a XOR b| = |a| + |b| − 2|a AND b|, i.e. it needs the AND term as the correction. **This correction step is my derivation from the fetched sources, not a quotation from any of them — treat as derived, not cited.**

**Why the ternary alphabet {-1,0,+1} breaks bitwise treatment.**
- A weight needs ≥2 bits (three values). bitnet.cpp encodes {-1→00, 0→01, 1→10} with **11 unused**, and then does not compute bitwise at all: I2_S "transforms the weights back to their original values and performs the vanilla GEMV operations", and TL1/TL2 replace the multiply with a **lookup table**. — [HTML §2 Tables 1–3](https://arxiv.org/html/2410.16144v2)
- The 0 case has no bitwise encoding because it is a **skip**, and a skip is not a two-input Boolean function of (activation bit, weight bit) — no gate can express "this operand is absent". The literature's answers are the two non-XOR ones: **skip the zero** (TWN: "the zero terms need not be accumulated") or **table the whole pair/triple** (TL1 3²=9 entries, TL2 3³=27 entries). — [TWN HTML §2.1](https://arxiv.org/html/1605.04711v3), [bitnet.cpp §2](https://arxiv.org/html/2410.16144v2)
- 2B4T's GPU kernel is the same story one level down: 4 ternaries packed per int8, then unpacked before matmul, with Ladder cited for details. Unpack/decode cost is acknowledged as implementational, not eliminated. — [HTML §5.1](https://arxiv.org/html/2504.12285v2)

**Bitserial / bitsliced multi-bit packing, and its decode cost.**
- **PrecisionBatching (arXiv 2003.00822)** decomposes fixed-point W and x into 1-bit tensors: `W = 2^-16 (2^(n-1) W1^(b) + … + 2^0 Wn^(b))`; negatives handled by a two's-complement-style extra negatively-scaled bitlayer. Uses AND+popcount over bit-packed ints. **Measured [KERNEL + E2E]:** wall-clock over 1000 iterations of each op, NVIDIA **Tesla T4**, baselines via NVIDIA **Cutlass/WMMA** (4/8/16-bit tensor cores); >8× end-to-end on GPU within <1% error of FP32, 1.5–2× over 8-bit quantized inference at equal error. Decode costs named and quantified qualitatively: conversion to fixed point is "a simple multiply and cast", bit rearrangement is a bitwise matrix transpose with "negligible overhead"; memory reduced ~32/n; compute ops increase by factor k. **This is the honest precedent: the decode is real but cheap, and it is AND/transpose, never XOR.** — [ar5iv 2003.00822](https://ar5iv.labs.arxiv.org/html/2003.00822)

- A RISC-V PIM paper with a `bitserial_conv2d` operator exists but the publisher page is **403-blocked** ([link](https://dlnext.acm.org/doi/fullHtml/10.1145/3458744.3473351)); numbers UNVERIFIED.

**Booth encoding, redundant signed digits, carry-save — standard, additive, and unrelated to XOR.**
- Booth's algorithm "multiplies two signed binary numbers in two's complement"; it "examines adjacent pairs of bits", adds the multiplicand when it sees 01, subtracts when it sees 10, does nothing on 00/11, then arithmetic-shifts. It is often described as "converting strings of 1s in the multiplier to a high-order +1 and a low-order −1 at the ends of the string" — a **signed-digit recoding**, implemented purely with adds/subtracts and shifts. **No XOR appears anywhere in the algorithm.** — [Wikipedia Booth's multiplication algorithm](https://en.wikipedia.org/wiki/Booth%27s_multiplication_algorithm)
- So: a ternary (or any small-alphabet) digit **can** be handled additively — Booth radix-4 is exactly the standard, long-shipped case (Intel Pentium used a radix-8 Booth multiplier with carry-lookahead/carry-select/Kogge-Stone adders). Carry-free/redundant-binary and carry-save accumulation are standard arithmetic, not exotic. **Honest statement: this machinery is orthogonal to XOR.** GF(2)-XOR is characteristic-2 algebra with no carries; Booth/carry-save are integer signed-digit tricks that exist precisely *because* integer addition carries. They solve the ternary-decode problem by *avoiding a multiplier*, which is what bitnet.cpp's LUT also does — not by turning multiply into XOR.

**What "packing ±1 as a bit" actually buys, from primary sources.** XNOR-Net's binary **weight-only** case yields ~2× by replacing multiplications with additions/subtractions; the 58× requires binarizing activations too, and is an operation count. — [HTML §1, §3.1](https://arxiv.org/html/1603.05279v4). PrecisionBatching adds the memory-side story: packing "yielding 32× reduction in memory for each product of bitlayers", with the speedup attributed to memory-bound batch-1 inference, not to gate count. — [ar5iv §3.4, §1](https://ar5iv.labs.arxiv.org/html/2003.00822)

## 6. Does anyone call a ternary-weight network "XOR-based"?

**No.** Two targeted searches for `"XOR-based" ternary weight network` and `ternary weight network popcount/XNOR bitwise` returned no paper that brands a ternary network as XOR-based. The XOR/XNOR branding in the literature belongs to **binary ±1** networks only (XNOR-Net; XNOR-Net++ and similar). The closest things actually done to ternary are: (a) LUT decomposition of weight pairs/triples with integer accumulation (TL1/TL2 in bitnet.cpp, [HTML §2](https://arxiv.org/html/2410.16144v2)); (b) skip-the-zero sparsity (TWN, [HTML §2.1](https://arxiv.org/html/1605.04711v3)); (c) "sparse binary weight networks… potentially accelerated with custom circuit" (TTQ, [abs](https://arxiv.org/abs/1612.01064)); (d) LUT-based bitwise table lookup for arbitrary low-bit widths (T-MAC, [abs](https://arxiv.org/abs/2407.00088)). **None of these is XOR-based, and none claims to be.**

**Bottom line for the brief.** XOR = GF(2) addition is true and citable, but it is a statement about a 2-element field, not about ternary arithmetic: GF(2) has no third element and no bitwise multiplication, XOR+popcount yields Hamming distance (a distance, needing an AND correction to become a signed dot product), and the {-1,0,+1} alphabet forces ≥2 bits per weight with the 0 handled as a skip or via a 3²/3³-entry lookup table. Measured wins in this line come from **memory bandwidth and LUT/add kernels** (2.37–6.17× x86 E2E, [2410.16144](https://arxiv.org/html/2410.16144v2)), not from bitwise arithmetic. The 58× figure everyone quotes is an **operation count** ([1603.05279](https://arxiv.org/abs/1603.05279)); the honest measured kernel number there is 7× against an unoptimized GPU kernel ([1602.02830](https://arxiv.org/abs/1602.02830)).
