# The pipeline map

This page follows one token from the training data to the last word of a reply served on an Apple M1 laptop. For each stage it gives seven things:
- the mechanism;
- the exact domain it reads and the domain it writes, and whether the next stage reads that domain;
- its size now and the size the goal needs;
- its hardware;
- its cost per token;
- its status;
- what it depends on.

It answers the owner's direction of 27 October 2026 (recorded verbatim in the item [`pipeline-map`](../roadmap/items/pipeline-map.md)). The goal is a local model of about GPT-4's ability, trained on less than a datacenter and served on a laptop like this one. The page ends with:
- the scale arithmetic for that goal;
- the gaps, ranked by what blocks the goal first;
- an order of work.

**Labels.**
- **Measurement:** a recorded run; its source is named.
- **Proof:** follows from the code or from arithmetic on stated numbers.
- **Hypothesis:** untested.
- **External:** a published figure from outside the project, with the publication named under [Sources outside the project](#sources-outside-the-project).

Code line numbers are at `5bc6f6522`.

**The hardware this page targets** (measurement, `sysctl` on this laptop, 27 Oct; the same machine as [claude-126's timing](../loop/tasks/d11-exporter-float-trunk/claude-126/REPORT.md), line 73):
- Apple M1, with 4 performance and 4 efficiency cores;
- 16 GiB of memory (17,179,869,184 bytes);
- macOS 27.

The M1's other units are an 8-core GPU and a 16-core Neural Engine (external, Apple).

## Two model paths

The repository trains two different models, and they do not meet:

| | Float in-space trunk ("FBS trunk") | Discrete path |
|---|---|---|
| Code | [`crates/uor-r4-float-train`](../../crates/uor-r4-float-train) | [`crates/uor-r4-discrete`](../../crates/uor-r4-discrete/README.md) |
| What it carries | The replies: DEV text at every checkpoint ([float-training notebook](../research/notebook/float-training.md), row of 27 Oct "Exploration") | The M1 bar ([PLAN](../../PLAN.md), "The path to M1") |
| Table | 4,096 × 256 float values | 4,096 tokens × 4 blocks of 8 integers, each block one of 16 E8 roots ([the model, end to end](architecture.md), stage 2) |
| Export | `uor-r4.lut-stack/4`, through `fbs-export` | `uor-r4.lut-discrete/1` |
| Best DEV top-1 of 14,287 | **8,765** whole-table nearest, float, content-read arm at seed 1 ([float-training](../research/notebook/float-training.md) line 13) | **455** writer, integer, Stage T `FrozenZero` ([m4-serving](../research/notebook/m4-serving.md) line 17) |

They share:
- the tokenizer and the data;
- the D11 runtime crate, [`crates/uor-r4-integer`](../../crates/uor-r4-integer).

They share no table, no trunk and no artifact format. This page follows the FBS trunk, because it is the one that writes replies. Where the discrete path differs, the stage says so.

## The chain at a glance

| # | Stage | Reads | Writes | Does the next stage read it in that domain? |
|---|---|---|---|---|
| 1 | Data | text | token ids (u16) in windows of 192 | yes |
| 2 | Tokenizer | UTF-8 bytes | ids in [0, 4,096) | yes |
| 3 | Table | an id | a point in ℝ²⁵⁶ (discrete: four E8-root blocks in ℤ³²) | yes, as trunk input. The readout compares against the same points |
| 4 | Trunk | one table point per position | a state in ℝ²⁵⁶ after the final norm | yes, but the state carries about 6 tokens back (stage 4) |
| 5 | Look-back | earlier positions' table points, as 64-bit sign codes | a copied token's table point, which moves the readout point | open: two copy forms landed where the readout does not read; the readout-move form is unrecorded (branch, #3332) |
| 6 | Long memory | an exact address | stored bytes | **no**: no stage forms the address, and no stage reads the bytes |
| 7 | Readout | a query point in ℝ²⁵⁶ | a token id | yes. But the decoder served (the writer) is not the decoder evaluated (whole-table nearest) |
| 8 | Decode loop | an id | the next id, greedy | ids only: the FBS artifact has no text path |
| 9 | Training | DEV and TRAIN windows | float weights | yes |
| 10 | Integer export | a float snapshot | a `UORLUT01` integer artifact | discrete: exact. FBS: the export gap fails |
| 11 | Serving on M1 | the artifact and prompt ids | reply ids | — |

### 3. Table

| Field | Now |
|---|---|

| Cost per token | Input: one row, 256 values (1 KiB as f32; proof). The readout's cost is in stage 7. |
| Status | Built. The gradient split is measured. |
| Depends on | Upstream: the tokenizer. Downstream: the trunk, the look-back's codes, and the readout. |

### 4. Trunk

| Field | Now |
|---|---|
| Mechanism | The FBS sheet, all merged. | Domain | One table point per position in; a state in ℝ²⁵⁶ after the final norm out. The readout reads it as a query point in the table's space: yes. **What the state carries:** replacing the token k places back with BOS moves the opening point by 5.97 at k = 0, 0.37 at k = 6 and 0.04 at k = 12. 57–66% of lane positions in layers 1–5 sit at the shortest memory rate after training, against 33% at step 0. Both measurements: [float-training](../research/notebook/float-training.md) line 16. |
| Size | **Now:** 63,744 trainable values in the six layers. Each layer has six FBS maps holding 8,448 values, with 4 stages for inputs of 256 and 384, plus 2,176 norm, convolution, gate and decay values. Proof by arithmetic on `shapes()` (line 687); no receipt prints the count. With the table and the final norm, the model holds 1,112,576 values, 94% of them the table. The state does not grow with context (proof: a recurrence). **Goal:** Phi-3-mini has 3.8B parameters (external), about 3,400 times this whole model. |
| Hardware | Training: GPU only. The model refuses to run unless on CUDA in F32 with SpiralCore/FBS, with "no host or dense fallback" (`geometric_stack_native.rs` line 938). Serving: the integer runtime on the M1 CPU, scalar code. Native NEON table kernels exist only for an older frozen stack ([desktop client](../products/desktop-client.md) line 49). The M1 GPU and Neural Engine are unused. |
| Cost per token | **Training:** <ul><li>20,355–23,865 tok/s in the 25 Oct sheet, 4 arms × 2 seeds on two RTX 5090s ([float-training](../research/notebook/float-training.md) line 17);</li><li>20,113–24,524 across claude-126's eight arm-seeds ([claude-126](../loop/tasks/d11-exporter-float-trunk/claude-126/REPORT.md) line 82);</li><li>in the content-read run, two arms shared one GPU: the read arms ran at 21,820–21,989 and their twins at 24,852–25,068 ([float-training](../research/notebook/float-training.md) line 13). That is about 47,000 tok/s per GPU in total, but from two separate runs. No single run has been measured above about 25,000 tok/s.</li></ul> **Serving:** see stage 11; the trunk is not timed apart from the session. |
| Status | Fit is measured: whole-table nearest top-1 up to 8,765/14,287 ([float-training](../research/notebook/float-training.md) line 13), above the bigram's 6,300 and the M1 count table's 7,002 (line 16). Prompt use is measured negative: openings at 161 to 220 of 1,226, where 161 is the count of the commonest opening token (lines 15–16). |
| Depends on | Upstream: the table. Downstream: the look-back and the readout. |

### 5. Look-back

| Field | Now |
|---|---|
| Mechanism | On main, two trunk reads, both negative against their pre-registered bars: <ul><li>the state-keyed Flock read: openings 235 against a bar of 236 at seed 1, and 264 against 307 at seed 2 ([claude-144](../loop/tasks/in-space-trunk-to-text/claude-144/REPORT.md) lines 14–21, with the bars in its table);</li><li>the content read: openings 208, 302 and 280 against twins at 247, 229 and 280 ([float-training](../research/notebook/float-training.md) line 13). It passed the openings bar at one seed of three (302 against 265), and its reach stayed below its bar at all three: best `R16` 0.0195 against 0.05 ([claude-145](../loop/tasks/in-space-trunk-to-text/claude-145/REPORT.md) lines 16–18 and 35).</li></ul> **On branch `claude/hamming-read` (#3332, not merged)**, the Hamming read: <ul><li>each earlier position's key is the sign code of its token's table point after a learned per-lane rotation, 64 bits per head, with 4 heads;</li><li>the match is popcount of XOR, a hard top 16, weighted by max(0, m − d)/m;</li><li>copy heads move the readout point n toward the copied token's point c: n + w(c − n).</li></ul> |
| Domain | Sign codes in {0,1}⁶⁴ per head; out, a table point in ℝ²⁵⁶. Whether the readout reads it: open. The two earlier copy forms put the token where the readout does not read: the copied position's residual "reads as the trunk's own input, not its answer" (`87ade4920`), and a point added before the final norm "barely moves where the prediction lands" (`6d8bac253`). Both commits are on the branch. The readout-move form's result is not recorded (#3332). |
| Size | **Now:** a context of 192 (`SHEET_CONTEXT`, `hamilton_sheet.rs` line 66). The serving session cannot slide its window (`fbs-toks.rs` line 9). The discrete path's window holds at most 243 = 3⁵ positions ([architecture](architecture.md), stage 3). **Goal:** GPT-4 shipped with 8,192 and 32,768 tokens of context (external), 43 to 171 times this. |
| Hardware | Training: GPU. Serving: none. The integer runtime has no Hamming read. |
| Cost per token | Proof, from the branch's shapes: 4 heads × 64 bits is 32 bytes of code per position per read. With reads at two points, a token costs 8N popcounts and reads 64N bytes at context N. At N = 32,768 that is 2 MiB per token. A dense model's cache, at Llama-2-7B's shape (32 layers, width 4,096, 16-bit keys and values; external), is 512 KiB **per position**, or 16 GiB per token at the same N: 8,192 times as many bytes (proof). Measured cost on main: the content read cost about 12% of training throughput ([float-training](../research/notebook/float-training.md) line 13). |
| Status | Hypothesis. No look-back form on main has cleared its pre-registered bars. claude-146 reports a recall result on its synthetic probe; it is not yet in the repository (#3332). |
| Depends on | Upstream: the table (its codes come from table points) and the trunk. Downstream: the readout, which it must move. |

### 7. Readout

| Field | Now |
|---|---|
| Mechanism | Two decoders, both merged, both scoring by negative mean L1 distance to table points: <ul><li>**The writer** ([`native_vector_writer.rs`](../../crates/uor-r4-float-train/src/native_vector_writer.rs) lines 13–39). It has 256 cells, keeps 1 to 16 of them (8 here), and picks the nearest token inside them. It refuses more than 8,192 identities, a width above 1,024, or more than 16 kept cells. The serving session decodes with it.</li><li>**Whole-table nearest** (`nearest_scores`, [`in_space_long.rs`](../../crates/uor-r4-float-train/src/in_space_long.rs) line 204). The float runs evaluate with it.</li></ul> The discrete path uses an integer writer: it opens K = 8 of 256 cells, and admission caps every stage above it ([architecture](architecture.md), stage 5). |
| Domain | A query in ℝ²⁵⁶ in, a token id out. The decode loop reads it: yes. **The two decoders disagree on the same checkpoint:** writer top-1 345 against whole-table nearest 7,813 at lr 1e-3 ([float-training](../research/notebook/float-training.md) line 16). The writer's address hinge at margin 1 cannot be met, because its 16 roots are at least 0.5 apart (line 16; `in_space_long.rs` lines 38–40). The `voronoi` objective sets the margin to 0.25, half that separation. It gave the best writer-decoded score, 7,906 at 16,384 steps; whether it prevents the writer's later collapse is untested ([claude-142](../loop/tasks/in-space-trunk-to-text/claude-142/REPORT.md) line 107). On the discrete path, a table keyed by the read code predicts 3,414 rows against the writer's 149 ([m1-discrete-attention](../research/notebook/m1-discrete-attention.md) line 97). |
| Size | **Now:** 4,096 candidates. **Goal:** about 100,000 (stage 2), beyond the writer's limit of 8,192. |
| Hardware | Training: GPU. Serving: M1 CPU, scalar. |
| Cost per token | Proof, by arithmetic: <ul><li>whole-table nearest is 4,096 × 256 = 1,048,576 absolute differences;</li><li>the writer is 8 cells × 16 tokens × 256 = 32,768, plus ranking the cells;</li><li>at 100,256 tokens and width 1,024, whole-table nearest would be 102,662,144 per token.</li></ul> At that size a sublinear index would be needed (hypothesis). |
| Status | The mismatch is measured. Which decoder should be the one served is undecided. |
| Depends on | Upstream: the table, the trunk and the look-back. Downstream: the decode loop. |

## The scale arithmetic for the goal

GPT-4's own size and training data are not published (GPT-4 Technical Report, external). The comparisons below therefore use published open models of known size as reference points.

| Quantity | Now | Reference (external) | Ratio (proof) |
|---|---|---|---|
| Training tokens | 7,512,797 (stage 1) | Phi-3-mini: 3.3T. Llama 3.1 405B: 15.6T | about 440,000× to Phi-3-mini |
| Trainable values | about 1.11M (stage 4) | Phi-3-mini: 3.8B | about 3,400× |
| Context | 192 (stage 5) | GPT-4: 8,192 and 32,768 | 43× and 171× |
| Vocabulary | 4,096 (stage 2) | `cl100k_base`: 100,256 | 24× |
| Training throughput | about 20,000–25,000 tok/s per run, one run per RTX 5090 (stage 4) | — | 1T tokens in about 116 to 145 days on 4 GPUs, assuming perfect scaling (stage 9) |
| Decode on this laptop | 231–268 tok/s at 1.1M values (stage 11) | A dense 7B model at 4 bits: weights of 3.5 GB against about 68 GB/s of M1 memory bandwidth, a ceiling near 19.5 tok/s | see below |

**Serving speed per value read** (an estimate). Assume cost grows with the values read per token:
- One decoded token reads about 64,000 trunk values and about 33,000 writer values (stages 4 and 7). At 231–268 tok/s that is 2.2–2.6 × 10⁷ values per second.
- A dense 4-bit model limited only by bandwidth reads about 1.4 × 10¹¹ values per second on this chip (68.3 GB/s at half a byte each).
- So per value read, the integer runtime is about 5,000 to 6,000 times slower than that bandwidth limit (1.37 × 10¹¹ against 2.2–2.6 × 10⁷).

No profile says where the time goes. This is the largest serving question at scale.

**Where the geometry claims to change the arithmetic**, and what is measured:

| Claim | What it would change | Measured | Hoped for |
|---|---|---|---|
| Facts live in exact memory, not in parameters | Fewer parameters for the same knowledge. Language models store about 2 bits of knowledge per parameter (Allen-Zhu and Li, external). | With the true address supplied, 80/80, against 0/80 with no memory. Free-running, 0/40 (stage 6). | That the model forms addresses and reads the result in the readout's domain. |
| Long context by popcount | Look-back reads 64 bytes per position, not 512 KiB: 8,192 times fewer (proof, stage 5). | Cost only. No look-back has cleared its pre-registered bars (stage 5). | That a Hamming read carries the prompt into the reply. |
| A recurrence with constant state | Memory per token does not grow with context (proof, stage 4). | The state carries about 6 tokens back (stage 4). | That retention or a look-back extends it. |
| Integer serving with no multiplier | Runs on any CPU, with an exact artifact. | Runs on this laptop at 231–268 tok/s for 1.1M values; the discrete export is exact. Energy is 4.3 times worse on an older dense model (stage 11). | That a laptop serves a capable model at a useful speed. |
| Training below datacenter scale | 1T tokens on 4 GPUs in about 116 to 145 days, about $6,200 to $7,800, if one model scales across them (stage 9). | Only for 1.1M values. Nondeterministic (stage 9). | That ability arrives at a small enough size for this budget. No scaling slope has been measured. |

## The gaps, ranked by what blocks the goal first

1. **No stage carries the prompt into the reply.** Without a read, openings sit at 161–220 of 1,226, where 161 is the commonest opening token's count. The best read reached 302 at one seed. The state reaches about 6 tokens back, and no look-back has cleared its pre-registered bars (stages 4 and 5). Without this, no reply answers its question.
2. **The decoder served is not the decoder trained and evaluated.** On the same checkpoint the writer scores 345 and whole-table nearest 7,813. The writer's margin 1 cannot be met. The table's output side gets 1/410 of its gradient (stages 3 and 7).
3. **The FBS artifact does not compute what was trained, and training does not repeat.** The FBS export gap fails on all six receipts, and five identical runs spread from 745 to 3,845 (stages 9 and 10). The discrete export is exact, but that model scores 455.
4. **The serving session cannot slide its 192-token window, and the integer runtime has no look-back** (stages 5 and 8). Long context, the geometry's main claim, cannot be served yet.
5. **Serving speed per value is about 5,000 to 6,000 times below the laptop's bandwidth limit** (an estimate, from the scale arithmetic). This is scalar code with no NEON or GPU kernel for the FBS step, and it is unprofiled (stage 11).
6. **Long memory is not connected to prediction.** No stage forms an address, and the store's bytes land nowhere the readout reads (stage 6).
7. **The FBS artifact has no text path.** It takes ids and gives ids (stage 8).
8. **The two model paths do not join.** The M1 bar rests on the discrete path, the replies on the FBS trunk, and they use different tables, trunks and formats (Two model paths).
9. **Scale caps, with no slope.** The writer allows at most 8,192 identities and width 1,024. The corpus is 7.5M tokens, the window 192 to 243, and no run has measured how ability grows with size (stages 1, 5 and 7).
10. **Greedy decoding only, and the cost of multiplier-free serving.** Neither has a decision: a lawful sampling rule does not exist, and the 4.3-fold energy cost was measured on an older model (stages 8 and 11).

## Recommended order of work

Each unit is one loop session. "Pass" and "fail" say what each outcome unlocks.

| Unit | What it does | A pass unlocks | A fail unlocks |
|---|---|---|---|
| U1 (in flight, claude-146, #3332) | Records the Hamming read whose copy heads move the readout. | It becomes the look-back for U3 and U4. | That configuration closes. The next form fixes the credit fault the research note names: a wider candidate set with graded weights. |
| **U2 (first new unit)** | **One decoder.** Train with the `voronoi` objective, whose address margin can be met (claude-142: 7,906), long enough to pass the step where the writer collapsed. Read the writer and whole-table nearest on the same checkpoints. | The served decoder is the evaluated one, so every later served number means what training measured. | Serve whole-table nearest instead: 1M differences per token at 4,096 tokens, which needs an index before a larger vocabulary. |
| U3 | An integer Hamming read in `uor-r4-integer`, with parity against float and `fbs-toks` timing. | The look-back can be served on the laptop. | The look-back stays float-only; find the part that does not export. |
| U4 | A sliding, long-context FBS session: shift the window, and give the look-back a ring of codes longer than 192. | Contexts beyond 192 tokens on the laptop, timed. | The recurrence's window handling is redesigned before any long-context claim. |
| U5 | A deterministic FBS backward (a fixed-order reduction in place of float `atomicAdd`), then the export gap re-measured with repeats. This is claude-140's next unit. | Runs can be compared, and the export gap gets a verdict. | Report every comparison with a stated spread from repeats. |
| U6 | Store to prediction: on the M3 oracle rows, write the stored token's table point where the readout reads. | Free-running memory above 0/40, and the first evidence that facts can leave the parameters. | Address formation has to be learned first; that becomes its own unit. |
| U7 | A text path for the FBS artifact: the tokenizer, the dialogue protocol and the turn-end token, in `uor-chat --stack`. | A typed question gets a typed reply on this laptop. | The protocol bundle needs porting first. |
| U8 | A scale probe: width 512 and 1,024 (the writer's limit), and a corpus beyond 7.5M tokens. `distill-d1` needs the owner's release. | A measured slope of ability against size: the first number for the goal arithmetic. | The architecture's scaling becomes the open question before anything larger is trained. |
| U9 | Profile the FBS session, then a NEON kernel for its step, then the M5 laptop cost. | A per-value serving rate that can be extrapolated. | Serving speed becomes the binding constraint, with a profile saying where it goes. |

U1 to U3 come first because nothing downstream means anything until the prompt reaches the reply through a decoder that is the one served. U5 can run in parallel: it is a kernel change with its own instrument.

## Proposal for the owner's queue

This is only a proposal. No §3 constraint is relaxed here, and this page waits on no answer.

The multiplier-free rule (D11, CHARTER §3.6) has one measured cost: 4.3 times the energy, on an older dense model (stage 11). On the FBS runtime, its share of the estimated 5,000- to 6,000-fold per-value gap is unknown. If the owner wants that share as a number, a profile of the FBS session (U9) can report the time spent in table-emulated products.
