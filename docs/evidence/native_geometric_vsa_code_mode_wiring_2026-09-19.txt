Date: 2026-09-19
Executed by: Zed (agent), local M1 checkout /Users/casey.allard/uor-r4

WHY
  The routing measurement showed codes derived from the learned 120-root assignment (`root`)
  beat the fixed token-id hash (`fixed`) on every routing metric, replicated on two disjoint
  slices. D2 says a measured improvement must not remain an evaluation-only switch, so the mode
  must be declarable IN the artifact.

WHAT CHANGED
  1. `ExportedGeometricModel::vsa_code_mode: u8` (`#[serde(default)]`, so artifacts written
     before the field load as 0).
  2. The mode is stored in header byte 26, which is `_reserved[0]`. Header size, section count
     and section layout are unchanged, so the artifact format stays SIZE-COMPATIBLE: a mode-1
     artifact is byte-for-byte the same length as the mode-0 artifact it came from
     (verified: 963,950 -> 963,950 bytes). Both readers reject a mode other than 0 or 1.
  3. `ExportedGeometricModel::vsa_codebook()` returns the code space the declared mode implies;
     `prepare_vsa_code_mode()` performs the coherence rebuild. Both live in `learner/vsa_codes.rs`.
  4. The native API loaders (`load_prose_rgm`, `load_prose_json`) call `prepare_vsa_code_mode`
     after deserializing, and `from_prose_model` uses `model.vsa_codebook()` instead of
     constructing a fixed-hash codebook directly. An artifact whose stored centroids do not match
     its declared mode is therefore CORRECTED ON LOAD rather than silently incoherent.
  5. New tool `crates/uor-r4-core/src/bin/set-vsa-code-mode.rs` declares the mode and verifies
     the rebuild.
  6. The EXPORT path now declares mode 1 and builds the hierarchical codebook with the root
     codebook (`export_discrete`), so new artifacts are coherent by construction.

THE COHERENCE REQUIREMENT, AGAIN
  `HierarchicalCodebook` centroids are bundles of token vectors, so a code-space change without a
  matching rebuild would leave the router comparing a query against centroids from another space.
  This was checked structurally rather than assumed: the fine-cluster partition is derived from
  `root_tokens[r].chunks(LEAF_BUCKET_CAPACITY)` — token-order chunking — so it does NOT depend on
  the code space, and only `centroid`/`root_anchors` change. Verified empirically: 120 sectors and
  175 buckets in both spaces, with 960 of 960 anchor words differing.

WHAT THE END-TO-END CHECK ESTABLISHES, AND WHAT IT DOES NOT
  * ESTABLISHED: the mode is honoured by the serving path (the two artifacts produce different
    output), both load without error, and the declared-mode artifact reconstructs its routing
    codebook in the right space. Plumbing verified.
  * ESTABLISHED, weak quality signal: mode 1 reaches more distinct content before collapsing into
    the dominant n-gram loop ("...and said", "a little girl named Lily. She loved to play with
    her toys. One day, he saw a big, red ball") where mode 0 loops within a few sentences. Both
    still loop; this is one prompt, one sample, not a quality measurement.
  * NOT A SERVING CLAIM: the 94.7 -> 144.6 tok/s difference is a codebook-REPRESENTATION
    artefact, not a routing effect. Mode 0 uses `Codebook::on_demand` (every `get` regenerates
    64 words via SplitMix64) while mode 1's table is materialised by `from_vectors` and served by
    direct lookup. Debug build; single prompt; not a throughput result.
  * NOT MEASURED END TO END: served quality. The evidence for better routing is
    `shortlist-recall` on two disjoint slices (recall 8.4-8.8 % -> 10.7-11.2 %, shortlist BPB
    2.72-2.83 -> 2.67-2.78), not this CLI comparison.
