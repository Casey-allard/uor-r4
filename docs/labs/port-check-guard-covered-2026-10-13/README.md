## The history: I built this, measured it, found it wrong, and removed it

Two units ago I implemented this rule against **`ruleinventory::all_ids()` — the rules the *port* has
implemented** — while the rule must resolve against the rules the **engine** registers. Four real
lessons whose guards name a `prlint.*` gate were reported as *"not a rule this engine registers."*
**Rust said 4, Python said 0.**

**I removed the function and shipped the reasoning instead of a wrong check**, because *"a guard check
against an incomplete port is not a weaker check, it is a wrong one — it would tell authors to delete
guards on real rules."*

## And the fix repeated the mistake once

My first correction put the id set in a data file — generated from **`checkrules.rules()`**, which is
**40 ids.** The probe still read **4 findings.**

**Measured against Python:** its `_known_rule_ids()` returns **53**. The engine resolves guards from
**three sources**, not one:

| source | contribution |
|---|---|
| `checkrules.rules()` | 40 |
| each module's own `register_rules()` | 13 more |
| `prlint.GATE_RULES` | the gates raised against a **PR body** rather than against repo state |

**My data file took the first source and stopped — the same false positive, in a new place.**

**The lesson repeated exactly: I asked "what rules are registered" and answered with the first list I
found, twice, instead of reading the function that answers the question.** The second time I caught it
because the same probe that caught the first one still read 4.

## Why the extra 13 are not padding

**`prlint`'s gates are raised against a PR body, which the engine never has** — so they are declared as
data rather than registered as checks. **A lesson may still cite one as its guard**, and four do.
**Resolving guards from the check registry alone excludes precisely the guards a lesson is most likely
to name**, because the lessons are about how PRs are written.

## Limitations, stated

- **`check` still delegates.** Seven rules remain.
- **The id set is a snapshot, refreshed by hand.** A rule added to the engine and not to this file
  would make Rust report **a valid guard as unknown — a finding that is wrong rather than missing.**
  A test asserts the count so a drift fails loudly, **but nothing refreshes the file automatically.**
- **The file was generated by running Python's own `_known_rule_ids()`.** That is the right source and
  it is also a **one-way dependency**: when Python is retired, this file must be maintained by hand, or
  regenerated from Rust once Rust owns the rule registry.
- **Only `block` severity is checked**, matching Python. A `warn` lesson with a nonsense guard passes in
  both.
