## Evidence contract

The existing `CompletionPlan` gains optional `redirect` evidence. Absent evidence
serializes exactly as before, preserving historical K8 plan digests. K16 requires:

| Field | Contract |
|---|---|
| `schema` | `uor-r4.redirect-owner-release-plan/1` |
| `status` | `HELD_OWNER_ACTION_REQUIRED` |
| `scope` | One exact arm/seed scope above |
| `execution` | Exact source/PTX/geometry/executable/driver/config/lineage/sheet hashes; `base_source` is `2fa663b54`, `reviewed_source_commit` is the final full 40-character review head |
| `sheet` | Pinned redirect sheet carrying prospective TEST FITNESS: FIT |
| `pilot_parent` | `null` |
| `run_state_directory` | Absolute, disjoint from sealed evidence directories |
| `redirect.packet` | FilePin for the completed, measured D-Packet record |
| `redirect.qualification` | FilePin for the qualification index below |
| `redirect.pm_review` | FilePin for PM acceptance below |
| `claude_review` | Legacy wire-key retained; must equal `redirect.pm_review` for K16, not an assertion that Claude reviewed K16 |

The qualification index schema is `uor-r4.redirect-qualification/1` with
`scope`, `execution`, `packet_sha256`, and:

- `controls`: exactly six ordered `{id, status, receipt}` entries, C-R1 through
  C-R6, each `PASS`, with a nonempty digest-verified FilePin to the GPU receipt.
- `cuda_build`, `cuda_clippy`: nonempty FilePins to pod transcripts, with
  `cuda_build_exit` and `cuda_clippy_exit` both integer zero. The adopted step-0
  commands are `cargo build --features cuda` and
  `cargo clippy --features cuda --all-targets` for the actual qualification/timing
  executors, before any timing. Retain commands, manifests, toolchains and source
  heads in the transcripts. This laptop's host tests do not discharge that gate.
- `timing`: nonempty FilePin to the measured K16 timing record, not a historical
  K8 rate or an UNMEASURED placeholder.
- `initial_checkpoint`: FilePin to this configuration's zero-update
  `DriverCheckpoint` (the `init-corpus` output `report.json`).
- `initial_evaluation`: FilePin to its `eval-corpus` `report.json`. The validator
  checks zero epochs/updates, configuration/lineage/model bindings, recounts stored
  per-row observations against their aggregates and requires target-admitted rows
  >=4,894. This recount is metadata validation, not CPU model evaluation.

PM acceptance is a JSON record with `reviewer: Kimi`,
`verdict: APPROVE_K16_REDIRECT_QUALIFIED_ADMISSION`, exact `scope` and `execution`,
`qualification_sha256`, `packet_sha256`, and the GitHub comment URLs
`exact_source_review` (the dispatched review) and `receipt_url` (PM acceptance).
It binds the completed packet, actual timing and all qualification records to the
final execution identities. A lab must not fabricate this acceptance. The reader
checks file integrity and declared metadata; it does **not** prove a GPU ran,
authenticate GitHub identities, parse compiler transcripts, or independently
judge the timing/fixture instrument. PM reviews those pinned records before
attesting. Labels/empty scaffolds are not evidence.

On the CUDA execution path, the actual fresh initialization and evaluation must
equal the qualified checkpoint-zero artifacts before an update capability is
issued. Both K16 seeds get stored baseline authentication; historical K8 seed1
continues to use its original archived baseline. The driver's source identity
includes the new validator module, so earlier driver lineage/release pins cannot
silently carry across this change.

owner-release file.

directly. [PM has been asked](https://github.com/UOR-Foundation/uor-r4/issues/2029#issuecomment-6202504373)

no-manual-operation requirement. That policy/interface dependency remains open;
this PR does not claim to make that comment an executable capability or ask the
owner to perform manual git/tool steps. Qualification and training admission
remain distinct, and neither FIT nor source approval bypasses missing evidence.
