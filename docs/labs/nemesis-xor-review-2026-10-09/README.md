| Page 1, `hammingWeight` and `hammingDistance` | Correct mathematical definitions of population count and unequal-coordinate count for a fixed 256-bit vector. | `Core256`, its operations, imports and Lean version are absent. | Page 1, `divergenceVector` | Exactly identifies which encoded bits changed; XOR is symmetric. | It does not encode directed geometric transport, evolutionary cause, semantic difference or a signed displacement without further structure. |
| Page 1, `transformationalCost` | Hamming count is shortest-path length on the unrestricted cube graph with unit-cost single-bit edges. | Arbitrary Store states can restrict legal vertices/edges, require unequal costs or retain information outside `core`. It is not a runtime/energy/training-cost measure. |
| Pages 1–2, `isCompositionalPath` | Defines membership in a Hamming geodesic interval. | No composer theorem, E8 map, icosian witness or geometric compatibility is given. The predicate can be false for the purported composition. |

There is also a concrete Lean interface question: current official `BitVec.getLsb` accepts a `Fin w`, whereas `List.range 256` supplies natural numbers. If `Core256` is the ordinary `BitVec 256`, the displayed fold needs a bounded-index construction or the total Nat-indexed accessor, unless omitted project definitions provide an adapter. It is therefore **compile UNVERIFIED**, not a confirmed repaired Lean implementation. This is a source-compatibility concern, not an executed compile failure. [Official Lean bitvector API](https://lean-lang.org/doc/reference/latest/Basic-Types/Bitvectors/).

For an arbitrary extraction `E : Store → {0,1}^256`, the pullback `d(s,t)=Hamming(E(s),E(t))` is generally a **pseudometric**. Identity of indiscernibles holds only when E is injective on the admitted state domain, or when Store is explicitly quotiented by equal codes. Distinct occurrence/version/fiber states must not silently become one identity because their core matches.

The interval condition has a simple exact characterization: every coordinate where a and b agree must have that same value in c. Equivalently, `(a XOR c) AND (b XOR c) = 0`. If a and b differ in d coordinates, there are `2^d` interval vertices; either endpoint always qualifies. This is neither a unique midpoint nor an algebraic ligature theorem. A direct counterexample to interpreting XOR composition as interval interpolation is `a=b=1`, `c=a XOR b=0`: both legs have length 1 while the endpoint distance is 0. The same example embeds in 256 bits. Conversely any interval point can be placed on some cube shortest path, but that path can leave the set of legal geometric states.

The routing function receives the target only for comparison; its displayed `route current` method does not receive the target. A route independent of target cannot strictly improve toward every arbitrary target: choosing target=current already gives distance zero. If an actual target-conditioned legal route strictly decreases an integer Hamming potential every step, termination within at most 256 decreases follows. Reaching the intended Store state still needs injectivity and a no-stall/completeness argument. Legal geometric routing can require temporary distance increases, so the proposed condition can reject valid routes.

## Why Boolean geometry is not yet the project's R4 geometry

The Fano plane organizes seven imaginary octonion units with oriented multiplication. That orientation determines signs: swapping operands can change the sign, and octonion multiplication is not associative. XOR alone is commutative and associative. Binary labels can encode part of a multiplication-table index, but multiplication still needs the sign/orientation law. The paper does not define that bridge. [Baez, The Fano Plane](https://math.ucr.edu/home/baez/octonions/node4.html).

For unit quaternions interpreted as SO(3) rotations, q and −q represent the same rotation; a retained spin state can distinguish them. Accordingly a rotation metric, signed-spin metric, hemisphere code and exact occurrence identity have different equivalence relations. The PDF does not specify which one its antipode is meant to preserve. [Baez, The Octonions, introduction](https://math.ucr.edu/home/baez/octonions/node1.html).

UOR-R4's concrete icosian construction retains exact `Z[phi]` coordinates, golden/Galois companion, glue, maps and orientation. It is not an independent second arbitrary quaternion nor simply a Boolean cube. Its [profile fields](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/canonical_lexical_ingestion.rs#L986) include the basis order, glue parity, conjugation, norm relation, shell, forward and inverse maps. Its [anchor compiler](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/anchors.rs#L28) retains the phi-Galois companion and signed chirality/cosine polarity. The PDF's two-page excerpt supplies none of these witnesses.

A 256-bit representation can be useful, but its bit meanings must be fixed. Hamming on arbitrary numeric root indices changes under relabeling. Hamming on cryptographic identities does not acquire semantic meaning. Hamming on signed geometric predicates has a defined relation to geometry; Hamming on learned features needs measured task relevance. Combining these into a universal core without type separation would erase the very distinctions the current model must preserve.

## What is already implemented

**Artifact-bound Hamming geometry already exists.** [Metric source](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/hamming_refinement/metric.rs#L1) explicitly uses geometry predicates, not hash identity. It binds 120 roots to two-word signatures, rejects padding, evaluates XOR/popcount at line 66 and concatenates two ordered root lanes at lines 69–72. It is 120 useful bits per root and 240 per two-lane comparison, not a new 256-bit state algebra.

The [signature construction](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/addressed_attention/artifact.rs#L101) evaluates strict positive signed ranks against all 120 landmarks. This is an actual encoding contract. The retained [geometry census](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/docs/native_geometric_hamming_refinement_973.md#L31) reports 120 distinct signatures, no root collisions, 45 set bits each and 856,800 single-root ranking comparisons without angular preference/tie disagreements. Opposite roots have distance **90, not 120**. Zero-valued landmark predicates mean their signatures are not complements. Blind bitwise NOT has 75 set bits and therefore is not one of these 45-set-bit admitted codes.

This census is retained published evidence, not a new rerun. It establishes single-root ordering compatibility on that codebook. It does not establish equal angular/Hamming softmax weights, equal sums across varying lanes, semantic relevance, faster serving or improved language. Repeating that census would not advance the programme unless the encoding changes.

**Repeated contextual reads already exist as a bounded experimental path.** [Refinement runtime](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/hamming_refinement/runtime.rs#L210) binds geometry, immutable committed memory/frontier and policy, then scans at most 256 occurrences, eight results and Null per hop. It preserves exact leases and group updates before subsequent queries. [Policy packing](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/hamming_policy/policy.rs#L245) excludes expected answers and identity/hash bits; [decoding](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/crates/uor-r4-core/src/native_geometric/hamming_policy/policy.rs#L445) uses nearest signature XOR/popcount. This realizes much of the document's inexpensive distance machinery while retaining legal native roots.

Availability is not accepted-path activation. These modules are used by historical/experimental adaptive, relational and dependent-language paths. Their [policy record](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/docs/native_geometric_hamming_policy_973.md#L3) explicitly reports initialized language unqualified, 0/24 complete answers without a learning fit, and unfinished normal artifact dispatch/full paired-H4 transport. The current Source/Prefix/Generate learner does not invoke a PDF-style Core256/Fano routing primitive. Do not turn broad module existence into a current 8/512 mechanism claim.

## Useful additions and consolidation

1. Keep exact identities, signed geometric state, geometric relevance signatures and learned emission scores as separate types. If a 256-bit container is needed for a specific binary signature, specify meaningful/padding bits and artifact identity; do not create a universal Core256 solely to match the PDF.
2. Reuse the existing XOR/popcount implementation and its encoding/census contracts. Consolidate duplicated helpers only where their width, padding, null/tie rules and geometry provenance genuinely agree. Do not merge exact address equality with approximate distance or collapse directed H4 transport to symmetric Hamming.
3. The document's interval predicate could become an optional offline diagnostic with the accurate name “Hamming interval membership.” To use it as a composer invariant, first state which admitted composition is expected to satisfy it and prove that property on that domain. Retain counterexamples rather than enforcing it on all icosian compositions.
4. Rename/describe the routing predicate as one-step Hamming descent. A future legal routing mechanism needs explicit target-dependent actions, retained signed/fiber state, admitted edges and termination/coverage conditions. The paper alone does not justify a new Fano route operator.
5. A small standalone Lean reference could formalize the bitstring identities after its definitions/import/version are supplied. Rust remains the runtime/training implementation; a formal bit lemma is not a language milestone. No new Lean dependency is necessary for the current mission.

D11 permits bounded XOR/popcount/table/additive kernels, but compatibility is only a necessary engineering condition. The [serving contract](https://github.com/UOR-Foundation/uor-r4/blob/27f89a6cf7c216e98a5afef4aaf514eab5aa325d/docs/integration/DECISIONS.md#L410) additionally forbids served float/multiplier/divider paths, treats dense weight reads as interim, excludes a transformer backbone and requires measured energy claims. A functional 256-element fold does not establish allocation-free runtime, latency or energy advantage.

## Prioritized falsifiable decision

The minimal PDF-specific question is **encoding compatibility**, not a new fit: using the already bound codebook/retained census, document which distinctions its Hamming representation preserves and whether a proposed state-level encoding loses direction, signed spin/fiber or occurrence identity. Reuse existing results; do not rerun the unchanged 120-root census. If a genuinely new typed encoding is proposed, a bounded source/fixture check should expose collisions, complement closure, admitted transition legality and agreement/disagreement with the specific existing geometric relation. Collision or wrong antipode rejects that encoding; numerical agreement alone grants no semantic or language claim. There is no reason to launch GPU training for this two-page sketch.

The next experiment that can change the **current learning decision** is the already evidence-supported protected-constraint-aware joint quantized transaction from the original selected parent. Form directions using mechanically selected protected violations or winner margins over the complete population, not named token keys. Preserve the complete 15-position episode including EOS, 17 reference roles, all 380 original guard winners, source-bound donor/Generate coupling and exact integer alias reducer. Freeze the finite policy before execution; neither increase the unchanged radius sweep nor weaken guards.

Its decisive outcomes are: (a) a protected native transaction offers and commits corrections unavailable to the four rejected vectors, supporting the changed direction mechanism; (b) projected directions eliminate task improvement, showing a bounded local task/protection conflict for that policy; (c) relaxed utility predicts improvement but a native donor/post change invalidates it, exposing a concrete coupling/discretization defect. None establishes global geometric capacity or useful conversation. A construction-positive result still needs immediate actual-artifact own-feedback qualification and retained complete replies before promotion.

This review itself required source/PDF reading only, small local rendered images and this report. A proposed encoding fixture is a bounded CPU task, not GPU/model work. The learning successor must receive its own complete cost projection; the latest measured 301-second supervised model run, roughly 173-second scoped build and separately charged comparison are relevant anchors, not guaranteed future costs. Keep existing GPU/RAM/disk caps, count preparation/reviews/retries/preservation, and avoid a separate full historical audit or proof campaign.

**Recommendation:** preserve this advisory on main as research material, reuse its valid Boolean definitions where the existing typed encoding warrants them, and continue the source-supported protected learning correction. Do not replace native transport or exact addressed memory with a universal Hamming core, adopt complement as geometric antipode, or interpret one-step distance descent as semantic routing success.
