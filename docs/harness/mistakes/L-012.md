## What happened

D22 requires every mechanism pre-registration to carry a `TEST FITNESS: FIT` review on its
milestone **before compute**, and the M1 cycle-8 product-key run was reviewed as
`TEST FITNESS: NOT FIT` and re-registered with a no-memory control, a memory-off
evaluation of each checkpoint, a longer fine-tune and a fresh held-out set. The operator
phase of 12 October then had to record that **no current training configuration is
compliant** and that rung 0 waits for FIT, because the replacements (a geometric gate, a
matmul-free head) did not exist yet. The rule existed before either case; what did not
exist was anything that read a PR body and asked where the bar came from.

## Symptom

A PR reports model numbers and the pre-registration, if it exists at all, is linked from
the same PR after the run. Or a bar is quoted that was chosen once the numbers were known.
Or GPU time is spent on a configuration that the rules already exclude.

## Lesson

The pre-registration is the bar, the base artifact, the data split, the steps, the stop
rule and the cost - posted on the milestone issue before the run starts, and reviewed as
FIT. Bars are never narrower than the panel's noise, and they are frozen before the draw.
A configuration that the rules exclude does not get a run, and a comparison whose baseline
they forbid does not get a run either.

## How to apply

- Write the sheet first: `uor-harness prep new -m <milestone>`; then get
  `TEST FITNESS: FIT` recorded on the issue (`prep fit -m <milestone> --verdict FIT`).
- Cite it in the PR body: `Prereg: #issuecomment-<id>` or `TEST FITNESS: FIT`. A body that
  reports numbers without one fails `prlint.prereg_before_compute`.
- Keep the panel and its noise fixed: `uor-harness panel show -m <m>`.
- If the run is already done, record it as unpromoted and re-register the next one; do not
  back-date the bar.
