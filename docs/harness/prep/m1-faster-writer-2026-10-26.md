## 1. Why

`writer` ([`crates/uor-r4-discrete/src/discrete.cu`](../../../crates/uor-r4-discrete/src/discrete.cu) lines 307–345) chooses among the members of `K` admitted address cells, but finds them by scanning the full vocabulary on every row:
- `:309` calls `token_cell` (`:286-290`) on every token `0..V` to mark cell occupancy; any `ABSENT` cell returns `~(W)0` (`MAX`);
- `:311` calls `token_cell` once more for `target_cell`;
- `:313-325`: for each of up to `K = s[3]` admission passes, it evaluates `cell_distance` (`address_distance` in `s[15] == 0` outer-L1 mode) on every occupied, unused cell under `cell_precedes_w` (`:301-303`), then scans all `V` tokens again with `token_cell(t) == cell` (`:319`) and evaluates `token_distance` on members of `cell`.

Per row (`s[15] == 0`), the full scan performs `V + 1 + A * V` `token_cell` calls (`36,865` at `V = 4,096, A = K = 8`; `69,633` at `V = 4,096, A = K = 16`; `147,457` at `V = 16,384, A = K = 8`) plus up to `K * 256` cell-distance evaluations in the admission loop. Replacing the full-vocabulary scan with a 256-cell CSR bucket index reduces per-row `token_cell` calls to `0` (`1` under a virtual `kind == 1` move) and cell-distance admission evaluations to `256`, unblocking `#2887` (`r-vocab-4096-vs-16384`).

## 2. What changes

One new ahead-of-time compiled CUDA module (`bucket.ptx` / `bucket.cubin`), generated by [`crates/uor-r4-discrete/src/bucket_source.rs`](../../../crates/uor-r4-discrete/src/bucket_source.rs) and wrapped by [`crates/uor-r4-discrete/src/writer_bucket_device.rs`](../../../crates/uor-r4-discrete/src/writer_bucket_device.rs). It indexes the codebook by the 256 root-pair address cells (`cell = root(block 0) * 16 + root(block B - 1)`).

- **Index (`BucketIndexDevice` / `BucketIndexSnapshot`).** `offsets[0..=256]`, `members[0..V)` (token IDs grouped by cell, strictly ascending token ID within each cell), `cells[0..V)` (each token's base cell or `ABSENT`), and `absent_count[0..1)`. Built on the GPU by `discrete_bucket_build`.
- **Incremental update (`discrete_bucket_update`).** After each accepted token-block move (`discrete_apply`, `:431`), at most one token changes cell. `discrete_bucket_update` recomputes `token_cell` for `moved_token` only, updates `offsets`, `members`, `cells`, and `absent_count` in place on the GPU while preserving ascending token ID order within every bucket, and writes `entries_written` (`<= 2 * V + 258`). A fresh `discrete_bucket_build` is the exactness control after every step (§5).
- **Bucketed writer (`bucket_writer`).** In `s[15] == 0` (`OuterL1V1`), occupancy is `count[c] > 0` where `count[c] = offsets[c + 1] - offsets[c]` (adjusted by `±1` for `moved_token` when `kind == 1 && candidate != 0`). Admission evaluates `address_distance` once for each of the 256 cells (`cell_distance_evals = 256`) and selects up to `K` occupied cells in `(address_distance, cell_id)` order. Membership walks only the admitted buckets' CSR spans `offsets[cell]..offsets[cell + 1]` (skipping `moved_token` in its base cell and including it in `moved_cell` when `kind == 1`), applying the exact tie-break `(d < best_distance) || (d == best_distance && token < best_token)`.
- **Target `ad` and telemetry accounting.** At `discrete.cu:326`, target `ad = distance[target_cell]` reuses the precomputed `distance[256]` array from the 256-cell admission pass (`0` extra `cell_distance` calls). The rank-telemetry loop (`discrete.cu:330-333`) also reuses `distance[c]` in `bucket_writer`.
- **Both `IdOrder` and `ServingPruned` walks tested on GPU.** `discrete_bucket_writer_eval` supports both `WALK_ID_ORDER (0)` (full loss, rival, telemetry, and `top8` parity with `discrete.cu`) and `WALK_SERVING_PRUNED (1)` (admitted buckets walked in admission order, skipping any bucket with `distance[cell] > best_distance`; exact `prediction`, `admitted_cells`, and `address_rivals` parity with `discrete.cu`).
- **Build.** [`crates/uor-r4-discrete/build.rs`](../../../crates/uor-r4-discrete/build.rs) compiles `bucket.cu` with `nvcc -ptx -std=c++17 -arch=compute_120`, admits the 7-entry PTX via `admit_ptx_inventory(&bucket_source::ENTRIES)`, and assembles `bucket.cubin` + `bucket-resources.txt`. Ordinary `discrete.ptx`, `ordinary.cubin`, and `driver_source_sha256` (`04c5165464a18eea6d4edadc6970007dbdc7908ead420f4a2f575e22ea43061d`) remain unchanged.

## 8. Controls and negatives

All four planted faults in `run_planted_fault_controls` (`writer_bucket_qualification.rs`) execute on the GPU via `discrete_bucket_writer_eval` against `discrete_fullscan_writer_eval` and must each be caught (`mismatches_detected > 0`):
1. `FAULT_STALE_BUCKET (1)` (`stale_bucket_after_move`): under a cell-crossing move `kind == 1`, bucket occupancy ignores the move;
2. `FAULT_REVERSED_TIE (2)` (`reversed_tie_break`): equal-distance cell and token ties prefer the larger ID instead of the smaller ID;
3. `FAULT_OVER_PRUNED (3)` (`over_aggressive_serving_prune`): `ServingPruned` skips an admitted cell when `distance[cell] >= best_distance` instead of `> best_distance` on a cross-cell token tie;
4. `FAULT_CORRUPTED_CSR (4)` (`corrupted_csr_offset`): each bucket's CSR end offset `offsets[cell + 1]` is decremented by `1`, dropping the last member of the bucket.

Any planted fault that passes undetected (`mismatches_detected == 0`) fails `B3` and aborts the qualification.
