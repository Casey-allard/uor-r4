## Verdict

The programme has a coherent research direction and a useful staged distinction between attention, correctness, reasoning, durable integration, optimization, formal closure and release. It is **not yet a complete executable plan to a local frontier reasoning/coding product**. The principal missing work is the explicit handoff from the current learned, dense, supplied-clause binding reference into general language/context behavior, a native service, and finally the promised integer/table serving kernel. Coding and agent workflow capability also have no active named acceptance lane.

The right response is to preserve #1079 and its next diagnostic, add explicit intermediate contracts and owners, and separate product-interface work from claims that the final model is ready. Do not treat the donor workbench, provider-free operation, full prediction preservation, a closed issue, or a long proof vocabulary as a substitute for those handoffs.

## Proposed sequence and exact issue amendments

### 1. Preserve and name the immediate scientific action

Create one proposed #973 child for the construction-only attention-weighted token exposure diagnostic, linked to #1079's exact artifact/control and latest completion comment. Its contract should declare only descriptive measurements, immutable population and a report that discriminates exposure/cancellation/tolerance; it should not tune the control, fit, score development or expand geometry. Keep #973 open and #954 blocked.

### 2. Reconcile the current authority without erasing history

Append a compact native #973 scope amendment outside its body if necessary, and update only its tiny pointer. For #820 and current planning mirrors, a suitable current statement is:

> The active scientific reference is the frozen #1077 learned interface and #1073 binding core preserved through #1079 R4 transport. Preservation passed; token-control strong sensitivity remains limited. The next owned step is the separately frozen construction-only exposure diagnostic. General language/context transfer, final-kernel lowering, correctness, reasoning, coding, multi-turn product behavior and release remain unqualified. Historical route-loop results remain retained evidence and are not automatically the artifact consumed by the new path.

Then explicitly identify the still-unmet #973→#954 consumer condition and the artifact/state schema that will satisfy it. Any change from the original higher-scope/source-free terminal must be a visible native decision, not an inference from a child PASS. Mark dated earlier “current/next” sections as historical. Keep measurement records append-only.

### 3. Add the missing interface and artifact bridge lane

Propose a product-interface parent under #820, with small child deliveries for:

- same-origin Rust service + modular web shell + explicit model/capability discovery;
- one actual supported operation with truthful result/error/stop semantics;
- model/artifact lifecycle, load/cancel/progress/cache identity;
- later native export/loader/parity for the accepted learned path, when its input/state contract is frozen;
- workspace/editor/diff/save and isolated preview;
- deliberate issue/worktree/PR workflow through the same local backend or harness.

The first shell/API tasks can proceed in parallel with #973 because they need no new model or claim. Native inference integration depends on the selected artifact; the final #962 remains blocked by correctness/reasoning and its own memory contract. The first port issue should copy selected UI components and attribution, not replace the Rust engine with donor code or ship the donor's model aliases.

### 4. Explicitly gate capability growth and final representation

After the diagnostic's interpretation, #973 should own separately frozen language/context generalization successors with independent data and one changed limitation per step. A new lowering/compilation child or lane should name how the accepted dense reference can become the intended no-dense/no-softmax serving kernel, with behavioral and cost criteria. Lowering cannot be inferred from gauge preservation and should not be attempted merely to satisfy a product label.

Once the declared #973 terminal is met, retain #954 for grounded facts, contradiction and abstention, then #955 for checkable multi-step composition. Amend their consumer references to the actual accepted artifact/schema so every inference step names the runtime it invokes. Their existing tiny probes are useful entry gates, not frontier-level completion evidence.

### 5. Add coding and operational evidence explicitly

Propose a coding-capability lane linked to #955 and the product/workspace interface. It should progress from single-file executable tasks to multi-file repository changes and controlled tool loops, with independently checkable outcomes, stable task identity, context provenance and regression preservation. Tool execution/harness engineering can be built before a model is a competent coder; keep that distinction in status and acceptance.

Define #962's identity-scoped memory operations and user-visible persistence/forget semantics. Importing historical Claude/Gemini/Codex conversations into a project knowledge base is useful provenance/retrieval work; it is not training, correctness or proof that model memory is load-bearing. Provider history and generated conclusions should remain distinguishable, with source paths/hashes and project boundaries.

### 6. Close cost, proof and release against the implemented product

Amend #963 to profile the actual deployed path rather than prescribe an immutable worker count. Keep #964 as the final artifact/operation closure, fed by a maintained obligation matrix. Amend #965 with a concrete product capability matrix and the exact deployment/API/install/rollback contract; activate only its named release checks. Keep #940 as separate administrator governance work. A product should not claim frontier capability until the declared task/resource comparison has actually been observed.
