# UOR-R4 Charter

Adopted 19 October 2026 by the owner (Casey), at checkpoint 1 of the repository renormalization; replaces the stacked directions formerly in AGENTS.md and D0–D41.

Old text moves byte-identical to `archive/`. Bracketed ids are sources.

## 1. Mission

Build the **UOR-R4 Geometric Language Model**: a fast language model that is not a transformer. It predicts text with geometry (prime addresses, zeta phases, E8/H4/icosian rotations, SpiralCore/FBS routing) and exact memory, on an ordinary laptop or in a browser. Conversation with durable memory first, then coding and reasoning, on one model [AGENTS:mode, D19, AGENTS:both-lines]. Pre-alpha; no capability is established.

The owner's rule: **"USE GEOMETRY. THAT IS THE END OF IT. NEVER USE ANYTHING ELSE."** [OWNER:0]

The owner's goal behind every ban (18 Oct, verbatim): *"my goal with all of these bans is to ban expensive operations and to always optimize for what is best for the project goal... fast local ai that can train fast and run fast and reach almost frontier level capability ... we have so many mechanisms, at this point we just need to stitch the right ones together and optimize all of the things that aren't, which will likely be found in the details"* [OWNER:26, D37]. When unclear, choose what trains and serves fastest locally on the geometric path, and write it down [D37:why-bans]. **The lead metric is tokens per second** (decode, and context separately); a small quality gap is acceptable [OWNER:5].

## 2. Products

1. **Model:** the geometric model, exported as one D11 integer/table artifact; built in `crates/uor-r4-discrete`, served by `crates/uor-r4-integer` [AGENTS:ownership].
2. **Web client:** the Studio at `/studio` on the mdBook site, running the integer model locally in the browser as WASM [renorm decision 7, D36].
3. **Desktop client:** a Tauri app sharing the web UI, the native integer model with D19 memory, offline, on M1-class laptops; spec only [renorm decision 8].
4. **Legacy crates are repaired, not archived:** `uor-r4-graph-compiler`, `uor-r4-graph-certify`, `uor-r4-api`, `uor-r4-proof-model` and the root crate are repaired to build on the current core; repairing restores the build only, and their mechanisms (r4g1-graph, native-geometric) stay PARKED. [D36, owner 19 Oct]

## 3. Technical constraints

1. **Geometry only.** Every mechanism, training signal and fix comes from the project's geometry; keep R4/S3, Hopf and paired-H4/icosian roles distinct (E8 = H4 ⊕ φH4, fixed). Flock reads use local rules (~7 nearest neighbours), not a dense teacher. *Why:* the bet is that geometry replaces expensive dense operations. [OWNER:0, OWNER:6, D20, D32:hamming-one-factor, AGENTS:typed-geometry, AGENTS:e8-shorthand]
2. **No squashing functions.** No softmax, log-softmax, cross-entropy (implicit softmax), softplus, sigmoid, tanh, GELU or normalized exponential, anywhere: runtime, losses, gradients, sampling, teachers, surrogates, comparators, including renamed or table forms. *Why:* they are expensive and hide a dense global normalization. [D23, D25, OWNER:1, HR:no-squash]
3. **No matmul.** No dense matrix multiplication or GEMM anywhere: training, evaluation, instruments, serving and tooling, including wrappers and hand loops. A geometric feed-forward block (Hamilton gate and projections) is allowed; a dense MLP is not. *Why:* matmul is the cost the project exists to remove. [D25:no-matmul-anywhere, D30, OWNER:2, OWNER:14, HR:no-matmul]
4. **Presence counts.** Banned code may not exist in any compiled or loaded module or vendor path; NVRTC is banned; CUDA is prebuilt by nvcc. Ahead-of-time nvcc kernel builds run on the GPU pod (authorized by D30); the laptop runs CPU-only builds and static checks. The ratchets `uor-harness ratchet d23|d25` only go down. *Why:* code that is present eventually runs. [D29, R5, OWNER:no-nvrtc, HR:banned-module]
5. **Research compute is GPU-only.** Training, evaluation, qualification, and model and parity reference execution run on the GPU; a host fallback is a defect to fix with a kernel. Spend GPU only where a run can change a decision. *Why:* host runs gave wrong timing and wrong evidence, and the GPU is where the speed is. [D24, OWNER:4, OWNER:20, HR:gpu-only]
6. **Serving is integer, on the user's device.** The exported artifact has no float, transcendental, multiplier or integer-divide instruction (D11 R1–R5); the frozen runtime does no steady-state allocation, and a dense model disguised as lookup tables is excluded. Serving it on client devices (CPU, browser WASM, Apple silicon), including measuring tokens/s and energy, is the product and is allowed; D24 does not apply, and D36's browser-as-CPU clause is replaced. Panel scoring, qualification and milestone evaluation of an exported artifact remain GPU research compute (§3.5); only product serving, and measuring its tokens/s and energy, run on client devices. *Why:* the product is fast local AI on ordinary hardware. [D11, D36, D39:float-horizon, HR:serving-integer, AGENTS:frozen-tla; owner 19 Oct]
7. **Float only offline, with an export gap.** Float forward, gradients and optimizers are legal offline, in a separately scanned module, never in the discrete crate. Every float candidate reports its export gap on the same evaluator; a gap above the two-seed noise band disqualifies it. The D32 discrete path stays active; its qualification uses exact arithmetic. *Why:* float trains faster; only the integer artifact ships. [D37, D39:export-gap, R13, HR:float-offline, KIMI:d37]
8. **Zeta exception.** Float is allowed on the complex plane for zeta-zero parts, prime log-phases and the C4→R4/C8→R8 phase maps; everything downstream is discrete. *Why:* zeta phases are complex numbers by nature, and the bans target expensive operations, not geometry. [D32:zeta-exception]
9. **Efficiency is measured.** Report sparse access, bytes/token, bounded candidates, multiplier-free kernels and exact memory together, naming D5-a (residency) or D5-b (per-token sparsity, the end state). *Why:* unmeasured efficiency is not efficiency. [I1-I5, D5, D38]
10. **No neural comparisons** (comparators, controls, teachers, graders) until the owner says the model works end to end; panels are graded deterministically. Sole exception: D41's one-time `distill-d1` donor pass, on its binding conditions: the student consumes hard targets only (no logits, probabilities or distributions), the donor never executes in student preparation, training, evaluation, serving, grading or any panel, a generation receipt is bound at generation, and an owner release (§5.1) is required at dispatch. *Why:* a neural comparator would hide a dense model behind the geometry, against geometry only. [D28, OWNER:memory-no-transformer, D41]
11. **Rust first**, building on the uor-foundation crates; Python only where Rust cannot; no ad-hoc scripts. *Why:* one fast, checked language keeps training and serving on the same geometric path. [D27, OWNER:20, HR:rust-default]
12. **Exact identity stays separate from geometric address**; one shared vector writer serves input, carry and output; every artifact binds its data, seed, config, parameters and format. *Why:* one representation avoids translation costs, and exact identity cannot be recovered from a geometric address. [POLICY:shared-vectors, AGENTS:shared-vector, AGENTS:artifact-determinism]
13. **Hygiene:** `Result` errors at library boundaries; no unwrap/expect/panic on recoverable paths; keep `forbid(unsafe_code)` in portable runtime and format crates; no committed binaries, corpora or secrets; never read or print API keys. *Why:* hygiene keeps the repository small and fast to clone, and keeps keys out of it. [AGENTS:errors, HR:no-artifacts, HR:no-credentials, AGENTS:no-keys]

## 4. Evidence

1. **A negative closes a configuration, never a mechanism.** Mechanism statuses are **ACTIVE** (on the model path), **READY** (built and tested, not yet trained in) and **PARKED** (failed or broke a rule; reopen conditions listed). There is no terminal status. Stopping a mechanism needs the owner. [D22, D12, D2, POLICY:gates-promote, renorm decision 5]
2. **Instrument first.** Classify a failing check as instrument or mechanism before calling anything; an instrument defect is a fix, never a negative. No target is set from a vacuous instrument; no single number rules out a line. [D31, R12, R14, D39:gcap]
3. **Power.** Decisive runs use ≥ 2 seeds or ≥ 200 fresh rows, with bars no narrower than measured noise, the mechanism trained in, and a fresh transfer number with every development gain. [D22:power, D22:transfer, D17]
4. **Controls and progress.** Compare against lawful non-neural baselines (count tables). After three results on a line that do not move its headline, write a pivot note: stop, or one decisive run. [D21, D6, D9, POLICY:progress-control]
5. **Pre-register only where it decides spend.** A one-page sheet (bar, noise, controls, seeds, cost, what each outcome decides) with a non-author FIT review is required only before GPU training or evaluation, and before any run a milestone claim rests on. A fresh-context subagent counts as non-author. Builds, finite kernel tests and host checks need no sheet. Archived float sheets return only as new sheets with a fresh FIT. [R4, D37:archived-sheets, AGENTS:mech-briefs; owner 19 Oct]
6. **Claims.** "Measured X on Y against Z"; label proof, measurement, hypothesis; NOT_RUN is not PASS; tests are not trained capability. [HR:claims, POLICY:evidence, AGENTS:invariant-formal, PROTO:status-vocab]
7. **Preserve.** Nothing is deleted: negatives, unique source and other labs' work go to the archive byte-identical. [R6, HR:archive]
8. **M1 closing bar.** Bar (d) is replaced, for M1: integer top-1 through the D11 export, on each of two seeds, beats both the unigram table (1,226/14,287) and the T2 successor table (6,300/14,287) on the same DEV panel, with tokens/s reported. BPB returns as a later milestone bar once a lawful likelihood exists. Bars (a), (b), (c) and (e) are unchanged. [D39, owner 19 Oct]

## 5. Workflow

1. **The owner sets** this charter, §3 and the GPU caps. This record does not change §3, so D41's donor pass still needs his release at dispatch (§3.10). Nothing else waits on the owner: "in theory the project structure should be build in the github issues so there should not be a point where anything is waiting on my decision" [owner 24 Oct, D65, D69]. **Every step is one a single lab can finish alone.** Other labs and the owner can speed work up or reverse it, never hold it, and no step posts a question and waits for the answer: "if there was only one single lab running what would the process be? a single lab can't park and wait for another lab or me to review"; "Posting and waiting for an answer is where we lose" [D65]. A GPU or training run, held work included (Training, M2, Stage B), goes ahead when the lab's own pre-run review passes (§5.10), inside the caps of §5.4 [D67]. A bar, status, scope fix, classification or stop rule goes ahead when the lab's own decision review passes [D68]. Each review reads the whole project before it approves: "make sure before the decisions are made that the entire project is understood and that we understand from a whole project context what this step is for and what it is achieving and that it makes sense to do it - do not approve without larger context". The owner's queue is a log of the runs and decisions made on the owner's behalf, each with its review record and open to reversal; a lab that needs this charter, §3 or a cap changed proposes it there and goes on with other work [D69]. Casey's words beat written acceptance text; record directions verbatim the same day [OWNER:9, OWNER:10, OWNER:11].
2. **Coordination.** GitHub `main` is the single source of truth [PROTO:github-authority]. The owner plus one PM seat: Kimi, with a cover lab named by the owner when Kimi is offline; the owner is the last fallback when Kimi and the cover lab are both offline [owner 20 Oct, D52]. The PM sequences work and keeps `NOW.md` (with the roster) and operating notes that may not contradict this charter. The D14 council is retired [OWNER:21, OWNER:28, OWNER:32, R7, R9, R11, D14; owner 19 Oct]. **Subagents never make critical decisions:** a change to a bar, status, scope or stop rule is a decision card that the lab's top session approves only after its own decision review passes (§5.1, D68), and a change to §3 or a cap is a proposal in the owner's queue; subagents review, test adversarially and research [OWNER:26]. No lab waits on the PM: an ask the PM has not answered becomes the asking lab's own decision review [D65].
3. **Labs self-direct from `NOW.md`:** pick work, post a one-line intent note, claim the branch, continue unless redirected [D39:self-direction, R1]. Every piece of work has a roadmap issue before it starts: the gaps live as one file each in `docs/roadmap/items/`, `cargo xtask roadmap sync` turns them into issues, a newly found gap is a new item file in a PR, and the PM runs sync and render weekly ([docs/roadmap/](docs/roadmap/README.md)) [owner 20 Oct]. Set `UOR_LAB`; the harness is the shared view with automatic presence and no manual heartbeat cadence; claims record the charter version, with no `adopt_policy` hold [AGENTS:uor-lab, R3, PROTO:cadence, PROTO:versioned-authority; owner 19 Oct]. The harness freeze is lifted entirely [owner 20 Oct, D51]. Every lab tags its claims, PRs, reviews and comments with its lab name; other labs leave tagged work alone unless it is stale or needs help [owner 20 Oct, D55]. Outsiders skip the harness; a maintainer runs gates [OUT:no-harness]. Outsiders may run GPU steps on their own GPU, never a CPU, with the hardware specs attached to the PR; when the hardware is not equivalent to the project baseline (an RTX 5090), a maintainer re-runs the step under the same FIT after the PR [owner 20 Oct].
4. **Compute:** pods only through `scripts/pod/uor-pod`; Vast.ai default, Runpod emergency backup; at most 4 pods and $8/h across all labs; lease what you use; never touch another session's GPU or files; never cancel a healthy run for a self-set budget; save results off the pod. Choosing Runpod by hand needs `--owner-approved` (D26). A lab never lifts the GPU caps itself: environment overrides, alternate configs and `--owner-approved` need the owner's approval (§5.1), and the lab stages the command [owner 20 Oct, D52]. [D26, D26:caps, AGENTS:gpu-pods, AGENTS:budgets, PROTO:expired-lease, OWNER:17]
5. **Delivery:** short branch in your own worktree → PR → exact-head review → checks at that head, posted → merge queue, which serializes itself with no PM call per entry → verify on fresh `main` → delete branch and worktree → `uor-hygiene --apply`. Merge forward, never force. Queued is not merged; partial work says "References #N", and the PR whose unit meets its item's "done when" says `Closes #N` and sets the item to `done` in the same PR [D70]. Long-lived branches are `main`, `gh-pages` and `gh-pages-preview` (registry `docs/harness/branches.json`) and are never deleted; every other branch is `<lab>/<topic>`, one per open PR, deleted after its merge. **The exact-head review is part of the unit:** before the PR goes ready, its lab runs a fresh-context adversarial review that has seen only the item chain, the ORDER and the diff, never the plan, posts the `uor-review v1` record and queues the PR in the same session; no lab posts a review request and waits: "Reviewers waiting 30 minutes for other labs to see it is the entire problem." Other labs review after the merge: with nothing of higher unblock value, a lab audits recent merges by other vendors, and a finding becomes a repair item any lab can take. Every lab PR carries its ORDER and REPORT in `docs/loop/tasks/<item>/<lab>-<n>/` (§5.10); for an outsider PR, the maintainer lab that adopts it adds them. [AGENTS:delivery, R2, R8, R10, R-queue, AGENTS:merge-forward, HR:delivery; owner 24 Oct, D66, D70]
6. **Records:** one **notebook page per research line** (`docs/research/notebook/<line>.md`), one row per result: date, what ran, number, bar, verdict, artifact link. A dated evidence folder is kept only when a run seals artifacts. `docs/integration/NOW.md` plus the notebooks replace `current-state.md` as the running record. STATUS and ROADMAP change only with state, never as receipt logs. New results go to the HF store with checksums; iCloud `UOR-R4/results/` is a read-only archive indexed in `archive/storage/`; keep 30–70 GB free. [AGENTS:cadence-oct9, C:cadence, AGENTS:storage; owner 19 Oct; owner 20 Oct]
7. **Lessons:** pitfalls live in `uor-harness mistakes`, not here. [AGENTS:pitfalls]
8. **Approved sequences** (D34, D39 item 4, D41 item 3) live in `NOW.md` and bind until the owner changes them.
9. **Workspace.** One clone, `~/uor-r4`; the owner checkout stays on clean `main`. Each lab works in `.worktrees/<lab>-<topic>` (one per open PR), keeps scratch in `local/<lab>/<topic>/` and builds into `target/<lab>/`; nothing project-related lives elsewhere on the laptop. `uor-hygiene` runs after every merge. Details: [docs/labs/workspace.md](docs/labs/workspace.md). [owner 20 Oct]
10. **The loop**, adapted from the Loop Kit by Ron Brazil; details and build plan in [docs/loop/README.md](docs/loop/README.md) [owner 20 Oct, D43–D58; owner 24 Oct, D65–D71]:
    - **One unit per session.** A session does one build, repair, review or GPU collection, then closes, and the next starts fresh from the lab's PICKUP. Labs run continuously and stop only for an empty queue or the owner's kill switch. A session ends on `loop next`, never on a wait, and a supervisor that survives restarts starts any idle lab that owns the next move, on clients that can run headless [D45, D52, D65, D71].
    - **Reviews run inside the unit, never as a wait.** The lab's own fresh-context adversarial reviewer does the exact-head review (§5.5), the FIT (§4.5), the pre-run review and the decision review (§5.1). A pre-run review shows five things: the whole-project chain the run serves and why it is the right test now; that the mechanism is finished and every tool, input and checkpoint exists in the repository or the HF store; what a pass and a fail each unlock, refusing a run whose result would change nothing; the sheet's FIT; and a lease inside the caps. A decision review reads the charter, the milestone chain and earlier decisions, and refuses a card without that context. Work is taken in order of how many items it unblocks ("It's all about removing blockers at this point"), so a finished mechanism waiting on its GPU run comes first [D66–D68].
    - **Arrive by checking.** A session first checks its notes against the repository; where they disagree, the repository wins, and the session says so before any work [D43].
    - **An order before work.** Each task has an ORDER: its roadmap item, the files and areas in scope, a done-check, a cancel probe and a stop list. The cancel probe runs first; going outside the scope means stop and re-scope: a new ORDER, or a decision review (§5.1). Size is reported, never capped: "I don't think we can do our work honestly with a 200 line cap on PR's. Please allow any length since this is a research project and bookkeeping is the key" [D48].
    - **Negatives first.** The REPORT lists what did not work before what changed, then the measurements, the checks run and what is still open. The close writes the lab's PICKUP and keeps orders already carried out apart from standing rules [D43].
    - **The 2-hour check-in.** "2 hour limit should actually be a soft limit. If there is truly good work being done, it may be continue past 2 hours, but otherwise, the 2 hour cap is a checkin to close out sessions that have spiraled and/or stopped. (Although the PM should be prompting anyone stopped.)" A watched, leased GPU run under a FIT and a passed pre-run review is exempt [D53, D67].
    - **Notes are rendered, not hand-typed.** Once the harness renders them, STATE and HANDOFF replace `NOW.md` and `STATUS.md`, built from the roadmap items, claims and notebook rows; until then `NOW.md` stays the running record (§5.6). Each lab keeps its own PICKUP, ORDER and REPORT [D47].
    - **Subagents inherit the order,** with the same or a narrower scope, at any depth. A subagent never claims, opens or merges a PR, posts as the lab or decides (§5.2); it reports to its parent, and the lab's top session writes the REPORT [D50].
    - **One rulebook.** Rules live in this charter, its change log, the decision index and the lessons; a client's private memory holds pointers to them only [D57]. Ron Brazil's own text stays private: it is installed only in each client's local skills folder, never committed, and a local check guards it [D44].
    - *Why:* five labs from five vendors work at once with nobody watching each step. The loop gives every task an edge, a written memory and a check that can fail, so labs stay on the research goal and the records cannot drift, which was the costliest failure [D43].
