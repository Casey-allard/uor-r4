UOR-R4

The geometry of UOR-R4

Most chat AIs predict the next word by multiplying very large grids of decimal numbers. UOR-R4 is a bet that a different set of tools can do the same job more cheaply: rotations in a few dimensions, exact whole-number addresses built from primes, and lookup tables. This section explains those tools one chapter at a time, with pictures. It also says which ones the model uses today and which are research that has not yet been put to work. The project is pre-alpha: 1 of its 8 milestones is complete, and no model holds a useful conversation yet (PLAN.md and rendered STATE.md).

How the geometric pieces connect. Each arrow is one correspondence, and the table below says whether the link is forced by the mathematics or was chosen.

Why geometry

The owner's rule for this project is that the core of the model is built from geometric mechanisms. The reason is a cost hypothesis. A transformer's expensive parts are dense matrix multiplication, a score for every possible next word, and storing every earlier position. Rotations, exact addresses and tables may be much cheaper on a laptop (a hypothesis: no efficiency has been measured yet). Whether they are also good enough to model language is the open question.

These rules shape how the geometry is used.

  • No softmax or squashing, no matrix multiplication. Softmax, sigmoid, tanh and softplus are banned in every executed model path (D23, D25), and so is matrix multiplication in training and serving (D25, D30). Attention itself is not banned: bounded geometric reads replace it.
  • Research compute is GPU-first (D24). GPU results remain the qualification authority. D84 permits only the owner-authorized, named CPU training program to run CPU training, evaluation and parity as development research. Serving the exported D11 integer artifact on a client device (CPU, WASM, Apple silicon) is the product and is allowed. It uses no floating point. Since D80 and D81 (28 Oct 2026) it may use the hardware integer multiply and divide.
  • Floating point is for offline training only (D37). Float never re-admits softmax, squashing or matrix multiplication. The active discrete path and the served model stay integer (D11), and every float-trained candidate must report its export gap, the quality lost when converting to the integer artifact.
  • Geometry is a design priority, not a measured advantage. A failed experiment closes one configuration, never a whole mechanism (D22). A passing check on a piece of mathematics does not show that the piece helps a language model.

Labels on this page follow docs/formal_vocabulary.md: proof means derived from definitions or code, measurement means a recorded run, and hypothesis means an untested idea. Mechanism status is ACTIVE (on the current model path), READY (built and tested, not yet trained in) or PARKED (the tried forms failed or broke a rule, and the mechanism stays open). The mechanism board holds the full list. It replaces the older labels active, dormant and archived-negative.

The compliant next-token path

This is the path the current integer model (crates/uor-r4-discrete, called M1) follows for each token. Source for each step is in the architecture table.

flowchart LR
  tok["Token ID"] --> tab["Shared table:<br/>blocks of 8 integers"]
  tab --> ctx["Ordered context<br/>(ternary FBS plan)"]
  ctx --> read["Read:<br/>Route, Flock or Relation"]
  read --> wr["Shared writer:<br/>admission + exact distances"]
  wr --> out["Next token"]
  out -. "learning" .-> tab

The five steps of one token. The dotted arrow is learning, which changes the shared table by exact moves.

  1. Input. A token ID selects blocks from Snapshot.table.
  2. Context. Ordered ternary FBS plans (a three-branch tree over earlier tokens; see the glossary) preserve context order for the read.
  3. Read. Route selects one carrier per block and transports it without summing or snapping. Flock ranks eligible nodes, transports them, sums and snaps. Relation adds finite relational reranking before the Flock selection. See route read, flock read and relation read.
  4. Shared writer. Product-address admission and exact distances select a token using the same table. The writer is implemented (admission).
  5. Learning. The learner compares virtual exact moves on a fixed batch and accepts objective improvements through the admitted driver. rows_v1 parallelizes proposal work (discrete learning).

Each block is 8D, and four blocks give width32. The carrier has 16 roots, acted on by 64 signed transport actions (build.rs). These three counts describe different objects. The orbit is not full E8 coverage.

The earlier float operator path is preserved as evidence and is not the current token path. It includes the Hamilton gates (G2), the geometric recurrence and the delivered head (OP3a). See the operator record, the head record and the historical geometry tour. Its earlier sheets are inactive until they are re-registered and reviewed under D37. The dated operator diagram illustrates those retained operators.

Two cautions for anyone building on this.

  1. Half-turns do not compose like bivectors. Two half-turns whose K6 edges share a vertex multiply to an order-5 rotation, never a half-turn. The match between primes and half-turns is a correspondence of sets, not of products.
  2. Labelling primes to axes is a choice. A design that routes primes through icosian rotations must say which of the 12 inequivalent labellings it uses.

Serving without multiplication

A served kernel has no floating point. Under D11 as first written it also had no multiplier instruction, so a product of two runtime values is read from a table. Since D80 and D81 (28 Oct 2026) the hardware integer multiply and divide are allowed, and since claude-177 the stack's kernels use them. The table method they used before is described here, and it stays the tests' reference. Build the sixteen multiples (0 to 15) of one operand by repeated addition, index that table with the radix-16 digits of the other operand, and combine the results with shifts and adds. For example, to compute \(37 \times 43\), the table holds 0, 37, 74, …, 555. Write 43 as hex 0x2B, with digits 2 and 11. Then

\[37 \times 43 = (T[2] \ll 4) + T[11] = (74 \ll 4) + 407 = 1184 + 407 = 1591.\]

A 4-bit weight is a single digit, so one product is one table read. Division is restoring long division, square root is digit-by-digit, and the kernels are kept opaque to the optimiser so that an add chain is not folded back into a multiply. Products are taken modulo \(2^{64}\) or \(2^{128}\) to match the earlier integer engine. The code is in crates/uor-r4-integer/src/stack/kernels.rs (stack_mul_u64, stack_div_u64, stack_isqrt), and the ARM64 audit is scripts/audit_zero_matmul_serving.py --stack. The numbers in the example are illustrative and are not taken from the code. The serving contract is described on the D11 integer serving page. It is ACTIVE as the export boundary: the discrete M1 pair and the separate FBS lut-stack/5 trunk have been exported and served at their declared scopes.

Reproduce the figures

The status diagrams (architecture, milestones, pipelines, the geometry stack, the compliant path and the operators) are generated in Rust, and CI-style checks confirm that they are current:

cargo run -p xtask -- figures            # check
cargo run -p xtask -- figures --write    # regenerate

The mathematical figures in the chapters are drawn by a standard-library script. Porting it to Rust (D27) is a recorded follow-up:

python3 docs/figures/geometry/generate.py
