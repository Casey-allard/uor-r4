## [09] Addressing schema

Format: O0.O1.O2.O3 , basis_id geo.dodeca-icosa.v1 . Fields that depend on the selected demarc are prefixed [demarc=N] in the serialized SpiralCore label. A peer using a different context would interpret those fields differently because rebuildCubes() changes which physical vertices a cube slot, tetra slot, or invariance flag refers to. Context-free identifiers never need this tag.

 IPv6 documentation mirror: every four-octet symbolic identifier is also displayed reversibly inside 2001:db8::/32 . Each O-field occupies one hextet before RFC 5952 text canonicalization. An E8 240.S.0.0/16 group maps to a documentation-only /64 . This is a structural one-to-one presentation—not IPv4-mapped IPv6, not a bit-preserving prefix conversion, not ULA space, and never a deployable address. The decoder accepts both v64's legacy structural spelling and equivalent RFC 4291/5952 spellings.

 Four Bell semantics, no address breakage. MF-LAYER keeps v61's mapping of the fifteen core O0 layer prefixes 0,16,...,224 to codewords 0...14; H3ROOT and H2DEC remain typed members of O0= 176 , the existing H3/ICOSIDODECA family. MF-PORT uses an AXIS2 node's own axis id. MF-H2 walks the ten oriented H2 roots and uses the actual AXIS2 direction carried by each root, producing five legitimate two-of-six codewords twice each—not six invented single-frequency Bell symbols. MF-OP is edge metadata: the route action x→B ij x supplies the Bell pair directly. The E8 subnet family uses O0= 240 , outside the fifteen active Bell layer codes; its sounds come from operators, not by pretending a sixteenth 2-of-6 pair exists.

 Scope boundary: [demarc=N] is a SpiralCore context/realm tag, not a CIDR prefix. E8 “operator subnet” is likewise a protocol-local name for one verified 16-root action orbit; it does not claim external IP allocation or CIDR routing behavior.

The 1,020-record difference is genuine label multiplicity: different bivectors can send the same source root to the same target. There are no self-loops. Labelled out-degree is exactly 15; unique-target out-degree is 9–13 and is non-uniform inside every 16-root subnet. Here and in the manifest, 3,600 “actions” or “transitions” means labelled records, never distinct graph edges.

 F4 convention boundary: this build uses the self-dual realization in which the embedded binary-tetrahedral/D4 24 remain at norm²=1 and are called short , while the complementary 24 are scaled to norm²=2 and called long . The usual coordinate presentation instead makes the 24 roots ±e i ±e j the long D4 subsystem and the remaining 24 short. Exchanging the length classes gives the dual, isomorphic F4 root system; the build is valid, but its convention is now explicit.

 Incidence fan-out, not IP multicast. Each AXIS (5-fold) is incident to 8 bridged icosians (4 rotation powers × 2 signs), each AXIS3 to 4, and each AXIS2 to 2.  The rhombic triacontahedron : for each of the 30 dodecahedron edges, its two vertices plus the two zone centers of the faces sharing it form a candidate face — but only at the exact scale factor rtScale = 3 − φ (closed form, not a decimal approximation) does each one become a genuine golden rhombus: all 4 sides equal, both diagonals in an exact φ ratio. Verified on all 30, not sampled. This scale applies only to RHOMB's own rendering and address geometry — it does not change the ICO layer's position anywhere else in the file.

## [13] Stabilizers and the inversion angle-invariance

Every point's stabilizer (the subgroup of the 60-element rotation group that fixes it) was verified by directly building the group and counting, not by trusting orbit arithmetic: ROOT = 60 (fixed by everything — the maximum possible, confirming it as the group's true center), ICO = 5 , VERT = 3 , DUALFACE = 3 (matches VERT exactly, via the equivariant bijection already established), AXIS (5-fold, as a line) = 10 , AXIS3 (3-fold, as a line) = 6 , AXIS2 (2-fold, as a line) = 4 . CUBE, TETRA, and ICOSIAN stabilizers were not computed in this build — they're set-stabilizers rather than point-stabilizers and need a different method, flagged rather than guessed.

 Separately, verified numerically: the inversion transform (r,θ) → (R²/r, θ) changes only radius, never angle — tested across five angles, zero deviation at each. This is why root's stabilizer and the inversion behave the way they do together: root is fixed by every rotation (the maximal stabilizer), and inversion about that same point can only ever act on the one coordinate rotation doesn't touch.
