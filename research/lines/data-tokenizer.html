UOR-R4

Research line: data and tokenizer

A language model never sees letters. It sees numbered pieces of text, and it learns from whatever text it is given. This line holds the small set of records about both choices: which tokenizer cuts the text, and where training text comes from. The project has used one 4,096-piece tokenizer for every current corpus, panel and model. A larger one is prepared as a tool but never trained. The newest records plan a one-time, owner-approved corpus written offline by a large open model.

Two preparations on 19 October; neither has produced a model result.

What it set out to do

Fix a single text-to-piece mapping so every corpus, test panel and trained file refers to the same pieces, and decide where enough good training text can come from.

What happened, in order

  1. Corpus sizing (16 Aug). A historical scaling-law document measured a coverage knee near 1.5 million records, then a correction said the sweep was not fixed-partition evidence and gives no estimate of the exponent (scaling law).
  2. Teacher rehearsals. A pinned small teacher compiled a 20,000-token corpus into table-native artifacts, explicitly not a quotable quality baseline (record). A how-to for refreshing a corpus with the frozen integer runtime alone labels the result self-distilled, kept apart from teacher-fidelity numbers (record).
  3. Reuse audit (3 Sep). External repositories were audited for licences and interfaces. No new dependency was admitted and matrix multiplication was rejected as a backend (audit).
  4. Dialogue format (26 Sep). A contract binds training, panel and chat encoders to one tokenizer identity and a shared role format. So far only the integer session path uses it (contract).
  5. 19 Oct: two preparations. A deterministic Rust command can train a byte-level BPE tokenizer of 16,384 pieces; it does not change the active tokenizer (trainer). Decision D41 lets one open model (gpt-oss-120b) write a training corpus offline once, then never run again for the student. The estimated production corpus of about 30 million tokens costs about $52 to $63 on one large GPU, and executing it needs a separate owner release (D41). A host-only checker that validates such a corpus against its registered sheet passes 32 of 32 self-tests, with no generation run (verifier).

What it taught

A tokenizer is a hidden hypothesis. The missing multi-digit pieces look like an obvious cause of the numeric-memory failures, but an untrained probe found that the number codec already stores two-digit values in order, so the failure sits in the learned read and emit path (probe). A number-aware tokenizer was planned and never built or run (docs/labs/repo-renormalization-2026-10-19/audit/mechanisms/tokenizer.json, field never_tested). A data source that is borrowed, such as a teacher, sets the ceiling (lesson 5 in what the project knows). Self-distilled numbers must stay apart from teacher-fidelity numbers.

Current state

Nothing has been trained on any tokenizer except d36d3e87. The never-run tests are 4,096 against 16,384 pieces, a number-aware tokenizer, and whether tokenizer choice interacts with the address placement of the discrete model. D41 releases no training hold: generating a corpus is not training the student (scope note).
