UOR-R4 D0-a — dynamic measurement is not available on this hardware, and where the VSA multiplies actually come from
Date: 2026-09-19
Executed by: Zed (agent), local M1 checkout /Users/casey.allard/uor-r4

PART 1 — FEASIBILITY: THE DYNAMIC HARNESS I PROPOSED CANNOT BE BUILT HERE
  I recommended a dynamic retired-instruction harness reporting multiplies per token. Checked
  before building it, and it is not available:

  * `xcrun xctrace` — **not present** on this machine ("unable to find utility xctrace"), so the
    Instruments CPU-counters route is closed.
  * `frida` — **not installed**, so software dynamic binary instrumentation is not available
    without adding a dependency.
  * Apple's PMU — the kernel does expose kpc counters (`kern.num_static_scalable_counters: 90`,
    `kpc.pc_capture_supported: 1`), but ARMv8 defines no architectural **multiply** event, and
    Apple's implementation-defined events are undocumented. A hardware multiply count therefore
    cannot be obtained, with or without root.

  Stated plainly: **there is no way on this hardware to measure executed multiplies directly.**
  I proposed an instrument that does not exist. That is the fifth time an instrument for this
  question has been wrong, and this time the error was mine before a line was written.

PART 2 — WHAT I DID INSTEAD: IDENTIFY THE SOURCE, WHICH IS SOUND
  Locating the instruction pattern is a sound method even though counting is not. Disassembling
  `MultiHeadVsaAttention::attend` and inspecting the multiply sites with their neighbours gives an
  unmistakable signature:

      eor x16, x12, x12, lsr #30      <- z ^= z >> 30
      eor x17, x11, x11, lsr #30
      mul x14, x14, x25               <- z *= a 64-bit constant
      mul x15, x15, x25
      mul x16, x16, x25
      mul x17, x17, x25
      eor x16, x16, x16, lsr #27      <- z ^= z >> 27
      mul x14, x14, x26               <- z *= another 64-bit constant

  The `>> 30` then `>> 27` sequence, interleaved with `mul` by a register-loaded 64-bit constant,
  is the SplitMix64 finaliser. Confirmed independently: the constants `0xbf58`, `0x94d0`, `0x9e37`
  and `0x1331` all appear in the disassembly (16, 21, 30 and 16 occurrences).

  `Hypervector::from_seed` is SplitMix64, four multiplies per 64-bit word. `attend` obtains token
  vectors through `Codebook::get`, whose fallback for a token not in the table calls `from_seed`,
  and it is inlined into `attend`.

PART 3 — CORRECTION TO MY OWN EARLIER CLAIM
  I reported that "the inert mechanism is the largest multiply consumer — the VSA layer is 898 of
  3,100 = 29 % of serving multiplies", and built a redesign on it. **That was a static artifact
  and it is wrong as a statement about serving.**

  The multiplies are on the **on-demand codebook path**, which calls SplitMix64 to synthesise a
  hypervector. Under `vsa_code_mode = 1` (`Codebook::from_vectors`, table materialised) `get`
  hits the table and `from_seed` is never called, so those multiplies sit in the image and **do
  not execute**. Static presence is not execution — which is exactly the flaw I identified in the
  instrument one step earlier, and then failed to apply to my own reading of it.

  Count caveat: the `attend` figure of 306 counts only symbols whose mangled name matches
  `MultiHeadVsaAttention`. A separate span extraction over everything between the first and last
  such symbol reported 1,906 — that span crosses other symbols and is **not** the method's own
  count. Only the symbol-matched 306 was ever reported as such, and it should not be inflated.

PART 4 — THE SOUND SUBSTITUTE FOR A COUNT
  A **per-function zero-check** is sound where a count is not: if the disassembly of a function's
  address range contains no multiply mnemonic, that function cannot execute a multiply. That is a
  sufficient condition, it is checkable with the tooling already present (`otool` + symbol ranges),
  and it does not care about dead code, inlining or compiler decisions.

  Proposed check: designate the serving entry points and their transitive callees, assert **zero**
  multiply mnemonics in each function's range in a `--release` build, and ratchet. It cannot be a
  cargo unit test (it needs a release build), so it belongs as a checked-in script plus a recorded
  procedure, re-run on any serving-path change.

  Under this check, the current tree would FAIL for the VSA attention symbol and PASS for
  `context_predicted_fiber_from_ring` (mul = 0) and `binary_model` (4, and the four are not in the
  certified set). That failure is the honest starting point.

PART 5 — THE ACTIONABLE FIX THIS IDENTIFIES
  The multiplies are not in the correlation arithmetic (the `* 32767` was already a shift) and not
  in the bundle/majority logic. They are in **on-demand pseudorandom hypervector generation**. Two
  sound ways to remove them:

  1. **Guarantee the materialised codebook in serving.** Mode 1 already does this; extend the
     guarantee so no serving path can reach the on-demand fallback. Cheap, but leaves the fallback
     as latent non-compliance.
  2. **Make the generator multiplier-free.** SplitMix64's two `wrapping_mul` calls by arbitrary
     64-bit constants are the entire cost, and the hypervector bank is *arbitrary by construction*
     — any fixed deterministic pseudorandom family works. An xorshift/rotate mixer uses only
     shifts and `eor`, so it is multiplier-free, and it makes the fallback compliant as well as
     the materialised path. This also makes the per-function zero-check passable.

  Option 2 is the better engineering answer: it removes the possibility rather than excluding the
  path that uses it. It is a behavioural change (different codes), and because the stored
  `hierarchical_codebook` anchors are built from those codes it requires the anchor rebuild that
  `prepare_vsa_code_mode` already performs, plus a re-measurement of routing recall and BPB. It was
  not implemented here.

NOT DONE
  * No dynamic harness: not buildable on this hardware, as established above.
  * No code change: the generator swap (option 2) is a behavioural change needing its own
    measurement, and the correlation-identity change from the previous step was a measured no-op
    that is already recorded as such.
  * The per-function certification script is specified above but not written.

STATUS OF THE QUESTION
  The project still does not have a per-token executed-multiply number, and on this hardware it
  cannot get one by counting. It CAN get a sound per-function guarantee, which is stronger for the
  functions it covers. That is the recommendation and it is not yet implemented.
