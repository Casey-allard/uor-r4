PART 1 — THE ZERO-CHECK, AND WHY IT IS SOUND WHERE COUNTING IS NOT
  Four counting instruments for "how many multiplies does serving execute" failed here: raw grep
  of `*`; the `forbidden_arith` scanner; a token-level classifier; and a static binary
  disassembly count. A hardware multiply counter is not available either (`xctrace` absent, no
  architectural MUL event on ARMv8).

  The replacement is `scripts/serving_multiplier_check.py`. It disassembles a `--release` binary
  with `otool -tV`, segments **per symbol**, and for each symbol in a declared CERTIFIED list
  asserts **zero** multiply mnemonics. That is a *sufficient* condition: a function whose own
  instruction range contains no multiply cannot execute one. It is indifferent to dead code, to
  inlining and to compiler strength reduction — the three things that broke the counters.

  It also reports what it cannot check. Seven declared serving names have **no release symbol**
  because they are inlined (`compose_context_roots`, `score_readout`, `score_vsa_candidate`,
  `hamming_distance`, `bipolar_correlation_q15`, `similarity_q15`, `cluster_of`), so they are **not
  certified** and the script says so rather than implying coverage. The whole-binary multiply
  total is printed as INFORMATIONAL with an explicit note that it counts instructions present,
  not executed.

PART 2 — WHAT IT FOUND IMMEDIATELY
  First run:

    context_predicted_fiber_from_ring   mul=0   PASS
    context_fiber_from_ring             mul=8   FAIL   (hopf_fiber_project's S3->S2 map)
    compose_ring_roots                  mul=4   FAIL   (exact 2I composition!)
    binary_model                        mul=4   FAIL   (3 symbols)
    score_token                         mul=34  FAIL   (hierarchical lattice scoring)
    MultiHeadVsaAttention               mul=306 WATCH  (SplitMix64 on-demand generation)

  A composition helper that is supposed to be pure table lookups carried four multiplies. The
  cause is instruction-level, not source-level: `% GROUP_ORDER` and `state * GROUP_ORDER` address a
  120-wide table, and a modulo or multiply by a non-power-of-two constant is lowered to a `umulh`
  / `madd` sequence. **No source census could have found this**, because the source contains no
  multiply at all in either place.

PART 3 — TWO MEASURED REDUCTIONS, USING THE SOUND INSTRUMENT
  1. `token_to_root[..] as usize % GROUP_ORDER` replaced by `.min(GROUP_ORDER - 1)`. The modulo was
     redundant: `token_to_root` holds canonical root indices and the loader guarantees the range, so
     the reduction is a defensive bound and a branchless min is equivalent and multiplier-free.
     **`compose_ring_roots` 4 -> 2.**
  2. The product table's row stride padded from 120 to 128, so the row base is a shift rather than
     a multiply by 120. Cost: 960 padding bytes (15,360 vs 14,400). **`compose_ring_roots` 2 -> 1.**
     Held-out behaviour unchanged: greedy 128-token generation is byte-identical, and 617 tok/s.

  Whole-binary informational total: 3,000 -> 2,996. The point is not the global delta, which is
  not an execution count; it is that `compose_ring_roots` fell from 4 to 1 against a *sound*
  per-function measure, and that the remaining 1 is now a specific, located instruction.

  Self-inflicted regression, recorded: changing the stride broke three group_table tests and then
  a fourth assertion, because the tests used `GROUP_ORDER` as the stride. Fixed to `ROW_STRIDE`;
  6/6 pass. `cargo fmt --check` and `check_claim_wording.py` clean.
