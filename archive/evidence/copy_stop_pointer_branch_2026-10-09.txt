UOR-R4 — Serving-time copy stop on the pointer branch: it recovers F=1.0 from 6/84 to 46/84 and every floor above 0.5, but it does NOT reach the F=0.5 plateau, so the degeneration above 0.5 is not merely termination (a value-token stop, min_span=3, is implemented and NOT run)
Date: 2026-10-09 (evening round). DeepSeek session. References #820. Follows gate_floor_breakthrough_2026-10-09.txt (#2008) and the run card gate_floor_run_card_2026-10-09.txt (#2007).

THE QUESTION
  The gate floor peaks at F=0.5 and collapses after it: arm-ptr 35 -> 40 -> 49 -> 16 -> 6 over
  F = 0, .25, .5, .75, 1.0. At F=1.0 the gate is exactly 1.0 and the value is PRESENT in 79/84
  replies (p_mixture of its first token 0.8700) yet exact copies are 6/84, because the replies no
  longer terminate or read as the value alone ("Fennor.\n\nAss name is Fennor. Fennor.\n\nA"). The
  stated reading was that ABOVE ~0.5 THE BINDING CONSTRAINT IS THE GENERATOR'S CONTRIBUTION TO THE
  REPLY'S SHAPE AND TERMINATION. This experiment tests that reading directly, with a serving-time
  stop rule on the pointer branch.

WHAT RAN
  An optional serving-time rule, `pointer_copy_stop=MIN_SPAN`, default 0 = OFF = the historical
  decoder bit for bit (`greedy_reply`, i.e. the pre-existing `greedy_reply_with`). Generation ends
  once an emitted id breaks a run of at least MIN_SPAN ids reproduced from the window that the
  pointer ITSELF selected: at each step the source the head attends most (the lowest index on a
  tie), then the consecutive window positions after it. The run may open at that source or at the
  position after it (the head may select the position just read). A run that breaks before MIN_SPAN
  is not a copy and the reply continues as if the rule were off. Values are not consulted: the rule
  never sees the expected term, only the model's own selection.
  MIN_SPAN = 2 was pre-registered here as the test of the stated hypothesis (the smallest thing
  that is a span). A stricter MIN_SPAN = 3 is implemented and NOT run in this round (see SCOPE).
  Inference only, no training, no new parameters, no serialization or export change. The gate floor
  from #2008 is untouched and combines with it.

  GRID, on the three existing checkpoints, 28 never-seen values x 3 conditions = 84 cells each,
  protocol 2, greedy, max_new_tokens 40, device=cuda, one session, one binary:
    F = 0 (untouched reference), then F = 0.5, 0.75, 1.0 each WITHOUT and WITH the rule.

THE DEFAULT IS PROVABLY UNCHANGED
  The F=0 runs were compared RECORD BY RECORD against the sealed pre-change files
  (bindprobe/rate/arm-ptr-{natural,sure,noted}.json for arm-ptr, ptrident/rate-arm-a-w05-*.json and
  ptrident/rate-arm-c-ctrl-*.json for the identity arms): every field that existed before this
  change - reply, reply_ids, reply_eos, window_ids, window_text, span positions and sizes, all read
  masses, the pointer gate/attention/span masses, the marker generator and mixture probabilities -
  is IDENTICAL on 9 of 9 arm-condition files (288 records, zero differing fields), and the exact
  counts reproduce the sealed ones exactly: arm-ptr 12/10/13 = 35/84, arm-a-w05 2/2/6 = 10/84,
  arm-c-ctrl 10/11/3 = 24/84. The only added fields are the new ones, all null or empty with the
  rule off. The probe was rebuilt from current main (b7541b9f9) on the pod; the pre-change and
  #2008 binaries in bindprobe/floor are preserved untouched.

THE MECHANISM: THE RULE STOPS ON THE PROMPT TEMPLATE, NOT ON THE VALUE - AND THAT IS WHY IT CANNOT
REACH THE PLATEAU
  A per-step pointer trace (`copy_trace=1`; the same selection the rule uses, recorded for every
  generated id) was taken on the ruled F=1.0 runs and compared with the window's OWN value span
  (`span_positions.expected`). The matched run the rule stops on is a copy of the question template
  ("User: My nam...", "Assistant: Sure.<|eos|>..."), not of the value:
    arm             fired    matched run inside value span / overlaps / outside    exact among fired
    arm-ptr   F=1.0  79/84   20 / 57 / 2                                            44 of 79
    arm-a-w05 F=1.0  50/84    2 / 47 / 1                                            43 of 50
    arm-c-ctrl F=1.0 82/84   18 / 59 / 5                                            51 of 82
    arm-a-w05 F=0.5   6/84    6 /  0 / 0                                             0 of  6
  At F=1.0 the head keeps selecting the just-written positions, so the reply walks down the prompt
  template it is re-reading; a template run completes and then breaks, and the rule stops there.
  That is LUCKY TIMING, not value detection. Each invented value tokenizes to about 5-7 ids (the
  exact replies of the best configuration run 5-8 ids per value, and not one of them is a single
  id), so the value is written over several steps while the run the rule is watching is the
  template's. Where those two intervals line up well enough - the template run ends after the
  value's ids have all been emitted - the stop leaves " Vantel.\n\n" and the reply reads as the
  value alone, which is why the recovery is real but partial. Where they line up badly the reply
  stops early and is not exact (" Brind is" for n_brindor). THE FLOOR KEEPS THE VALUE PRESENT
  (p_mixture 0.8700) BUT AT F=1.0 THE POINTER DOES NOT SUSTAIN THE VALUE'S OWN SPAN, and the
  template run ending right after it is a coincidence of these rows, not the mechanism working.
  The mechanism channels are CONSISTENT WITH THIS AND WITH #2008: the reported gate, pointer mass on
  the value span, read mass and p_mixture of the value's first token are bit-identical with and
  without the rule wherever the window is unchanged (arm-ptr F=1.0: gate 1.0000/1.0000, ptr on value
  0.8342/0.8296, read 0.5789/0.5564, p_mixture 0.8700/0.8644; the small differences are the shorter
  windows the rule produces). THE FLOOR MOVES ONLY THE MIXING WEIGHT, THE STOP RULE MOVES ONLY WHERE
  THE REPLY ENDS, AND NEITHER CHANGES WHAT THE POINTER IS LOOKING AT. At F=1.0 what it looks at is
  the template it is re-reading.

WHAT THIS SETTLES
  1. THE SHAPE/TERMINATION READING IS PARTLY RIGHT: termination alone is worth +40 cells on arm-ptr
     at F=1.0, +38 on arm-a-w05 and +45 on arm-c-ctrl, with essentially no cost. The F=1.0 collapse
     is NOT an information problem - the value is present in 79/84 replies and the floor keeps it
     there.
  2. BUT IT IS NOT MERELY TERMINATION: a stop rule on the pointer's own selection recovers to 46/84
     on arm-ptr and 64/84 on arm-a-w05, not to the 49/84 and 59/84 the floor already reaches at 0.5.
     At F=1.0 the constraint above 0.5 is the COMPOSITION - with the generator crowded out the
     pointer follows the prompt template rather than the value, so where the reply stops and what it
     reads as are both symptoms of the same thing, and fixing only the stopping point leaves ~3
     cells (and the value-alignment) behind.
  3. THE BEST MEASURED CONFIGURATION IS NOW 65/84 = 0.7738: the identity-lineage arm (whose
     unfloored read-out is 0.1190) at gate floor 0.75 with the copy stop on. The gate floor and the
     stop rule are complementary and their optimum is INTERIOR in both knobs - F=0.75, exactly the
     point where the floor stops being the only problem.
  4. MIN_SPAN=2 IS A WEAK INSTRUMENT AND ITS FIRING IS ONLY LOOSELY RELATED TO THE VALUE. This is
     measured, not inferred: at F=0.5 the rule fires on 6 cells and every one of those firings is a
     cell that was exact WITHOUT the rule (0 of 6 exact among fired); at F=1.0 the matched run is
     inside the value's own span on 20 of 79 cells (arm-ptr) and 2 of 50 (arm-a-w05). The next
     instrument must tie the stop to the value's tokenization, not to a span length: a token-identity
     stop, min_span=3, is implemented behind the same flag and is the obvious next run.

HONEST POSITION
  84 cells per arm per condition, one seed per arm, greedy, one session, one rebuilt binary, and the
  default reproduced field-for-field against the sealed files on all three arms. The rule is a
  read-out change only and is not saved. The trace is a diagnostic, not a scored channel.
  NOT MEASURED: MIN_SPAN=3 (implemented, not run); the rule under a non-greedy decoder; any other
  panel; any trained arm other than these three; any integer/D11 port - export still refuses a
  pointer with an identity term ("no integer port"), so this remains an offline-capability result.
  The "token-identity stop" that the alignment measurement points at is a hypothesis for the next
  run, not a result.
  The one thing this round did NOT reproduce is a positive control for the rule itself: no
  configuration in the grid shows the rule firing mainly on the value span, so its mechanism claim
  rests on the trace counts above, which are reported in full.
