## Source diagnosis and reused mechanism

The existing scanner already retains exact entity bytes in the four lexical cues
preceding a numeric literal. `operand_provenance` compares those bytes directly
with the current query, independently of dictionary membership, then carries
query/cue position masks into the two-lane signed-H4 selector. The historical
[operand-provenance result](native_geometric_operand_provenance_1139.md) established
bounded computed-result selection using that information. The shared
[literal extension](native_geometric_literal_selection_1139.md) later regressed
computed roles; the separate literal component and admission gate now protect
that boundary.

For `How many coins does <name> have? Assistant:`, the queried entity is at query
position 2 and its ordinary `<name> has <number>` literal cue is at position 1.
Copy therefore exposes `(kind=5, a=2, b=66)`. Parent 433e has no learned code for
this feature. Its existing query-position-2 provenance codes are all geometric
identity. Exact binding survives capture but is skipped at learned-code lookup.
First-turn retained query words can also include preceding facts: the existing
query boundary is the session/response boundary, not a parser for a `User:`
delimiter. Reordering facts changes those extra features. Neither diagnosis
justifies inventing a new entity scanner, dictionary name list or semantic
metric from hash bits.
