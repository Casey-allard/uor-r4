## The history: I built this, measured it, found it wrong, and removed it

Two units ago I implemented this rule against **`ruleinventory::all_ids()` — the rules the *port* has implemented** — while the rule must resolve against the rules the **engine** registers. Four real lessons whose guards name a `prlint.*` gate were reported as *"not a rule this engine registers."* **Rust said 4, Python said 0.**

**I removed the function rather than ship it approximate**, because *"a guard check against an incomplete port is not a weaker check, it is a wrong one — it would tell authors to delete guards on real rules."*

## And the fix repeated the mistake once

My first correction put the id set in a data file, generated from **`checkrules.rules()` — 40 ids.** **The probe still read 4 findings.**

**Measured against Python: `_known_rule_ids()` returns 53.** The engine resolves guards from **three sources**:

| source | contribution |
|---|---|
| `checkrules.rules()` | 40 |
| each module's own `register_rules()` | 13 more |
| `prlint.GATE_RULES` | gates raised against a **PR body**, not repo state |

**My data file took the first source and stopped — the same false positive, in a new place.**

**The lesson repeated exactly: I asked "what rules are registered" and answered with the first list I found, twice, instead of reading the function that answers the question.** The second time I caught it **only because the same probe that caught the first still read 4.**

## Why the extra 13 are not padding

**`prlint`'s gates are raised against a PR body, which the engine never has** — so they are declared as data rather than registered as checks. **A lesson may still cite one as its guard, and four do.** **Resolving guards from the check registry alone excludes precisely the guards a lesson is most likely to name, because the lessons are about how PRs are written.**
