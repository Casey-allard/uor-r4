## Disposition of the four earlier findings

**1. Atomic replacement — materially improved, still incomplete (session.rs:920–951).** Writing a create-new sibling, completing the write and syncing the file before rename fixes the original direct truncation hazard. Two concrete faults remain:

- Parent open/fsync failures are discarded at944–945, so the API can return success despite failure to persist the replacement directory entry. A basename-only relative path also has an empty parent; opening that empty path fails and is silently ignored. Normalize an empty parent to `.` and propagate the directory synchronization result. If failure occurs after rename, report that the new complete file may already exist; do not falsely promise the previous contents survived every possible error.
- On `create_new` failure, the error path unconditionally removes `temp_path` at951 even though this invocation never created it. A stale file from a reused PID/counter or another preexisting entry can therefore be deleted. Only clean up a temporary file owned by this successful create, or retry a fresh name without removing the colliding entry.

The added failure fixture (tests.rs:773–803) saves to `checkpoint.json/impossible_subfile.json`, a different impossible target, so its unchanged-checkpoint assertion does not exercise failure while replacing the original path.
